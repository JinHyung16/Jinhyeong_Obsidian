# 정답지

상위: [클라 파트](Client.md)

## 정답지 제작

### 요약

- 정답지는 원본을 N가지 상태로 돌려 계산 결과 전 필드를 덤프한 것이다.
- 이건 프로젝트가 직접 만드는 것이다. 어디서 받아오는 게 아니다.
- 정답지만 있고 채점기가 없으면 「검증됨」이 아니다.

### 규칙

- #강제 [원칙 R6](원칙.md#R6) 하네스가 없는 동안 그 수치 항목은 `미측정(③ 하네스 없음)`, 달성률 0% 다 (분석로직 「섹션별 기입 규칙」).
- #강제 [원칙 R6](원칙.md#R6) 채점기 없이 정답지만 남은 상태는 「검증됨」이 아니다.

### 설계

| 무엇 | 누가 | 언제 |
|---|---|---|
| 원본을 헤드리스 브라우저로 돌려 정답지(json) 덤프 | Transfer_Programmer (Client 지식 기반) | G2 를 열기 전 |
| 파서 · 필드 대응 · 채점기 · 에디터 메뉴 (`.cs`) | Transfer_Programmer | 같이 |
| 어느 상태를 몇 개 뽑을지 (스위트 설계) | Client 지식이 `02_시스템_*.md` 로 넘긴다 | 학습 단계 |

| 자리 | 무엇 | 수명 |
|---|---|---|
| 정답지 JSON | N벡터 | 프로젝트와 함께 남는다 |
| 채점기 (에디터 메뉴) | 정답지를 읽어 이식본과 대조 | 게임별 하네스라 이관이 끝날 때까지 남긴다. 회차용 검사기만 회차 끝에 지우고 `Tools/Verify/out/` 은 회차마다 비운다 |

- 하네스 제작은 별도 리스트업 항목으로 올리는 것이 기본이다 (PD 「재는 도구를 먼저 만든다」). 이유: 「스탯 환원」 아래 묻히면 재는 도구가 없는데도 수치 항목이 진행 중으로 보인다.
- 전제: 정답지는 임의 키 수백 개짜리 맵이라 `JsonUtility` 로 못 읽는다. 선택지와 접점 격리는 [DataFramework 「전제」](DataFramework.md).
- 주의: 스탯 계통을 다시 손대면 기본 순서는 채점기를 먼저 복원해 돌린 뒤 고치는 것이다. 이유: 고치기 전 기준선이 있어야 무엇이 바뀌었는지 보인다.

## 출처 대조

### 요약

- 순서를 지킨다. 출처 대조가 채점보다 먼저다.
- 정답지는 특정 시점의 원본 데이터를 전제로 뽑혔다.
- 전제가 깨지면 실패가 전부 계산 오류로 보인다.

### 설계

기본 순서는 출처 대조기를 먼저 돌려 계열별 노드 수가 정답지 메타와 같고 주입 키·유닛 코드가 전부 있는지 보는 것이다. 「전부 일치」여야 그다음 실패를 계산 오류로 읽을 수 있다.

## 이름 대응

### 요약

- 이름 대응은 규칙 두 개 + 예외표로 끝난다.
- 원본 JS 는 camelCase, 이식본은 PascalCase 다.
- 예외가 많으면 대응표보다 이식을 먼저 의심한다.

### 규칙

- #강제 [원칙 R9](원칙.md#R9) 대응 필드가 없으면 「대응 필드 없음」으로 세어 보고한다.

### 설계

- 예: 310키 중 296키가 규칙만으로, 13건이 `_xxxDed → XxxDedicated` 규칙으로 맞았다.
- 사례: 원본 `s.guidedMult`(2948)를 `GuidedMul` 하나에 겸해 쓰던 미이식을 잡았다.

## 실패 분류

### 요약

- 실패를 세 갈래로 갈라 놓고 시작한다.
- 채점기가 상대오차 분포를 같이 찍는 것이 기본이다.

### 규칙

- #강제 [원칙 R9](원칙.md#R9) 비교에서 뺀 정답지 필드는 건수와 사유를 보고한다.

### 설계

| 갈래 | 신호 | 처방 |
|---|---|---|
| 자료형 한계 | 상대오차 1e-9 ~ 1e-6 구간에 몰림 | float → double. 계산은 안 건드린다 |
| 진짜 계산 차이 | 1e-6 초과 · 특정 스위트/필드에 집중 | 원본 라인과 대조 |
| 정답지 쪽 결함 | 기대값이 모든 벡터에서 같은 이상값 | 비교에서 빼고 왜 뺐는지 적는다 |

예: 79,897필드 중 완전일치 77.7% · 1e-9~1e-6 구간 12,748 · 1e-6 초과 754. 분포 없이는 754건을 못 찾는다.

## 정답지 결함

### 요약

- 정답지도 틀린다.
- 기대값이 전 벡터 동일이면 생성기를 의심한다.

### 설계

- 예: `stats._syn` 이 230벡터 전부 `{}` 였다. 원본이 `s._syn = new Set()` 이고 `JSON.stringify(new Set([...]))` 는 언제나 `{}` 다. 6종을 옳게 켠 이식본이 71건의 가짜 실패로 찍혔다.
- 생성기가 `Array.from()` 으로 다시 뽑기 전까지 측정 불가 필드로 빼고 코드에 적는다. 뺀 것은 「실패 분류」처럼 센다.
- 정답지를 뽑을 때 기본 점검은 JSON 을 못 건너오는 `Set` / `Map` / 함수 / `undefined` / `NaN` / `Infinity` 를 먼저 훑는 것이다.

## 암묵 상태

### 요약

- 입력에 안 적힌 암묵 상태를 같이 옮긴다.
- 정답지 입력에는 원본이 로드 때 채우는 기본값이 없다.

### 설계

- 비어 보이는 보유 목록에도 기본 지급분이 들어간다. `if(!owned.default) owned.default = 1` 류가 `boot()` 근처에 있다. 빠지면 보유 보너스 계열 벡터가 전멸한다.
- 기본은 상태 주입 뒤 로드 완료 이벤트를 한 번 더 쏴 이식본의 기본값 채우기를 다시 태우는 것이다. 이유: 규칙을 하네스에 베끼면 하네스와 이식본이 따로 놀고, 재발사하면 그 규칙도 같이 검증된다.

## 하네스 안전

### 요약

- 하네스는 사용자 세이브를 건드릴 수 없어야 한다.
- 조심하는 대신 경로를 없앤다.

### 규칙

- #강제 [원칙 R21](원칙.md#R21) 하네스에는 세이브에 닿는 경로가 없다.

### 설계

- 상태 주입의 기본 형태는 파일을 읽지도 쓰지도 않는 전용 API 다. 예: `SaveManager.InjectVolatile` 이 저장 가능 플래그(`SaveReady`)를 꺼 이후 저장을 무효화한다. 이름은 프로젝트가 정한다.
- 세이브를 만지는 하네스의 기본은 `GameInitialize` 가 세운 데이터·매니저를 쓰고 재생 중에만 도는 것이다 (Play → 인트로에서 게임 시작 → 로딩 완료 뒤 · 에디터 다리 `PLAYMODE=1 Tools/unity-batch.sh`). 이유: 중복 기동 경로(`DataManager.InitializeFromJson` 직접 호출·`GameManager` 자체 생성)가 생기면 아래 영구 null 같은 상태 꼬임이 난다. 세이브와 무관한 헤드리스 데이터 검증이면 DataFramework 「DataManager」의 `InitializeFromJson` 이 낫다.
- 에디트 모드에서 `GameManager.Instance` 를 억지로 만들면 남은 `MonoSingleton._isDestroyed` 에 걸려 영구 null 이 된다. 위 방식이면 사라진다.
- 재생 중 가드는 상태를 만지는 함수에 거는 것이 기본이다 (예: `GoldenHarness.RequirePlayMode`). 이유: 메뉴 가드는 우회된다.
- 파일이 무사한 건 `SaveReady` 차단 덕이다. 메모리 상태는 갈아엎히므로 기본은 채점한 세션을 버리고 Play 를 다시 켜는 것이다.
