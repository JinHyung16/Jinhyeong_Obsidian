# 클라 파트

방향 노트다. 기본값과 이유를 준다.

## 역할

### 요약

- 담당은 시뮬 루프 · 계산 이식 · 배선 · 레이어 규칙 · 수치 정밀도 · 데이터 접근이다.
- 지식 담당자다. 이관에 직접 참여하지 않고, [Transfer_Programmer](Transfer_Programmer.md) 가 100% 이관할 정확한 정보를 낸다.
- 원본은 행동할 때마다 계산 결과를 실어 보낸다. 그 배선이 빠지면 계수만 상수로 남는다.
- 상위는 [PD](PD.md) 다.
- 판단 대상이 아닌 것은 [원칙](원칙.md) 에만 있다.

### 규칙

- #강제 [원칙 R17](원칙.md#R17) 이 역할은 Unity 코드·프리팹을 만들거나 고치지 않는다.
- 이 역할로 들어갈 때 역할 선언을 출력한다 (PD 「역할 기동 규약」).
- 이전 역할의 결론은 md 에 적힌 것으로 잇는다.

### 설계

- 기본은 HTML5 를 실제로 돌려 보며 파악하는 것이다. 이유: 정적 읽기로는 순서·타이밍·게이트 조건이 안 잡힌다.
- 이전 역할의 결론을 기억으로 이으면 앞 역할의 판단이 확인 없이 섞인다.

```
[역할 전환] 지금부터 나는 Client(지식 담당)다.
  할 수 있는 것 : 원본 읽기·실행 · 01_게임플로우.md / 99_원본지도.md 작성
  하지 않는 것  : Unity 코드·프리팹 수정 (그건 Transfer_Programmer 가 한다)
```

## 레이어 규칙

### 요약

- 기본 호출 방향이 정해져 있다.
- 하위 UI 는 Manager 를 직접 보지 않는다.
- 어셈블리를 나누면 컴파일러가 위반을 막아 준다.

### 설계

```
Manager (순수 로직)  <->  Management (화면 조종)      서로 호출 가능
        ^ 직접 호출 없음          ^ 직접 호출 없음
Window / Panel / Component --> Helper (정적, 읽기 전용) 만
```

- 기본은 하위 UI 가 Manager 를 직접 보지 않는 것이다. 데이터는 Helper 경유, 올릴 건 `event`. 이유: Helper 가 읽기 전용이라 UI 가 로직을 못 바꾼다.
- 패널은 자기 구획만 바꾸고 남는 높이는 부모 레이아웃이 나누는 것이 기본이다 (원본의 flex). 이유: 형제 패널의 `RectTransform` 을 고치면 원본 flex 가 하던 분배가 패널마다 흩어진다.
- 월드 오브젝트 이름은 UI 어휘(`Window`/`Popup`/`Panel`/`View`) 대신 `~Visual` 접미가 기본이다. 이유: 이름만으로 UI 와 월드가 갈린다.
- 어셈블리 분리를 권장한다. 이유: 순수 계산 어셈블리가 `UnityEngine` 을 참조하지 않으면 `Mathf`(float) 와 `Random` 직접 호출을 컴파일러가 막는다.

## 스탯 배선

### 요약

- 계산 결과가 유니티 호출부까지 안 가고 계수만 남는 누락이다.
- 가장 많고 가장 안 보인다.
- UI 로 넘기는 스냅샷 구조체에 안 쓰는 필드가 있으면 계약이 틀린 것이다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 원본 계산 결과가 들어가는 자리는 전부 유니티 호출부까지 간다. 계수만 남은 것은 다른 게임이다.

### 설계

예시다. 필드명과 수치는 프로젝트마다 다르다.

```js
// 원본
dmg: (cs.gunDmg || cs.dmgEff)                    // 1944.45
dmg: cs.dmgEff * (cs.sideDmgMult || 0.6)         // 31.07
dmg: (cs.laserDps || cs.dmgEff*2) * dt           // 103.58/s
```
```csharp
// 유니티 (틀림) — 기준값이 빠지고 배수만 남았다
AddShot(..., ShotColor);            // damage 기본값 1f  (1/1944)
Damage(target, 2f * dt);            // x2 만 남음        (1/52)
```

- 증상: 적 HP 는 배수(×361)를 먹는데 피해가 1이라 적이 쌓인다. 엘리트가 살아 적 탄막이 생겨 다른 그림이 된다.
- 발생 지점은 Management 가 Panel 에 주입하는 스냅샷 구조체에서 필드가 빠질 때다. 새 기능을 붙일 때 여기부터 보는 것이 빠르다.
- 점검 기본 방법: 원본에서 계산 결과(`cs.` / `s.`)가 들어가는 자리를 전수 나열하고 유니티 호출부에 도달하는지 짝짓는다. 남은 리터럴 상수가 원인이다.
- 기본 가정은 UI 로 넘기는 `XxxEntry` 의 모든 필드가 화면 어딘가에 닿는다는 것이다. 표시 쪽이 안 읽는 필드는 누락 신호로 본다.
- 사례: 선택 카드 엔트리의 `Effects`·`FusionDescription` 이 선언만 되고 안 채워진 채 몇 달 남았다.

## 상한

### 요약

- 원본에 없는 상한을 넣으면 원본 밀도가 깎인다.
- 성능 걱정으로 넣은 캡이 전형이다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 상한은 원본에 있는 것만 옮긴다. 원본 밀도가 기준이다.

### 설계

예시다. 값은 원본에서 다시 잰다.

| 대상 | 원본 | 잘못 넣은 값 | 결과 |
|---|---|---|---|
| 발사체 | 상한 없음 (정상 상태 ~110) | `MaxShots = 40` | 40발에서 발사가 멎는다 |
| 폭발 파편 | 상한 없음 (실측 161) | `MaxParts = 90` | 격파가 겹치면 폭발이 안 터진다 |
| 적 | `> 60` 이면 안 낳는다 | 60 | 맞다 |

뷰 폭주 방어가 실제로 필요하면 기본은 정상 상태의 2배 이상 여유값으로 두고 주석에 실측치를 남기는 것이다. 이유: 정상 플레이에서 캡이 닿지 않아 원본 밀도가 유지된다.

## 거동 이식

### 요약

- 배치는 맞는데 안 움직이는 누락이다.
- 원본 함수 인자에 `t` 나 `dt` 가 있으면 움직이는 것이다.
- 유도체를 한 줄 Lerp 로 뭉개면 비행 모양이 달라진다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) `t`/`dt` 를 받는 거동, 유도 유무, 유도 세부(선회·가속·개체별 난수)는 원본대로다. 「비슷한 유도」는 다른 거동이다.

### 설계

| 대상 | 원본 | 빠진 것 |
|---|---|---|
| 발사체 | 발사 때 잡은 `s.target` 으로 매 프레임 선회 (`clamp(9*dt,0,1)`) | 유도 전체. 직진해서 빗나갔다 |
| 호위 드론 | 0.5초마다 최근접 적에게 발사 | 사격 코드 자체. 궤도만 돌았다 |
| 배경 장식 프롭 | 대부분 `t` 로 애니메이션 | 연출 전체. 정적 PNG 였다 |

주의: 일부러 유도가 없는 것도 있다. 보조 무기는 `target:null` 이라 직진, 전용 대형 무기는 별도 리스트라 유도 없음. 전부 유도로 통일하면 오답이다.

**「비슷한 유도」로 뭉개기 쉬운 6가지**. 유도체를 `Vector2.Lerp(v, desired, dt*k)` 한 줄로 옮기면 비행 모양이 달라진다.

| # | 원본 | 뭉갠 구현 | 보이는 차이 |
|---|---|---|---|
| 1 | 발사 때 잡은 `m.tgt` 유지, 죽었을 때만 재획득 | 매 프레임 최근접 재조준 | 궤적이 꺾이고 여러 발이 한 적으로 몰린다 |
| 2 | 각도 선회 (`na = cur + d2`) | 속도 벡터 Lerp | 속력도 줄어 곡선이 무뎌진다 |
| 3 | 선회 예산 `turned ≤ π`, 다 쓰면 직진 | 없음 | 빗나가면 영원히 빙빙 돈다 |
| 4 | 뒤쪽(`\|d2\| ≥ 2.7`) 표적은 선회 안 함 | 없음 | 뒤로 급선회 U턴 |
| 5 | 가속 `min(300, sp + 360·dt)` (직진 시 260) | 속력 고정 | 원본은 150에서 300까지 붙는다 |
| 6 | 개체별 선회율 `5·(0.8+rand·0.4)` · 조준 오프셋 `±20` · 흔들림 | 전부 고정값 | 미사일이 한 덩어리로 겹친다 |

- 꼬리(trail): 원본은 최근 8점 폴리라인이다. 기본은 선분 뷰도 풀에서 빌리고 본체가 사라질 때 같이 반납하는 것이다.
- 수명 종료: 원본 미사일은 수명이 다해도 그 자리에서 폭발하고 splash 를 준다. 조용히 사라지면 광역 피해가 빠진다.

## 메인 루프 게이트

### 요약

- 함수 단위로 이식하면 루프의 `if` 조건이 사라진다.
- 게이트 조건은 한 줄씩 옮긴다.
- 모달을 띄운 채 프레임을 흘려 고정 여부로 검증한다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 정지 게이트(모달 · 일시정지 · 결과 · 컷신)는 조건 한 줄 단위로 전부 원본대로다. 가변 dt 상한도 원본 값이다.

### 설계

```js
// 원본.html — 메인 루프 본체 (인용할 때 라인 번호를 grep 으로 재확정한다)
if(screen==='combat'){
  drawScene(t,dt);                                   // 그리기는 항상 돈다
  if(!(AUG&&AUG.open) && !(G&&G.paused)){            // 시뮬 게이트
    updateCombat(dt);
    …
  }
}
```

- 사례: 「선택 모달이 뜨면 시뮬 정지」 한 줄을 빠뜨려 카드를 고르는 사이 격침당했다.
- 기본 방법은 원본 루프 본문을 줄 단위 표로 만들고 각 조건을 유니티 쪽과 짝짓는 것이다. 이유: 함수 단위로 보면 루프의 조건이 안 보인다.
- 그리기 계속·시뮬만 정지인지, 둘 다 정지인지 구분한다. 대개 그리기는 계속이다.
- 표에 정지 게이트(모달 · 일시정지 · 결과 · 컷신)를 전부 나열해 두면 빠진 줄이 드러난다.
- 가변 dt 클램프 상한은 원본 값을 쓴다 (예: 0.033, 원본 실측값).
- 검증 기본 방법: 모달을 띄운 채 수백 프레임을 흘리고 `시각·개체 수·HP` 가 고정인지 본다.

```
778프레임 경과 · ctx.Time 3.952 고정 · 적 83기 고정 · HP 403.0 고정   통과
```

이 상태가 가장 안정적인 캡처·측정 프레임이다 (공통절차 「교전 중 프레임을 얼려서 본다」).

## 순회 방향

### 요약

- 원본의 배열 순회 방향은 사양이다.
- 배열을 훑으며 제자리에서 고치는 로직(낙하·전파·연쇄·정렬·확산)은 순회 방향이 결과를 바꾼다.
- 이유: 방금 고친 칸을 같은 순회에서 다시 본다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 제자리 수정 루프는 순회 방향 · 인덱스 산술 · 중간 상태까지 같은 절차로 옮긴다. 모아서 처리하면 결과가 같아도 절차가 다르다.

### 설계

| 원본이 훑는 방향 | 한 번의 호출에서 일어나는 일 |
|---|---|
| 오름차순, 「다음 칸이 비었으면 옮긴다」 | 하나가 빈 자리 끝까지 미끄러지고 중간은 비어 남는다 |
| 내림차순, 같은 일 | 각각 한 칸씩만 움직인다 |
| 한 번에 모아 압축 | 줄 전체가 한 번에 정렬된다 |

- 몇 프레임 뒤 화면은 비슷해서 차이는 중간 프레임과 연쇄 타이밍에서만 드러난다.
- 사례: 위에서 아래로 훑어 내리는 원본에서 세로 빈 칸 3개에 말 하나가 세 칸을 미끄러지고 중간 두 칸이 비었다. 「열 압축」이면 다른 보드였다.
- 방향을 고정하는 정답지 기본은 빈 자리를 연속으로 만든 입력과 떨어뜨려 만든 입력, 두 벡터다. 이유: 세 방향이 서로 다른 값을 내므로 방향이 고정된다.

```bash
# 원본에서 제자리 수정 루프를 찾는다 — 방향을 눈으로 확인한다
grep -nE "for *\(.*(i\+\+|i--|--i|\+\+i)" 원본.js
```

## 판정 순서

### 요약

- 먼저 처리한 것이 뒤 판정을 막는다.
- 한 루프에서 판정 여러 개가 즉시 자료를 고치면 앞 판정이 지운 자리를 뒤 판정이 못 본다.
- 순서가 곧 결과다. 전형은 이미 처리된 자리를 거르는 가드다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 판정 순서 · 즉시 수정 · 앞 판정이 남긴 가드(빈 자리·처리 완료 표시)는 원본 호출 순서 그대로다. 묶음 판정이나 「전부 찾고 한꺼번에 제거」는 원본의 이상 거동(4점만 남음)을 지운다.

### 설계

```js
// 예시: 첫 칸이 이미 비었으면 건너뛴다 — 앞 판정이 비운 자리다
const isBlank = cells[i] === "";
if (group.every(x => cells[x] === decided && !isBlank)) { … 제거 … }
```

| 겹치는 입력 | 순서를 지키면 | 「잘 만든」 판정이면 |
|---|---|---|
| 큰 패턴과 작은 패턴이 한 칸 공유 | 큰 쪽만 점수 | 둘 다 점수 |
| 판정 길이보다 긴 연속 | 앞부분만 먹고 꼬리가 남는다 | 전부 먹는다 |

- 사례: 가로 4연속·세로 3연속 공유 판에서 4점만 나고 세로 두 칸이 남았다(교과서 판정이면 7점). 5연속도 4점만 났다.
- 검증 입력은 겹치는 입력 벡터가 기본이다. 이유: 안 겹치는 입력으로는 안 잡힌다.

## 조기 반환 가드

### 요약

- 조기 반환 가드는 뒤따르는 로직보다 넓어야 한다.
- 빠른 탈출이 판정보다 좁으면 일부 입력만 조용히 건너뛴다.
- 그 결과를 데이터 탓으로 넘기게 된다.

### 설계

```csharp
// 틀림 — 정규식은 "/ Lv" 처럼 공백이 낀 것도 잡는데 가드가 "/Lv" 만 본다
if (text.IndexOf("/Lv") < 0) return text;
return LevelScaleRegex.Replace(text, …);
```

- 기본은 가드를 판정식의 가장 느슨한 부분집합으로 잡는 것이다. 위 예는 `"Lv"` 다. 이유: 가드가 판정보다 넓으면 걸러도 잃는 입력이 없다.
- 가드에 걸리는 케이스와 안 걸리는 케이스를 하나씩 실측해 폭을 확인한다.

## 충돌 반지름

### 요약

- 충돌과 크기를 상수로 박지 않는다.
- 원본은 양쪽 반지름을 다 본다.
- 탄 반지름은 종류마다 다르다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 충돌 반지름은 원본이 개체에 실어 보내는 값이다.

### 설계

```js
if(dx*dx+dy*dy < (e.r + s.r + 2)**2)   // 원본 — 양쪽 반지름을 다 본다
```
```csharp
HitTest(s.Position, 10f);              // 틀림 — 탄 반지름을 안 본다
```

- 기본 구현은 원본 반지름(`shots[].r`)을 그대로 통과시키고 창 배율을 곱하는 것이다. 상대편 반지름은 이미 스케일된 값이다.
- 탄 반지름은 종류(주무기 · 보조 · 요격 · 전용 · 드론)마다 다르다.
- 사례: 눈대중 상수로 특수탄이 2~3배 작았다.

## 회전

### 요약

- 회전은 여러 번 겹쳐 걸린다.
- 향하는 방향은 그 draw 트리의 회전 합이다.
- 스프라이트가 향하는 축은 프로젝트에서 하나로 통일한다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 향하는 방향은 그 draw 트리의 회전 합이다.

### 설계

```js
drawEnemy:       ctx.rotate(e.angle)      // e.angle = π/2 (스폰 시)
drawEnemySprite: ctx.rotate(Math.PI/2)    // 스프라이트 '위' -> +x 정렬
// 합 = π -> 앞머리가 화면 아래(플레이어)를 본다
```

| 대상 | 원본 회전 | 틀렸을 때 |
|---|---|---|
| 적 | `e.angle + π/2` = 180° | 등을 보이고 내려온다 |
| 호위 드론 | `atan2(ownerY−dr.y, ownerX−dr.x) + π` (주체 바깥) | 전부 오른쪽만 봐 커서 아이콘처럼 보인다 |

- 점검법: 그 draw 트리의 `rotate(` 를 전부 찾아 합산한다.
- 스프라이트가 향하는 축은 프로젝트에서 하나로 통일하는 것이 기본이다. 이유: `+x` 로 구웠으면 회전은 `atan2(vy,vx)` 그대로이고, 한 뷰만 `−90°` 를 붙이면 한쪽이 틀어진다.

## 수치 계층

### 요약

- 계산은 `double` 이 기본이다.
- 확률은 주입식 RNG 가 기본이다.
- 물리 엔진은 섞지 않는 것이 기본이고, 원본이 물리 엔진이면 뒤집힌다 (「물리 엔진」).

### 설계

- 기본은 계산을 `double` 로 하는 것이다. 이유: 원본 JS 숫자는 전부 double 이고, float 상대오차 실측 1.3e-7 (`gunDmg` 1944.4539975 → 1944.45374) 은 정답지 1e-9 판정을 못 넘는다. 원본이 JS 가 아니면 원본의 숫자 체계에 맞춘다.
- 확률은 주입식 RNG 가 기본이다. 이유: 기본 난수를 직접 부르면 재현이 안 되고, 재현 불가 = 채점 불가다.
- 물리 엔진은 섞지 않고 판정을 자체 코드로 하는 것이 기본이다. 원본이 물리 엔진 위에서 돌면 반대가 낫다 (「물리 엔진」).

## 물리 엔진

### 요약

- 원본이 물리 엔진을 쓰면 「섞지 않는다」 기본값이 뒤집힌다.
- 섞지 않는 기본값은 원본에 없는 거동이 생기는 것을 막기 위해서다.
- 원본이 물리 엔진(Box2D 계열이 흔하다) 위에서 돌면 엔진을 안 쓰는 쪽이 원본에서 멀어진다.

### 규칙

- #강제 [원칙 R5](원칙.md#R5) 정답지가 통과하도록 반발·마찰을 고르면 없는 실측을 지어내는 것이다.

### 설계

물리 상수·스텝 순서를 캐는 법은 [공통절차 - 원본에서 값 캐기](공통절차%20-%20원본에서%20값%20캐기.md)이 정본이다.

| 먼저 확인한다 | 어떻게 |
|---|---|
| 원본이 물리 엔진을 쓰나 | 런타임 인스턴스의 거동/컴포넌트 목록을 뒤진다 (`공통절차`·PD 「런타임을 먼저 찔러라」). 쓰면 반발·마찰·밀도·감쇠·충돌 도형·월드 중력을 재는 대신 읽는다 |
| 엔진 계열이 같은가 | 같으면 파라미터가 1:1 로 매핑된다 |

같은 계열이면 실측 파라미터로 엔진을 쓰는 것이 재구현보다 가깝다. 이 길을 고르면 셋을 챙긴다.

1. 엔진 스케일을 원본과 맞춘다. 내부 상수(접촉 슬롭 · 반발이 죽는 속도 임계)가 절대 크기에 의존하므로, 원본의 「1 미터 = N 픽셀」을 따라야 같은 지점에서 안 튄다. 어긋나면 다중 충돌 뒤 안정화가 갈리고 단발 궤적 검사로는 안 잡힌다.
2. 채점을 실제 경로에서 한다. 헤드리스 계산으로 채점할 수 없으니 재생 모드 검사로 옮긴다 (`공통절차` · 에디터 다리 `PLAYMODE=1 Tools/unity-batch.sh`).
3. 파라미터는 원본에서 읽은 값을 쓴다.

주의: 접선(마찰) 거동은 계수 하나로 재현되지 않는다. 회전 관성이 붙으면 접선 속도비가 흩어지고 각속도 부호까지 바뀐다. 원본이 회전 강체면 「반사 벡터로 튕기는 점」 모델로는 원리적으로 못 낸다.

## 밸런싱 채록

### 요약

- 레벨이 있는 게임의 가장 흔한 미완성은 1레벨만 맞추는 것이다.
- 「원본보다 쉽다/어렵다」는 정적 캡처에 안 잡힌다.
- 전수는 비용이 폭발하고 1개로는 규칙이 안 나오므로 범위를 확정표(11-b)로 못 박는다.
- 채록 밖 레벨로 검증하지 않으면 규칙이 아니라 암기다.

### 규칙

- #강제 [원칙 R13](원칙.md#R13) 채록 범위는 확정표 11-b 의 사람 답이다. 「대표 몇 개」로 줄이는 것은 에이전트가 고를 일이 아니다.

### 설계

| 단계 | 무엇을 |
|---|---|
| ① 묻는다 | 「앞 몇 개 레벨까지 원본과 똑같이 맞출까요?」. PD 가 착수 질문에서 받는다 |
| ② 채록 | 그 범위를 전부 원본에서 실측한다 |
| ③ 규칙 도출 | 채록값에서 공식·표를 뽑는다 |
| ④ 채록 밖 검증 | 도출에 안 쓴 레벨로 공식을 검산한다 (홀드아웃) |

**④가 없으면 규칙이 아니라 암기다.** 채록 N개에 맞는 공식은 언제나 만들 수 있다. 채록에 안 쓴 레벨에서 맞아야 규칙이다. 기본은 채록 개수를 정할 때 검증용 몫을 떼어 두는 것이다.

주의: 홀드아웃을 통과해도 등급은 ②(실측)까지다. 「고정 간격 + 가중치 뽑기」와 「위협 예산」이 같은 스폰 곡선을 냈다. ①로 올리는 것은 소스 직독 · 함수 후킹 · 죽일 조건을 건 가설 시험뿐이다 (PD 「근거 등급」 · 함정: [상수가 맞아 규칙도 맞다고 봄](함정%20-%20측정%20추론.md#상수가%20맞아%20규칙도%20맞다고%20봄)).

**자유 피팅은 「데이터마다 다르다」로 오독시킨다.** 파라미터를 다 풀고 레벨마다 맞추면 값이 레벨마다 달라져 레벨표에 N벌을 적는 틀린 결론이 난다.
사례: 발사점 보정 진폭이 레벨마다 달랐는데, 절편을 아는 값으로 고정하자 전 레벨이 한 값(잔차 0.07 이내)이었다. 원인은 모델 범위 밖 표본 한 점이었다.
기본은 자유도를 먼저 줄이고 맞추는 것이다. 실측으로 아는 항은 고정한다. 이유: 풀어 둔 항은 표본 한 점의 잡음까지 흡수한다.

## 난이도 측정

### 요약

- 「난이도가 같다」는 배치가 아니라 성공 범위로 잰다.
- 재는 값은 그 레벨을 깨는 입력의 범위다.

### 설계

| 약한 축 | 기본 축 |
|---|---|
| 배치·좌표 일치율 | 입력을 격자로 훑어 성공/실패를 원본과 격자점마다 대조 |
| 「깨진다/안 깨진다」 | 깨지는 입력 구간의 시작과 끝 |
| 한 번 깨봤다 | 격자점마다 n 회, 원본이 갈리는지도 본다 |

주의: 비교 축은 갈린 격자점 수가 기본이다. 성공 범위를 비율로 비교하면 우리 구간 개수가 분모를 바꾼다.

## 비결정 구간

### 요약

- 원본이 스스로도 재현하지 못하는 구간이 있다.
- 「같은 입력이면 원본이 같은 답을 낸다」는 전제가 깨진다.
- 웹 원본의 들쭉날쭉한 프레임 간격이 스침·저속 정착·다중 접촉에서 증폭된다.
- 이것을 면죄부로 쓰면 그 순간 규칙이 무너진다.

### 규칙

- #강제 [원칙 R9](원칙.md#R9) 원본이 갈린다는 확증이 먼저이고, 제외 건수는 항상 따로 보고한다.
- #강제 [원칙 R5](원칙.md#R5) 제외 범위를 넓히는 것은 점수를 근거로 값을 고르는 것이다 ([함정 색인](함정%20색인.md) 참조).

### 설계

사례: 발사 위치가 0.001 px 이내로 같은 두 발이 다섯 번째 모서리 접촉에서 33 ms 어긋나 한쪽만 골인했다.

| 무엇 | 어떻게 |
|---|---|
| 판정 | 같은 입력을 n 회(≥3) 돌려 갈리는지 본다. 2회로는 부족하다 |
| 분류 | 갈리는 벡터는 지우지 않고 「비결정」으로 분류한다 |
| 채점 | 불일치로 세지 않고 「비결정 N건 제외」를 리포트에 찍는다 |
| 정답지 고르기 | 접촉이 적고 짧게 결판나는 샷으로 고른다 |

- 안 맞는 자리를 보고 비결정이라고 짐작하기 쉽다. 먼저 원본을 n 회 돌려 잰다.
- 갈리는 빈도를 잰다. 원본 10회 중 9회 성공인데 우리가 0회면 우리 결함이다.

## 정답지

### 요약

- 정답지는 원본을 N가지 상태로 돌려 계산 결과 전 필드를 덤프한 것이다.
- 수치 환원을 증명하는 유일한 수단이다.
- 기본 수단은 정답지 JSON N벡터이고, 없으면 공통절차 「A/B 측정」의 A/B 개체 수 판정으로 대체한다.
- 만드는 주체 · 순서 · 이름 대응 · 실패 분류 · 하네스 안전은 [정답지](Client%20-%20정답지.md) 에 있다.

## 미리보기 계산

### 요약

- 미리보기 계산은 실제로 적용했다가 되돌린다. 원본이 그렇게 한다.
- 예: 「이 강화를 받으면 뭐가 바뀌나」 표는 실제로 획득시켜 스탯을 두 번 계산한다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 미리보기로 적용한 상태는 조기 `return` 을 포함한 모든 경로에서 원복된다. 원복이 빠지면 실제 스탯이 오염된다.

### 설계

```js
const A=computeStats();
AUG.act.add(k); AUG.stk[k]=stk+1;     // 받은 상태로 만든다
const B=computeStats();
AUG.stk[k]=stk; if(!wasAct) AUG.act.delete(k);   // 원복
```

- 캐시가 있으면 기본은 두 계산 사이와 끝난 뒤에 무효화하는 것이다. 이유: 무효화가 빠지면 B 가 A 의 캐시를 읽고, 끝난 뒤에는 받은 상태의 값이 남는다.

## 데이터 접근

### 요약

- 자동 생성 파일은 생성 입력에서 고친다.
- 테이블을 추가했으면 조회 성공까지 실측한다.

### 규칙

- #강제 [원칙 R22](원칙.md#R22) 자동 생성 파일은 원본(엑셀)이나 제너레이터에서 고친다.
- #강제 [원칙 R7](원칙.md#R7) 테이블을 추가했으면 조회 성공을 실측한다 (「스탯 배선」).

### 설계

- 콘크리트 컨테이너를 만들거나 지우면 `ContainerRegister` 와 `GameRoot` 프로퍼티를 손으로 맞춘다 (DataFramework 「폴더 · 파이프라인」).
- `Id` 가 아닌 컬럼 조회는 컨테이너가 자료구조를 만드는 것이 기본이다. 로드마다 새로 만들고 행마다 채우는 훅이다. 이유: 호출부가 로컬 캐시를 따로 들면 재로드 때 낡은 값이 남는다.

## 완료 체크리스트

### 요약

- 클라 파트를 닫기 전에 아래를 확인한다.
- 못 잰 것은 지우지 말고 사유와 함께 남긴다.

### 규칙

- [ ] 미측정 항목 0. 못 잰 것은 `미측정(사유)` 로 적고 재측정 대기에 등록했다 ([원칙 R6](원칙.md#R6))
- [ ] 내 권한 밖 파일을 건드리지 않았다 (PD 「역할 기동 규약」 권한표 · [원칙 R17](원칙.md#R17))

### 설계

1. 계산 결과가 들어가는 자리를 전수 나열했고 전부 도달하나 (「스탯 배선」)
2. UI 로 넘기는 구조체에 안 쓰이는 필드가 없나 (「스탯 배선」)
3. 원본에 없는 상한을 넣지 않았나 (「상한」)
4. `t`/`dt` 를 받는 원본 함수가 실제로 움직이나 (「거동 이식」)
5. 메인 루프 게이트 조건(모달·일시정지·결과·컷신)을 전부 옮겼나 (「메인 루프 게이트」)
6. 조기 반환 가드가 판정식보다 넓은가 (「조기 반환 가드」)
7. 충돌·표기 크기가 원본 변수인가 (「충돌 반지름」)
8. `rotate(` 를 전부 합산해 방향을 맞췄나 (「회전」)
9. 계산이 double 이고 RNG 가 주입식인가. 다르게 골랐으면 이유를 확정표에 적었나 (「수치 계층」)
10. 미리보기 계산의 원복이 모든 경로에서 도나 (「미리보기 계산」)
11. 새 테이블의 컨테이너 조회가 실제로 성공하나 (「데이터 접근」)
