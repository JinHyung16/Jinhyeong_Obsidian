# 연출 파트

방향 노트다. 기본값과 이유를 준다.

## 역할

### 요약

- 담당은 렌더 패리티 · 합성 모드 · 글로우 · 절차 이펙트 베이크 · 애니메이션 · 색공간이다.
- 지식 담당자다. 이관에 직접 참여하지 않고, [Transfer_Artist](Transfer_Artist.md) 가 퀄리티까지 100% 이관하도록 정확한 정보를 준다.
- 상위는 [PD](PD.md) 다.
- 판단 대상이 아닌 것은 [원칙](원칙.md) 에만 있다.

### 규칙

- #강제 [원칙 R17](원칙.md#R17) 이 역할은 프리팹·아트를 만들지 않는다.
- 이 역할로 들어갈 때 역할 선언을 출력한다 (PD 「역할 기동 규약」).
- 이전 역할의 결론은 md 에 적힌 것을 기준으로 받는다.

### 설계

- 기본 방향은 원본 캔버스 API 호출을 줄 단위로 읽어 그리기 값(선 굵기 · blur · 알파 · 합성 · 레이어 수)을 빠짐없이 옮기는 것이다.
- 배율은 눈대중 대신 원본 수치에서 가져온다. 이유: 눈대중 배율은 원본과 대조할 숫자가 없다.
- 코드 구조는 호출 순서를 흉내 내지 않고 Unity 식(베이크 · 렌더러 계층)으로 짠다 ([원칙 R2](원칙.md#R2)).
- 정적 캡처에는 `animation` · `:hover` 가 안 찍히므로 원본을 돌려 보며 파악한다.

```
[역할 전환] 지금부터 나는 FX(지식 담당)다.
  할 수 있는 것 : 원본 읽기·실행 · 05_연출.md / 06_리소스.md 작성
  하지 않는 것  : 프리팹·아트 생성 (그건 Transfer_Artist 가 한다)
```

## 그리기 파라미터 전수표

### 요약

- 착수하면 가장 먼저 하는 일이다.
- 기본 순서는 코드를 고치기 전에 원본의 모든 그리기 파라미터를 표로 뽑는 것이다.
- 이유: 표의 빈 칸이 남은 일이다.

### 설계

```bash
grep -n "globalCompositeOperation" 원본.html    # 합성 모드 — 어느 캔버스인지까지 구분
grep -n "lineWidth" 원본.html                   # 선 굵기 (절대 픽셀이다)
grep -n "shadowBlur\|shadowColor" 원본.html      # 글로우
grep -n "globalAlpha" 원본.html                 # 알파
grep -n "createRadialGradient\|createLinearGradient" 원본.html
```

| 대상 | 원본 값 | 원본 라인 | 우리 값 | 상태 |
|---|---|---|---|---|
| 예: 노바 링 | `lineWidth 4.5` · `shadowBlur 14` | 5231 (grep 으로 재확정) | 4.5 + 소프트링 | 통과 |

## 합성 모드

### 요약

- 프로젝트 기본값이 원본과 반대일 수 있다.
- 원본 합성 모드를 그 컨텍스트 기준으로 확정한다.
- 캔버스는 프레임 시작에 정규화하는 경우가 많다. 파일의 `'lighter'` 가 다른 캔버스(컷신·인트로 `ctx`) 것일 수 있다.

### 설계

```js
// 원본.html — 전투 그리기 진입 첫 줄 (라인은 grep 으로 재확정)
bx.globalCompositeOperation='source-over';   // 이후 끝까지 안 바꾼다
```

사례: 도형 컴포넌트의 `_additive = true` 기본값 때문에 탄환·링·보호막이 전부 가산으로 하얗게 탔다.

- 원본에 없는 렌더 기능은 기본값도 꺼 두는 것이 기본이다. 안 쓰기로 했으면 코드에서 지우는 쪽이 낫다. 이유: 스위치를 남기면 누군가 켠다.
- 프리팹에 남은 옛 머티리얼은 런타임에서 되돌리는 안전장치를 둔다.
- 기본 확인은 활성 렌더러를 전수 세어 가산 0 을 실측하는 것이다. 이유: 기본값 추정으로는 가산이 없음을 보일 수 없다. 예: `활성 SpriteRenderer 70개 → 전부 Sprite-Lit-Default (가산 0)`.
- 발광은 가산이 아니라 `shadowBlur` 로 내는 것이 기본이고, 아트에 이미 구워져 있다 (「글로우」). 원본이 가산이면 가산을 쓴다.

## 글로우

### 요약

- `shadowBlur` 는 수식이 있다. 도형 알파를 σ = b/2 가우시안으로 흐려 도형 아래에 깐다.
- 작은 도형은 봉우리 알파가 크게 내려간다. 상수 알파로 깔면 두 배 밝아진다.
- 눈대중 배율 대신 수치 적분해서 굽는다.
- 발광이 과해 보이면 글로우를 줄이기 전에 레이어 수부터 센다.
- 수식 · 베이크 계열 · 인자 단위 · 레이어 세는 법은 [글로우](Fx%20-%20글로우.md) 에 있다.

## 선 굵기

### 요약

- 원본 링·테두리는 고정 픽셀 스트로크다.
- 반지름 비례로 구우면 큰 반지름에서만 틀어진다.
- 사례: 「굵기 = 지름의 16%」로 구운 링이 반지름 200 오라에서 64px(원본 1.5px)로 나왔다.

### 설계

기본은 「굵기 / 반지름」 비율 계열로 굽고 런타임이 로그 거리로 최근접을 고르는 것이다. 이유: 선형 거리는 등비 계열에서 큰 쪽에 쏠린다.

```
ratios = { 0.006, 0.012, 0.024, 0.048, 0.096, 0.192, 0.384 }   // 등비 — 계열 값은 프로젝트가 정한다
고를 때: wanted = lineWidth / radius,  거리 = |log(ratio) − log(wanted)|
```

- 얇은 띠 텍스처는 512 이상으로 굽는 것이 기본이다. 이유: 128px 를 400px로 늘리면 깨져 보인다.
- `shadowBlur` 가 붙은 스트로크는 두 겹이다. 넓은 소프트 링을 아래, 또렷한 선을 위에 둔다(원본은 `stroke()` 한 번).

## 절차 이펙트 베이크

### 요약

- 절차 이펙트는 재구현하지 말고 원본에서 베이크한다.
- 사례: 원본 3프레임 실측에서 손으로 다시 그리면 최대 Δ183, 원본 렌더 결과를 추출해 구우면 Δ0 이었다.

### 규칙

- #강제 [원칙 R11](원칙.md#R11) 원본 렌더 결과 · 폰트 · SVG 를 그대로 가져오는 것은 원본을 쓸 권리가 있는 게임(허용 라이선스 원본 등)에서만 한다. 상용 원본이면 그리기 파라미터와 규격만 재서 다시 굽는다. 픽셀을 어디까지 맞출지는 그 게임 확정표를 따른다.

### 설계

- 굽는 도구(에디터 시점)에서는 원본 드로잉 코드를 줄 단위로, 캔버스 API를 그대로 받는 2D 페인터로 옮겨 텍스처를 굽는 것이 기본이다 (`FillRoundRect` · `StrokePolyline` · `Paint.LinearY/Radial` · `Halo`(=`shadowBlur`) 등). 런타임은 구운 결과를 쓰고 캔버스 호출 구조를 두지 않는다 ([원칙 R2](원칙.md#R2)).
- 기본은 색까지 굽는 것이다. 색이 데이터로 갈리는 것만 흰색+알파로 굽고 런타임 tint 를 준다.
- 원본을 쓸 권리가 있는 게임이면, 원본이 쓰는 폰트·SVG도 원본을 렌더해 가져오는 쪽이 손으로 다시 그리는 것보다 기본이다. 예: 허용 라이선스 원본에서 아이콘 92종을 원본 SVG로 렌더해 아틀라스로 뽑았다. 상용 원본이면 같은 절차로 규격만 잰다.
- 굽는 쪽 상수와 고르는 쪽 상수는 두 파일에 나뉜다. 서로 주석으로 가리키고 같이 바꾼다. 어긋나면 크기가 조용히 틀어진다.

## 애니메이션

### 요약

- 정적 PNG로는 연출이 사라진다.
- 원본 함수 인자에 `t` · `dt` 가 있으면 움직이는 것이다.
- 맥동은 대부분 크로스페이드로 끝나고, 회전·이동만 별도 레이어가 필요하다.

### 설계

| 원본 형태 | 옮기는 법 |
|---|---|
| `0.5 + 0.5·sin(t·ω)` 맥동 | 골(pulse=0)·마루(pulse=1) 두 장을 굽고, 마루를 위에 얹어 알파 0→1 을 흔든다(크로스페이드). 주기 = `2π/ω` |
| `rotate(t·ω)` 등속 회전 | 회전 요소만 따로 굽고 회전 컴포넌트 |
| `rotate(sin(t·ω)·A)` 왕복 | 별도 레이어 + 사인 회전 컴포넌트 |
| `(t·k) % m` 스캔선·타일 | 별도 레이어 + 드리프트 컴포넌트 |

- 기본은 범용 트윈 라이브러리 대신 최소 컴포넌트를 하나씩 만드는 것이다.
- UI 버튼의 배율 움직임(펄스·호버·상태)은 [UIFramework](UIFramework.md) 「UI 연출」의 최소 세트를 쓰는 쪽이 낫다. 배율을 곱하는 것이라 크로스페이드가 아니다.
- 방향·속도·순환 폭(이미지 높이)·왕복 여부는 원본 값을 쓴다. 사례: 원본 1.1px/s 배경 드리프트를 `11px/s` 로 넣었다.

## 바라보는 방향

### 요약

- 「어느 쪽을 보나」는 상태다. 매 프레임 다시 재지 않는다.
- 기본은 방향을 시뮬(모델)이 상태로 들고, 뷰는 부호만 받는 것이다.
- 게이트와 0 분기도 같이 옮긴다.

### 설계

```js
// 모양만 본다 — 값·이름은 원본마다 다르다
dx < 0 ? sprite.scale.x = -Math.abs(sprite.scale.x)
       : dx > 0 && (sprite.scale.x = Math.abs(sprite.scale.x))
```

`dx === 0` 분기가 없어 안 움직이면 마지막 방향을 둔다. 흔히 거리 게이트(「거리가 N 을 넘을 때만」) 안에 있다.

| 잘못 옮기면 | 증상 |
|---|---|
| 뷰가 매 프레임 `대상.x > 나.x` 를 다시 잰다 | 붙었을 때 부호가 프레임마다 뒤집혀 떤다 |
| 게이트를 빼먹는다 | 같은 증상. 멈춰 있을 때·겹쳤을 때만 난다 |
| 「0 이면 유지」를 빼먹는다 | 세로로만 갈 때 방향이 초기값으로 돌아간다 |

- 반전 호출부를 전수로 센다. 개체는 다 있으므로 「빠진 개체」 검사에는 안 걸린다.
- 사례: 반전 자리 다섯(주인공·잡몹·보스·동물·동료) 중 둘만 옮겨 주인공이 반대쪽을 봤다 (함정: [개체만 세고 행동은 안 센 분모](함정%20-%20판정%20보고.md#개체만%20세고%20행동은%20안%20센%20분모) · [뷰가 매 프레임 다시 잰 바라보는 방향](함정%20-%20로직%20데이터.md#뷰가%20매%20프레임%20다시%20잰%20바라보는%20방향)).
- 재는 법: 재생에서 배율 x 를 프레임마다 찍어 입력(이동) 부호와 변화 횟수가 같은지 본다. 한 번도 안 바뀌면 반전이 없는 것이다.

## 페이즈 진입 훅

### 요약

- 정지 프리뷰로는 애니메이션 상태를 못 본다.
- 페이즈 강제 진입 훅을 표준으로 둔다.
- 프리뷰 하네스는 한 프레임만 굽기 때문에 여러 페이즈 연출은 첫 프레임만 증명된다.

### 규칙

- #강제 [원칙 R7](원칙.md#R7) 정지 캡처 한 장은 첫 페이즈만 증명한다. 페이즈마다 되읽은 것만 통과로 센다.

### 설계

사례: 10연 뽑기 카드가 안 뒤집혔는데 정지 캡처는 뒤집기 전이 정답이라 몇 턴째 정상으로 보였다.
기본은 연출을 붙일 때 페이즈 진입점을 같이 만드는 것이다.

```csharp
#if UNITY_EDITOR
/// <summary>프리뷰·검수용 — 페이즈를 건너뛰고 그 상태로 바로 앉힌다. 트윈은 끝난 값으로 확정한다</summary>
public void EditorSetPhase(Phase phase) { ... }
#endif
```

1. 모든 페이즈에 이름이 있다(「연출 중」 하나로 뭉뚱그리면 진입점을 못 만든다).
2. 진입 시 트윈을 끝난 값으로 확정한다(중간값이면 캡처가 매번 달라 대조가 안 된다).
3. 프리뷰가 페이즈마다 한 장씩 굽고, 원본도 같은 페이즈로 찍어 짝을 만든다(`capture_*.js` 에 단계별 캡처).

## 색공간

### 요약

- 프로젝트당 한 번 결정하고 그에 맞춰 전부 짠다.
- 캔버스는 감마(sRGB)에서 합성한다. 유니티가 Linear면 `src·a + dst·(1−a)` 를 리니어 값으로 계산해, 반투명이 겹치는 자리의 결과가 달라진다.
- 불투명 단일 레이어는 문제없다.
- 역산은 두 방향이다. 오버레이가 밝은가 어두운가로 갈린다.

### 규칙

- #강제 [원칙 R12](원칙.md#R12) 사람 확정으로 걷은 것을 측정으로 되살리지 않는다.

### 설계

- 「Vertex Color Always In Gamma」 류 옵션과는 무관하다. 그것은 버텍스 컬러 인코딩 문제이고 블렌딩 수식은 그대로다. 예: 이 저장소의 Unity 6000.3 + URP 에는 그 설정이 없다.
- 사례: 알파 합성(남색 + 앰버 α0.6) 캔버스 R 157, Gamma 예측 157.0, Linear 예측 203.6.
- Linear로 확정된 프로젝트에서는 알파를 역산한다. 베이크 스프라이트는 굽는 마지막에 알파만 바꾼다(`a=1` 은 안 변해 실루엣이 보존된다).
- 기본은 역산을 한 헬퍼에서 하는 것이다. 호출부에는 원본 감마값을 그대로 두고 헬퍼가 변환한다. 이유: 원본 숫자가 코드에 남아야 대조할 수 있다.
- 어디가 뜨는지는 픽셀로 특정한다. UI 판은 대개 맞고 반투명이 여러 겹 쌓이는 자리만 뜨므로 거기만 고치는 쪽이 낫다.
- 색·알파는 하드코딩 대신 원본 `:root` 변수에서 가져오는 것이 기본이다.

리니어 합성은 둘 다 감마보다 밝게 끝난다. 밝은 것은 더 밝아지고, 어두운 것은 덜 어두워진다.

| 오버레이 | 리니어가 내는 결과 | 같게 보이려면 |
|---|---|---|
| 밝은 것 (가산 · 발광 · 밝은 색 판 · 밝은 반투명 선) | 감마보다 밝다 | 알파를 내린다. `a^2.2` (CSS .5 → 대략 .22~.3) |
| 어두운 것 (딤 · 그림자 · 어두운 판) | 감마보다 덜 어둡다 | 알파를 올린다. `1 − (1−a)^2.2` |

- 주의: 정확한 값은 배경색에 달렸고 닫힌 해가 없다. 위 식은 감마 2.2 근사다. 정확히 맞춰야 하면 기준 배경 한 색(그 게임이 실제로 덮는 색, 보통 지형 바닥)을 정해 채널별로 정확히 풀고 평균을 쓰는 쪽이 낫다. 아주 밝거나 어두운 배경에서는 몇 단위 어긋난다.
- 예: 지형 `#64779B` 기준 감마 α.5 → 리니어 α.76 (채널별 .750 / .759 / .771).
- 사례: 딤을 감마값 그대로 둬 `#64779B` 위 검정 α.5 가 원본 `#323C4E` 대신 `#47556F` 로 밝게 떴다.
- 사례: 버튼 둘레 반투명 띠(「버튼 주변 어두운 글로우」 지적)는 사람 확정으로 걷었다 (함정: [사람이 없애라 한 버튼 둘레 띠를 측정으로 되살린 일](함정%20-%20사람%20권리%20안전.md#사람이%20없애라%20한%20버튼%20둘레%20띠를%20측정으로%20되살린%20일)).

## 카메라 · 정렬

### 요약

- 카메라 간 렌더 순서는 `depth` 가 정하고, depth 가 같으면 비결정적이다.
- 카메라가 다르면 `sortingOrder` 는 소용없다.
- UI가 월드 위로 안 올라오면 여기부터 본다.

### 설계

- 사례: 월드·UI 카메라가 둘 다 depth −1 이라 월드가 HUD 위로 그려졌다.
- 그래서 기본은 카메라마다 depth 를 다르게 두는 것이다.
- 정렬 순서는 프리팹에 자식 간 상대 오프셋만 굽고, 기준값은 런타임이 넣는 것이 기본이다.

## 완료 체크리스트

### 요약

- 연출 파트를 닫기 전에 아래를 확인한다.
- 못 잰 것은 지우지 말고 사유와 함께 남긴다.

### 규칙

- [ ] #강제 [원칙 R6](원칙.md#R6) 못 잰 항목은 `미측정(사유)` 로 적고 재측정 대기에 등록했다
- [ ] #강제 [원칙 R17](원칙.md#R17) 내 권한 밖 파일을 건드리지 않았다 (PD 「역할 기동 규약」 권한표)

### 설계

1. 합성 모드를 그 캔버스 기준으로 확인했나 (다른 캔버스의 `lighter` 에 속지 않았나)
2. 렌더 컴포넌트 기본값이 원본과 같은가
3. 원본 겹 수와 자식 수를 맞췄나
4. `shadowBlur` 를 수식으로 굽고 이론식과 대조했나
5. `lineWidth` 를 절대 픽셀로 다루나
6. 얇은 띠 텍스처 해상도가 충분한가
7. `t`/`dt` 를 받는 원본 함수가 유니티에서 실제로 움직이나
8. 애니메이션 방향·속도·주기가 원본 값인가
9. 반투명이 겹치는 자리의 알파를 방향에 맞게 역산했나
10. 카메라 `depth` 순서가 의도대로인가
11. 굽는 쪽 상수와 고르는 쪽 상수가 같은가
12. 여러 페이즈 연출에 `EditorSetPhase` 진입점이 있고 페이즈마다 한 장씩 구웠나 (「페이즈 진입 훅」)
