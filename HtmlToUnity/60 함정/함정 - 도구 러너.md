# 함정 - 도구 러너

배치 · 에디터 다리 · 로그가 성공을 찍었는데 실제로는 작업이 날아갔거나 낡은 코드로 돌았고, 도구와 산출물을 둔 자리가 틀려 다시 못 굽거나 파일이 사라진 함정들이다. 러너 · 배치 · 에디터 다리를 쓸 때, 굽는 도구 · 측정 파일을 어디 둘지 정할 때 편다.

## 성공 표시

### 요약

- 컴파일 실패 뒤 직전 어셈블리로 찍힌 성공 로그: 낡은 코드로 도니 방금 고친 수를 찍고 컴파일 에러를 직접 grep 한다.
- 배치 종료에 잘린 비동기 에디터 작업: 성공 로그가 있어도 결과물이 없으니 파일로 확인한다.
- 잘린 배치 콘솔 출력만 본 판정: 콘솔이 잘려 실패를 놓치니 로그 파일을 grep 해 판정한다.
- 파일시스템으로 만든 폴더의 조용한 에셋 생성 실패: 파이프라인이 몰라 조용히 실패하니 폴더를 에셋 API 로 만들고 개수를 센다.

### 설계

#### 컴파일 실패 뒤 직전 어셈블리로 찍힌 성공 로그
옛 번호: #176 · 파트: 미기재
- 증상: 방금 고친 값이 로그에 반영되지 않았는데 도구는 성공을 찍고, 낡은 코드로 여러 번 더 돈다.
- 원인: 컴파일이 실패하면 에디터가 직전 어셈블리로 도구를 돌려 성공 로그를 낸다.
- 방향: 기본은 도구가 방금 고친 수(행 수 · 경로 · 스위치)를 찍게 해 확인하고, 엔진 로그에서 컴파일 에러를 직접 grep 하는 것이다. 성공 로그와 컴파일 성공은 다른 사건으로 본다.
- 관련: [공통절차](공통절차.md)

#### 배치 종료에 잘린 비동기 에디터 작업
옛 번호: #8 · 파트: 전 파트
- 증상: 성공 로그는 찍혔는데 결과물이 없다.
- 원인: 비동기 에디터 API 가 끝나기 전에 `-quit` 이 와서 작업이 날아갔다.
- 방향: 기본은 결과를 파일로 확인하는 것이다. 동기 경로가 없으면 단계를 나눠 실행하거나 패키지를 직접 푸는 편이 낫다.

#### 잘린 배치 콘솔 출력만 본 판정
옛 번호: #36 · 파트: 전 파트
- 증상: 실패 로그를 놓치고 다음 단계로 넘어간다.
- 원인: 배치 명령의 콘솔 출력이 잘려 있었다.
- 방향: 기본은 로그 파일을 grep 해 판정하는 것이다. 배치 로그는 다음 실행이 지우니 판정을 마치기 전에는 다시 돌리지 않는다.
- 관련: [공통절차 - 에디터 실행](공통절차%20-%20에디터%20실행.md) 「배치모드」

#### 파일시스템으로 만든 폴더의 조용한 에셋 생성 실패
옛 번호: #33 · 파트: 전 파트
- 증상: 에셋 생성이 오류 없이 끝났는데 에셋이 없다.
- 원인: 파일시스템으로 만든 폴더를 에셋 파이프라인이 몰라 조용히 실패한다.
- 방향: 기본은 폴더를 에셋 API 로 만들고 생성 개수를 세는 것이다.

## 셸 러너

### 요약

- 실행 중에 편집한 셸 러너: 도는 중에 고치면 밀린 줄을 명령으로 읽으니 끝난 뒤에 고친다.
- 개행까지 지워 한 숫자로 붙은 PID 목록: PID 가 한 숫자로 붙으니 `tr -d '\r'` 만 쓰고 찾은 개수를 찍는다.

### 설계

#### 실행 중에 편집한 셸 러너
옛 번호: #141 · 파트: 전원
- 증상: 러너가 엉뚱한 명령을 실행해 에디터가 닫힌 채 남는다.
- 원인: 셸은 스크립트를 읽어 가며 실행해, 도는 중에 고치면 밀린 줄을 명령으로 읽는다.
- 방향: 기본은 작업이 끝난 뒤 러너를 고치는 것이다. 급하면 사본을 고쳐 사본으로 돌린다.
- 관련: [공통절차](공통절차.md)

#### 개행까지 지워 한 숫자로 붙은 PID 목록
옛 번호: #104 · 파트: 전원
- 증상: PID 두 개가 한 숫자로 붙어 어떤 프로세스에도 맞지 않는다.
- 원인: 여러 줄 출력에서 `\r` 만 지울 것을 개행까지 지웠다.
- 방향: 기본은 `tr -d '\r'` 만 쓰고 찾은 개수를 로그로 찍는 것이다. 개수가 기대와 다르면 거기서 멈춘다.

## 에디터와 재생 환경

### 요약

- 포커스 없는 에디터 재생의 throttle: 뒤에 둔 재생이 느리니 검사기가 시작할 때 `Application.runInBackground = true` 를 켠다.
- 사람에게 넘긴 에디터 메뉴 조작: 의뢰자가 유니티를 모르면 멈추니 다리나 배치로 직접 실행한다.
- 재생 전용 호출이 박힌 프레임워크 골격: 하네스가 골격을 못 쓰니 재생 없이도 서게 가드를 넣는다.
- 배치 재생 화면은 원본 화면비가 아니다: 게임 뷰가 4:3 이라 화면 좌표가 어긋나니 모서리에서 떨어진 거리를 캔버스 단위로 잰다.
- 배치 재생에는 입력 장치가 없다: `Mouse.current` 가 null 이니 검사기가 가짜 장치를 붙인다.
- 검사기 진입점 이름을 안 보고 부른다: 「클래스를 못 찾음」이 뜨니 부르기 전에 공개 진입점 이름을 직접 본다.

### 규칙

- 사람에게 엔진 조작을 요구하지 않는다. #강제 [원칙 R16](원칙.md#R16)

### 설계

#### 포커스 없는 에디터 재생의 throttle
옛 번호: #156 · 파트: Transfer_Programmer · PD
- 증상: 뒤에 둔 에디터 재생이 느려, 검사마다 에디터를 껐다 켜 배치로 돌리게 된다(회당 5~8분).
- 원인: `runInBackground` 가 꺼져 포커스 없는 재생이 throttle 됐다.
- 방향: 기본은 재생 검사기가 시작할 때 `Application.runInBackground = true` 를 켜는 것이다. 「원래 느리다」를 절차로 굳히기 전에 원인부터 캔다.
- 관련: [Transfer_Programmer](Transfer_Programmer.md) · [공통절차](공통절차.md)

#### 사람에게 넘긴 에디터 메뉴 조작
옛 번호: #6 · 파트: 전 파트
- 증상: 의뢰자가 유니티를 모르면 절차가 멈춘다.
- 원인: 에디터 메뉴 조작을 사람 몫으로 남겼다.
- 방향: 기본은 에디터 다리나 `-batchmode -executeMethod` 로 직접 실행하는 것이다.
- 관련: #강제 [원칙 R16](원칙.md#R16) · [공통절차 - 에디터 실행](공통절차%20-%20에디터%20실행.md) 「사람 요청 금지」

#### 재생 전용 호출이 박힌 프레임워크 골격
옛 번호: #9 · 파트: Client · 전 파트
- 증상: 하네스가 골격 코드를 못 써 수치 판정이 막힌다.
- 원인: 골격에 재생 중에만 되는 호출이 들어 있다.
- 방향: 기본은 재생 없이도 세울 수 있게 가드를 넣는 것이다.
- 관련: [GameFramework](GameFramework.md) 「하네스 호환」

#### 배치 재생 화면은 원본 화면비가 아니다
파트: Transfer_Programmer · UIUX
- 증상: 화면 좌표로 잰 배치 대조가 전부 어긋난다 (한쪽으로 0.33배, 다른 쪽으로 0.38배).
- 원인: 배치 재생 게임 뷰가 4:3(640×480)이고, 화면 모서리에 붙인 요소는 창 크기를 따라 자리를 바꾼다. `-screen-width` 를 줘도 게임 뷰가 그대로일 수 있다.
- 방향: 기본은 **붙은 모서리에서 떨어진 거리** 를 캔버스 단위로 재서 실측값과 견주는 것이다. 창 크기가 달라도 맞고, 앵커가 잘못 잡힌 것도 잡힌다.
- 관련: [UIUX](UIUX.md)

#### 배치 재생에는 입력 장치가 없다
파트: Transfer_Programmer
- 증상: 진짜 마우스 · 키보드 이벤트로 재는 검사가 「장치 없음」 으로 죽는다.
- 원인: 헤드리스 배치 재생에는 붙은 장치가 없어 `Mouse.current` 가 null 이다.
- 방향: 기본은 검사기가 `InputSystem.AddDevice<Mouse>()` 로 가짜 장치를 붙이고 상태 이벤트를 넣는 것이다. 테스트 프레임워크 없이도 된다.

#### 검사기 진입점 이름을 안 보고 부른다
파트: Transfer_Programmer
- 증상: 「클래스를 못 찾음」 이 계속 나와 스테이징 · 컴파일 순서를 의심하며 여러 번 헛돈다.
- 원인: 클래스는 있는데 그 **메서드** 가 없었다 (`Run` 이 아니라 `RunAll`). 유니티 오류 문구가 클래스를 못 찾았다고만 말한다.
- 방향: 기본은 부르기 전에 그 파일에서 공개 진입점 이름을 직접 보는 것이다. 산출물 로그 파일 이름(`out/batch-…_RunAll.log`)에도 옛 진입점이 남아 있다.

## 도구와 산출물의 자리

### 요약

- 임시 폴더에만 둔 굽는 스크립트: 다시 못 구우니 만드는 도구는 저장소 안에 둔다.
- 공용 자리에 둔 게임 전용 도구: 지워도 되는지 몰라 쌓이니 게임 전용 도구는 게임 폴더에 둔다.
- 유니티 Temp 폴더에 둔 측정 파일: 시작 때 비워지니 측정 파일은 프로젝트 밖에 둔다.
- 쓰기 모드로 먼저 열고 실패한 수정 스크립트: 파일이 0바이트가 되니 부분 수정은 편집 도구로 한다.

### 설계

#### 임시 폴더에만 둔 굽는 스크립트
옛 번호: #19 · 파트: 아트 · 전 파트
- 증상: 다시 굽지 못하고, 에셋이 왜 그 값인지 근거가 사라진다.
- 원인: 구성 도구를 저장소 밖 임시 폴더에 두었다.
- 방향: 기본은 만드는 도구는 저장소 안, 재는 도구만 밖에 두는 것이다. 헷갈리면 「이 도구가 없으면 사람 손으로 돌아가나」로 가른다.
- 관련: [Transfer_Programmer - 검증 도구](Transfer_Programmer%20-%20검증%20도구.md) 「도구 두 갈래」

#### 공용 자리에 둔 게임 전용 도구
옛 번호: #25 · 파트: 전 파트
- 증상: 지워도 되는지 몰라 도구가 쌓인다.
- 원인: 한 게임 전용 도구를 공용 폴더에 두었다.
- 방향: 기본은 게임 전용 도구를 게임 폴더에 두는 것이다. 굽는 도구를 옮겼으면 렌더 판정을 다시 잰다.
- 관련: [GameFramework](GameFramework.md)

#### 유니티 Temp 폴더에 둔 측정 파일
옛 번호: #38 · 파트: 전 파트
- 증상: 캡처 · 측정 파일이 사라져 있다.
- 원인: 유니티가 시작할 때 `Temp/` 를 비운다.
- 방향: 기본은 측정 파일을 프로젝트 밖 검증 산출물 자리에 두는 것이다.

#### 쓰기 모드로 먼저 열고 실패한 수정 스크립트
파트: 전 파트
- 증상: 스크립트로 문서 · 소스 한 곳을 고쳤는데 파일이 0바이트가 됐다. 버전 관리 밖 파일이면 되살릴 곳이 없다.
- 원인: 파일을 쓰기 모드로 연 순간 비워지는데, 그 뒤 내용을 쓰다가 오류가 났다. 셸 heredoc 속 파이썬 문자열의 유니코드 이스케이프가 서로게이트 글자로 바뀌어 UTF-8 인코딩이 실패한 경우다 (같은 대화에서 두 번 났다).
- 방향: 기본은 부분 수정을 편집 도구로 하는 것이다. 스크립트를 쓰면 새 내용을 **다 만든 뒤** 열거나, 임시 파일에 쓰고 바꿔 넣는다. 사고가 나면 작업 대화 기록의 쓰기 · 편집 · 일괄 변환 명령을 시간순으로 다시 적용해 살리고, 그날 본 줄 번호 · 헤딩과 맞춰 본다.
