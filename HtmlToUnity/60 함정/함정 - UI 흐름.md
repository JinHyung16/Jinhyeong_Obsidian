# 함정 - UI 흐름

CSS 가 규칙으로 정하던 배분 · 맞추기 · 상대값을 계산된 고정값으로 옮기고 층 · 전이 구조를 캡처나 열거형 기본값에 맡겨, 검사는 통과했는데 버튼이 안 눌리고 창이 안 열리고 문구가 넘친 함정들이다. 창 · HUD 를 조립하거나 화면 전이를 붙일 때, 버튼이 안 눌리거나 화면이 안 열릴 때 편다.

## 버튼 입력

### 요약

- 손으로 조립한 버튼의 꺼진 raycastTarget: 버튼이 먹통인데 검사는 통과하니 `raycastTarget` 을 켜는 조립 함수 하나로만 만든다.
- 폭 하나로만 맞춘 기준 해상도: 세로로 넘친 요소가 화면 밖이니 「안 눌린다」는 배치부터 의심한다.

### 설계

#### 손으로 조립한 버튼의 꺼진 raycastTarget
옛 번호: #148 · 파트: Transfer_Artist · Transfer_Programmer
- 증상: 버튼 여럿이 먹통인데 모든 검사가 통과한다.
- 원인: 손으로 조립한 이미지의 `raycastTarget` 이 꺼져 포인터를 받지 않았다.
- 방향: 기본은 `raycastTarget = true` 를 켜는 조립 함수 하나로만 버튼을 만드는 것이다. 프리팹 속성 검사와 재생 포인터 검사를 둘 다 두는 편이 낫다. 편집 모드 레이캐스트는 캔버스가 그려지지 않아 판정에 쓰지 않는다.
- 관련: [원칙 R7](원칙.md#R7) · [UIFramework](UIFramework.md)

#### 폭 하나로만 맞춘 기준 해상도
옛 번호: #15 · 파트: UI/UX · Client
- 증상: 버튼이 안 눌려 입력 불량으로 보인다.
- 원인: 기준 해상도를 폭으로만 맞춰 세로로 넘친 요소가 화면 밖에 있었다.
- 방향: 기본은 `Expand` 로 맞추고 배선 검사가 확인하게 두는 것이다. 「안 눌린다」는 입력보다 배치부터 의심하는 편이 낫다.

## 프리팹 굽는 순서

### 요약

- 새 필드를 참조하는 코드가 옛 프리팹을 만난다: 창을 열자마자 예외가 쏟아지니 코드 → 프리팹 굽기 → 검사를 한 묶음으로 돌린다.

### 설계

#### 새 필드를 참조하는 코드가 옛 프리팹을 만난다
파트: Client · UIUX
- 증상: 창을 열자마자 `NullReferenceException` 이 쏟아지고, 그 창을 쓰는 검사가 통째로 실패한다.
- 원인: 창 클래스에 `[SerializeField]` 를 더하고 프리팹을 다시 굽기 **전에** 재생 검사를 돌렸다. 검사가 새 코드를 컴파일해 옛 프리팹(그 필드가 비어 있음)을 쓴다.
- 방향: 기본은 **코드 → 프리팹 굽기 → 검사** 를 한 묶음으로 돌리는 것이다. 창 코드가 필드를 쓰기 전에 `null` 을 견디게 두면 조용히 빠진 채로 지나가니, 굽는 순서를 지키는 쪽이 낫다.

## 화면 층과 창 구조

### 요약

- 스크린샷으로 정한 화면 층: 캡처로 층을 정하면 디머가 HUD 를 덮으니 덤프의 부모 사슬로 정한다.
- 창 루트 Image 로 붙인 배경: 계층에서 안 보이니 `Window → BG · SafeArea` 구조로 둔다.
- HUD 창을 가리는 불투명 배경: 가릴 것이 없는 HUD 는 배경을 두지 않고 이유를 주석에 적는다.
- 네 변 전부에 건 안전 영역: 좌우 인셋 기기에서 폭이 주니 적용할 변을 고를 수 있게 둔다.
- 그릴 대상을 안 가른 두 카메라의 이중 렌더: 월드가 두 번 그려지니 레이어로 카메라마다 대상을 좁힌다.

### 설계

#### 스크린샷으로 정한 화면 층
옛 번호: #165 · 파트: UIUX · Transfer_Programmer
- 증상: HUD 아래에 있어야 할 디머가 HUD 를 덮는다.
- 원인: 캡처를 보고 층을 정했으나 덤프상 그 화면의 부모는 모달 층이었다.
- 방향: 층은 덤프의 부모 사슬과 형제 순서로 정한다. 층을 옮기면 입력 순서도 바뀌니 버튼이 눌리는지 다시 재는 편이 낫다.

#### 창 루트 Image 로 붙인 배경
옛 번호: #27 · 파트: UI/UX
- 증상: 배경을 안전 영역 안으로 옮겨도 아무도 알아채지 못한다.
- 원인: 배경이 창 루트의 컴포넌트라 계층 구조에서 보이지 않는다.
- 방향: 기본 구조는 `Window → BG · SafeArea` 이고, BG 가 SafeArea 밖에 있고 먼저 그려지는지 검사한다. 배경이 없는 창은 이유를 주석에 적는다.
- 관련: [UIFramework](UIFramework.md)

#### HUD 창을 가리는 불투명 배경
옛 번호: #35 · 파트: UI/UX
- 증상: HUD 가 게임 화면을 가린다.
- 원인: 「창에는 배경」 구조를 기계적으로 따랐다.
- 방향: 기본 창 구조를 따르되, 가릴 것이 없는 HUD 는 배경을 두지 않고 이유를 주석에 적는 편이 낫다.

#### 네 변 전부에 건 안전 영역
옛 번호: #28 · 파트: UI/UX
- 증상: 좌우 인셋이 있는 기기에서 화면 폭이 준다.
- 원인: 안전 영역을 네 변에 일괄 적용했다.
- 방향: 적용할 변을 고를 수 있게 둔다. 세로 게임의 기본은 상·하다.

#### 그릴 대상을 안 가른 두 카메라의 이중 렌더
옛 번호: #34 · 파트: 연출 · UI/UX
- 증상: 뒤 카메라가 월드를 한 번 더 그려 배율이 틀린다.
- 원인: 두 카메라의 그릴 대상을 가르지 않았다.
- 방향: 레이어로 카메라마다 그릴 대상을 좁히고, 겹칠 때는 렌더 파이프라인이 주는 카메라 겹치기 방식을 쓴다.

## 화면 전이와 열거형 순서

### 요약

- 0번 첫 화면이라 무시된 첫 전이: 전이기가 재진입으로 보니 첫 진입 플래그로 첫 전이를 알린다.
- 열거형 맨 앞에 끼운 새 화면의 무시된 전이: 새 화면이 0번이 되니 열거형 뒤에 붙인다.

### 설계

#### 0번 첫 화면이라 무시된 첫 전이
옛 번호: #126 · 파트: Transfer_Programmer · PD
- 증상: 게임을 켜면 첫 화면 창만 안 열린다.
- 원인: 첫 화면이 열거형 0번(기본값)이라 전이기가 같은 화면 재진입으로 보고 무시했다.
- 방향: 첫 진입 플래그로 첫 전이를 알린다. 열거형 순서는 바꾸지 않고, 플로우 diff 의 첫 줄을 「첫 화면 창 열림」으로 두는 편이 낫다.

#### 열거형 맨 앞에 끼운 새 화면의 무시된 전이
옛 번호: #177 · 파트: Transfer_Programmer · UIUX
- 증상: 새로 넣은 화면으로 가는 전이가 조용히 안 먹는다.
- 원인: 새 화면을 열거형 맨 앞에 넣어 0번이 되었다. 전이기는 0번으로 서 있다가 같은 화면 재진입으로 보고 무시했다.
- 방향: 새 화면은 열거형 뒤에 붙인다. 「0번이 시작 화면」 규칙은 넣을 때와 뺄 때 모두 열거형 주석에 적는 편이 낫다.
- 관련: 같은 뿌리. 위 「0번 첫 화면이라 무시된 첫 전이」

## CSS 배치 규칙

### 요약

- 배분 간격을 고정값으로 옮긴 레이아웃: 결과값 말고 CSS 규칙을 옮긴다.
- 부모 기준 상대값을 절대 상수로 옮긴 좌표: 값이 전부 같으면 상대값을 의심한다.
- 레이아웃 그룹 자식에 붙인 크기 자기결정 부품: 크기가 폭주하니 임시 캔버스에 세워 레이아웃을 확정한 뒤 잰다.

### 설계

#### 배분 간격을 고정값으로 옮긴 레이아웃
옛 번호: #22 · 파트: UI/UX
- 증상: `space-between` 간격이 균일한 고정 간격이 되고 음수 마진이 사라진다.
- 원인: 규칙이 계산해 낸 결과값을 옮겼다.
- 방향: 값이 아니라 CSS 규칙을 옮긴다. 배분은 늘어나는 빈 칸으로, 음수 마진은 음수 간격으로 두고, 옮긴 뒤 모양을 잰다.
- 관련: [UIUX](UIUX.md)

#### 부모 기준 상대값을 절대 상수로 옮긴 좌표
옛 번호: #59 · 파트: UI/UX · 아트
- 증상: 좌표·크기가 원점 근처로 몰리거나 뭉개진다.
- 원인: 부모 기준 상대값을 화면 절대 상수로 읽었다.
- 방향: 여러 요소를 대조해 값이 전부 같으면 상대값을 의심한다. 절대 위치는 원본 bbox 를 정본으로 삼는 편이 낫다.

#### 레이아웃 그룹 자식에 붙인 크기 자기결정 부품
옛 번호: #16 · 파트: UI/UX · Client
- 증상: 부모·자식 크기가 폭주하는데 존재 검사는 통과한다.
- 원인: 크기를 스스로 정하는 부품과 레이아웃 그룹이 서로 크기를 덮어썼다.
- 방향: 임시 캔버스에 세워 레이아웃을 확정한 뒤, 크기가 부모·화면 안에 드는지 잰다.

## 문구 크기와 폭

### 요약

- 상자 맞추기 없이 고정한 글자 크기: 서체를 바꾸면 넘치니 상자를 데이터로 들고 맞추기 규칙을 옮긴다.
- 엔진마다 다른 텍스트 경계의 폭 비교: 폭 기준이 서로 다르니 자리를 엄격히 보고 폭은 ±10% 로 본다.

### 설계

#### 상자 맞추기 없이 고정한 글자 크기
옛 번호: #164 · 파트: UIUX · Transfer_Programmer
- 증상: 서체를 바꾸자 문구가 상자를 넘친다.
- 원인: 원본은 문구를 `min(상자폭/글자폭, 상자높이/글자높이, 1)` 배율로 줄여 넣는데 크기만 옮겼다.
- 방향: 문구마다 상자를 데이터로 들고, 넘치면 줄이는 컴포넌트를 쓴다. 맞추기 규칙 자체가 이관 대상이다. 레이아웃 전에 잰 크기 0 은 잰 값이 아니니 캐시하지 않는다.

#### 엔진마다 다른 텍스트 경계의 폭 비교
옛 번호: #157 · 파트: UIUX · Transfer_Artist
- 증상: 한 글자 숫자의 폭이 원본의 절반도 안 되게 나와 불일치로 잡힌다.
- 원인: 원본은 stroke 를 포함한 렌더 폭, 우리는 글리프 사각형이라 같은 값이 아니다.
- 방향: 텍스트는 자리(중심·모서리)를 엄격히 보고 폭은 ±10% 로 본다. 폭이 어긋나면 폰트 에셋 advance 를 먼저 재고, 남는 차이는 서체 차이로 등재한다.
- 관련: [함정 - 아트 굽기](함정%20-%20아트%20굽기.md) 「대체 서체의 글자 폭 차이」
