# 함정 - 아트 굽기

색 · 알파를 합성된 화면이나 브라우저에서 재고, 구운 값이 파일에 남지 않고, 시트를 굽고도 화면이 그것을 쓰는지 세지 않아 검사는 통과했는데 그림이 달랐던 함정들이다. 원본 그림을 재고 굽고 화면에 올리기 전에, 굽기 검사가 통과했는데 화면이 다를 때 편다.

## 원본 색과 알파

### 요약

- 합성 화면 캡처로 잰 자산색: 화면색은 자산색이 아니니 소스 텍스처 파일 바이트로 잰다.
- 브라우저 캔버스로 읽은 원본 그림의 색 왜곡: 낮은 알파에서 색이 틀어지니 이미지 파일 바이트를 여는 라이브러리로 잰다.
- 디머 아래에서 잡은 바탕색 팔레트: 오버레이 합성색을 바탕색으로 읽으니 오버레이가 없는 상태에서 잰다.

### 설계

#### 합성 화면 캡처로 잰 자산색
옛 번호: #94 · 파트: Fx · UIUX
- 증상: 캡처에서 뽑은 색으로 구운 자산이 런타임 착색을 한 번 더 받아 색이 틀린다.
- 원인: 화면색은 자산색 × 런타임 착색이라 자산 자체의 색이 아니다.
- 방향: 기본은 소스 텍스처 파일 바이트로 잰다. 자산이 단색 마스크면 색을 굽기보다 착색 기전을 옮기는 편이 낫다.
- 관련: [Fx](Fx.md) 「색공간」

#### 브라우저 캔버스로 읽은 원본 그림의 색 왜곡
옛 번호: #169 · 파트: Fx · Transfer_Artist
- 증상: 낮은 알파 픽셀의 색이 중성 회색으로 바뀌어 그림자가 검은 글로우처럼 보인다.
- 원인: `getImageData` 는 알파 곱을 되돌리는 오차가 낮은 알파에서 커진다.
- 방향: 기본은 원본 이미지 파일 바이트를 여는 라이브러리(Pillow 등)로 잰다. 알파를 고친 뒤에는 같은 자리 색도 다시 재고, 원본 파일과 바이트 단위 일치를 합격선으로 두는 편이 낫다.
- 관련: [공통절차 - 원본 관측 도구](공통절차%20-%20원본%20관측%20도구.md) 「도구 선택」

#### 디머 아래에서 잡은 바탕색 팔레트
옛 번호: #142 · 파트: Fx · UIUX · PD
- 증상: 디머가 깔린 화면의 색을 팔레트로 써서 바탕이 두 배로 어두워진다.
- 원인: 오버레이가 합성된 색을 원본 바탕색으로 읽었다.
- 방향: 바탕색은 오버레이가 없는 상태에서 잰다. 첫 화면 개체를 원본 정의와 1:1 로 세어 오버레이가 섞였는지 먼저 가르는 편이 낫다.

## 반투명 굽기

### 요약

- 모양 마스크가 덮어쓴 원본 알파: 반투명이 불투명이 되니 마스크와 원본 알파를 곱해 굽는다.
- Linear 프로젝트에 원본 값 그대로 구운 반투명: 섞인 색이 다르니 감마 합성 결과를 Linear 에서 내는 알파로 역산한다.
- 어두운 오버레이 알파 역산 방향 착오: 역산은 방향별로 가르고 어두운 오버레이는 `1 − (1−a)^2.2` 로 올린다.
- 색 키에서 빠진 알파 축: 낮은 알파를 버리면 판이 되니 규격과 채점기에 알파 축을 둔다.

### 규칙

- 사람이 지목한 자리는 다른 원인을 고쳤더라도 같이 걷는다. #강제 [원칙 R12](원칙.md#R12)

### 설계

#### 모양 마스크가 덮어쓴 원본 알파
옛 번호: #17 · 파트: 연출 · 아트
- 증상: 원본의 반투명 부분이 불투명으로 구워진다.
- 원인: 모양 마스크 값으로 알파를 통째로 덮었다.
- 방향: 기본은 마스크와 원본 알파를 곱해 굽는다. 구운 알파는 원본 알파와 대조해 확인한다.

#### Linear 프로젝트에 원본 값 그대로 구운 반투명
옛 번호: #18 · 파트: 연출 · 아트
- 증상: 알파는 같은데 섞인 결과 색이 원본과 다르다.
- 원인: 브라우저는 감마 공간에서 섞고 Linear 프로젝트는 선형 공간에서 섞는다.
- 방향: 감마 합성 결과를 Linear 에서 내는 알파를 역산해 굽는다. 굽는 스크립트에 이유와 최대 채널차를 적어 두면 다음 작업자가 원본 값으로 되돌리지 않는다.
- 관련: [Fx](Fx.md) 「색공간」

#### 어두운 오버레이 알파 역산 방향 착오
옛 번호: #183 · 파트: Fx · Transfer_Artist
- 증상: 딤·그림자가 원본보다 옅어 화면이 밝다.
- 원인: 밝은 오버레이용 역산(`a^2.2`, 내림)만 알았고, 어두운 오버레이는 감마값 그대로 두었다.
- 방향: 역산은 방향별로 가른다. 밝은 오버레이는 `a^2.2` 로 내리고, 어두운 오버레이(딤·그림자)는 `1 − (1−a)^2.2` 로 올린다. 다른 원인을 찾아 고쳤더라도 사람이 지목한 자리는 같이 걷는다.
- 관련: [Fx](Fx.md) 「색공간」 · 사람이 지목한 것을 걷는 부분은 `#강제 [원칙 R12](원칙.md#R12)`

#### 색 키에서 빠진 알파 축
옛 번호: #167 · 파트: Transfer_Artist · Fx
- 증상: 부드러운 반투명 그림자가 불투명한 한 색 판이 되는데 픽셀 일치 채점은 100% 가 나온다.
- 원인: 팔레트 키를 RGB 로만 잡고 낮은 알파를 투명으로 버렸다. 채점기도 알파를 보지 않았다.
- 방향: 규격에 알파 축을 따로 두고 채점기가 알파까지 잰다. 투명은 알파 0 하나로 정하고, 실루엣·색 배치·알파 배치 표가 같은 기준을 쓰는 편이 낫다.

## 구운 값의 저장

### 요약

- 텍스처 타입만 바꾼 스프라이트 변환: 로드가 null 이니 굽고 나서 실제로 로드해 빈 참조를 센다.
- 직렬화되지 않는 프로퍼티에 구운 값: 런타임에 기본값이 나오니 공유 에셋을 만들어 물린다.
- 인스턴스 재질에 쓴 문구 테두리 설정: 프리팹 저장 때 버려지니 재질을 에셋 파일로 저장해 공유 슬롯에 물린다.
- 선행 설정 없이 부른 엔진 API 의 값 유실: 넣은 값이 버려지니 파생값까지 저장된 파일에서 되읽는다.
- 임포터 설정이 먹기 전에 읽은 시트 격자: 칸 수가 모자라니 파생값은 설정이 먹은 뒤나 원본 파일에서 읽는다.
- 굽기 API 에 넣은 열거형 값과 인덱스 혼동: 한 칸씩 밀리니 밑값을 받는 API 를 따로 쓰고 되읽어 확인한다.

### 설계

#### 텍스처 타입만 바꾼 스프라이트 변환
옛 번호: #32 · 파트: 아트 · UI/UX
- 증상: 로드 결과가 null 이라 화면이 빈다.
- 원인: 텍스처 타입만 Sprite 로 바꾸고 스프라이트 생성 모드는 그대로 두었다.
- 방향: 굽고 나서 실제로 로드해 빈 참조 개수를 센다. 임포트 설정은 함께 바뀌어야 하는 항목까지 확인하는 편이 낫다.

#### 직렬화되지 않는 프로퍼티에 구운 값
옛 번호: #71 · 파트: 아트 · Client
- 증상: 굽기는 성공인데 런타임에는 기본값이 나온다.
- 원인: 그 프로퍼티가 새 인스턴스를 만들어 에셋에 참조가 남지 않았다.
- 방향: 직렬화 파일을 열어 참조가 남았는지 본다. 기본은 공유 에셋을 만들어 물리는 것이다.

#### 인스턴스 재질에 쓴 문구 테두리 설정
옛 번호: #171 · 파트: Transfer_Artist · UIUX
- 증상: 모든 문구에 테두리가 없다. 구운 프리팹의 재질 참조가 0 이다.
- 원인: 테두리 두께·색 설정이 엔진이 만든 인스턴스 재질에 써져 프리팹 저장 때 버려졌다.
- 방향: 재질을 에셋 파일로 저장해 공유 슬롯에 물리고, 같은 설정은 한 벌만 재사용한다. 「이 값은 어느 파일에 적히나」에 답이 없으면 저장되지 않는다고 본다(재질·메시·애니메이션 상태). 검사는 구운 파일이나 재생 화면에서 되읽는 편이 낫다.

#### 선행 설정 없이 부른 엔진 API 의 값 유실
옛 번호: #55 · 파트: Client · 아트
- 증상: 오류 없이 일부 값만 어긋난다.
- 원인: 엔진 API 에 설정 순서가 있어 선행 설정이 없으면 넣은 값이 버려진다.
- 방향: 넣은 값뿐 아니라 파생값(질량·크기·경계)까지 저장된 파일에서 되읽어 전부 대조한다.

#### 임포터 설정이 먹기 전에 읽은 시트 격자
옛 번호: #180 · 파트: Transfer_Artist · Transfer_Programmer
- 증상: 시트 칸 수가 모자라게 잘리는데 굽기·임포트는 성공을 찍는다.
- 원인: 격자 수를 임포트된 텍스처 크기에서 뽑았고, NPOT 반올림 끄기는 재임포트 뒤에야 먹었다.
- 방향: 파생값은 설정이 먹은 뒤에 읽거나 원본 파일에서 읽는다. 로드하는 쪽이 「N칸 중 M칸만 읽힘」을 세어 오류로 남기면, 여유가 있어 우연히 안 터진 시트도 드러난다.

#### 굽기 API 에 넣은 열거형 값과 인덱스 혼동
옛 번호: #175 · 파트: Transfer_Artist · Transfer_Programmer
- 증상: 구운 항목이 전부 한 칸씩 밀리는데 개수 검사는 통과한다.
- 원인: 인덱스를 받는 API 에 값을 넣었다. 첫 항목이 0 이 아닌 열거형(`None = -1`)이었다.
- 방향: 밑값을 받는 API 를 따로 쓰고 되읽어 확인한다. 검사는 개수가 아니라 기대값이 전부 있는지 센다. 첫 항목이 0 이 아닌 열거형을 굽는 자리는 한꺼번에 찾아 바꾸는 편이 낫다.

## 시트와 타일

### 요약

- 상태별 시트를 구웠지만 뷰가 한 장만 그림: 구운 것과 쓰는 것은 다르니 재생에서 상태를 전이시켜 잰다.
- 일부만 옮긴 자동 타일링 갈래: 없는 종류가 대체되어 안 보이니 「타일 종류 수 = 원본 분기 수」를 검사한다.
- 굽는 쪽과 고르는 쪽에 따로 적은 역할 순서: 두 곳에 적어 어긋나니 제품 코드는 역할만 알고 대응은 검사가 든다.
- 칸 수와 자리 보폭이 달라 빈 시트 꼬리: 보폭은 하나만 쓰고 통째로 투명한 칸을 세어 실패로 찍는다.

### 설계

#### 상태별 시트를 구웠지만 뷰가 한 장만 그림
옛 번호: #153 · 파트: Transfer_Artist · Transfer_Programmer
- 증상: 상태가 바뀌어도 개체가 같은 그림으로 따라다닌다. 아트 채점기와 데이터 검사는 통과한다.
- 원인: 시트를 구운 것과 화면이 그것을 쓰는 것을 같게 셌다.
- 방향: 재생에서 상태를 실제로 전이시켜 상태값 변화·다른 시트로 갈림·컷 회전을 잰다. 여럿이 서는 개체는 개수·서로 다른 시트·자리를 센다. 새 시트마다 읽는 곳을 한 줄 적는 편이 낫다.
- 관련: [원칙 R7](원칙.md#R7) · [함정 - 로직 데이터](함정%20-%20로직%20데이터.md) 「읽는 코드가 없는 표 주소 컬럼」

#### 일부만 옮긴 자동 타일링 갈래
옛 번호: #151 · 파트: Fx · Transfer_Artist
- 증상: 가장자리·안쪽 모서리 타일 일부가 가까운 타일로 대체되는데 칸 수·같은 칸 검사는 통과한다.
- 원인: 자동 타일링 분기를 일부만 옮겼다. 없는 종류가 가까운 타일로 대체되어 눈에 띄지 않았다.
- 방향: 소스의 타일 ID 상수를 전부 훑어 분기 수를 표로 만들고 「타일 종류 수 = 원본 분기 수」를 검사한다. 이웃을 보는 패스(자동 타일링·목 제거)는 조건 순서도 규칙으로 옮긴다.

#### 굽는 쪽과 고르는 쪽에 따로 적은 역할 순서
옛 번호: #181 · 파트: Transfer_Artist · Transfer_Programmer
- 증상: 변종 두 개가 뒤바뀌었는데 둘 다 풀이라 칸 수·빈 칸·픽셀 검사가 통과한다.
- 원인: 역할 순서를 굽는 코드와 고르는 코드 두 곳에 적어 어긋났다.
- 방향: 제품 코드는 역할만 알고, 역할 ↔ 원본값 대응은 검사가 든다. 원본 규칙을 옮긴 스크립트의 정답 타일 격자와 화면 역할을 원본 숫자로 되돌려 전 칸 대조하고, 어긋남 0칸을 합격선으로 두는 편이 낫다. 새 생성기는 옛 골든과 한 칸도 다르지 않은지 먼저 검산한다.

#### 칸 수와 자리 보폭이 달라 빈 시트 꼬리
옛 번호: #182 · 파트: Transfer_Artist · Transfer_Programmer
- 증상: 시트 마지막 줄 뒤쪽 칸이 투명해 도는 동안 깜빡이는데 채점기는 100% 다.
- 원인: 칸 수는 쓰는 열 수로, 자리는 전체 열 수로 계산했다. 채점기도 같은 범위를 봤다.
- 방향: 보폭은 하나만 쓴다. 굽고 나서 게임이 도는 칸 중 통째로 투명한 칸을 세어 실패로 찍고, 채점 범위는 결과물의 칸 수로 잡는다. 도는 칸과 굽는 칸의 차이는 코드에 적어 둔다.

## 9슬라이스 테두리 두께

### 요약

- 스프라이트와 캔버스 PPU 불일치로 찌그러진 9슬라이스: 모서리가 타원이나 알약이 되니 두 PPU 의 비를 정적 검사한다.
- 화면 배율만큼 얇아진 9슬라이스 테두리: 모서리를 px 그대로 그리니 그려지는 두께를 검사하고 배수를 화면 배율의 역수로 넣는다.

### 설계

#### 스프라이트와 캔버스 PPU 불일치로 찌그러진 9슬라이스
옛 번호: #20 · 파트: UI/UX · 아트
- 증상: 둥근 사각형의 모서리가 줄어 타원처럼 보인다. 거꾸로 스프라이트 PPU 가 기준보다 작으면(코드로 만든 그림을 PPU 1 로) 모서리가 판 높이 절반까지 부풀어 알약 모양이 되고, 레이아웃 그룹이 붙은 카드의 선호 높이가 수천(경계 × 기준 PPU)으로 튀어 카드가 화면 밖까지 늘어난다.
- 원인: 경계만 넣고 스프라이트 PPU 와 캔버스 PPU 의 비를 맞추지 않았다. `Image` 는 9조각 경계를 `스프라이트 PPU ÷ 기준 PPU` 로 나눠 그리고, 같은 값을 레이아웃 선호 크기로도 낸다.
- 방향: 스프라이트 PPU 와 캔버스 기준 PPU 가 맞는지 정적 검사한다. 엔진 설정의 짝 구성요소를 보는 검사와 같은 틀에 넣으면 된다.
- 관련: [GameFramework - 프로젝트 설정](GameFramework%20-%20프로젝트%20설정.md) 「딸린 구성요소」

#### 화면 배율만큼 얇아진 9슬라이스 테두리
옛 번호: #166 · 파트: Transfer_Artist · UIUX
- 증상: 인셋 값은 소스와 같은데 테두리가 원본보다 얇고, 채우는 바의 둥근 끝이 잘린다.
- 원인: 엔진은 9슬라이스 모서리를 스프라이트 px 그대로 그려 캔버스가 키운 만큼 두꺼워지지 않는다. 채우는 바는 그림을 자르는 방식이었다.
- 방향: 검사는 그려지는 두께 `인셋 ÷ (스프라이트 PPU × 배수) × 캔버스 기준 PPU` 가 `인셋 × 화면 배율` 과 같은지 잰다. 빌더는 배수를 화면 배율의 역수로 넣고, 늘리는 방식(자르기 / 폭 키우기)도 소스와 맞추는 편이 낫다.

## 재제작 그림과 서체

### 요약

- 원본과 나란히 안 본 아트 재제작: 도형 수준 그림이 완료로 남으니 마감 전 대조 시트를 사람이 본다.
- 대체 서체의 글자 폭 차이: 비례폭으로 바꾸면 폭이 주니 글리프 폭을 원본과 비교한다.

### 설계

#### 원본과 나란히 안 본 아트 재제작
옛 번호: #139 · 파트: Transfer_Artist · PD
- 증상: 원본과 닮지 않은 도형 수준의 그림이 재제작 완료로 남는다.
- 원인: 재제작 결과를 원본과 비교하는 단계가 없었다.
- 방향: 마감 전 Assets 밖에 원본 vs 우리 대조 시트를 만들어 사람이 본다. 자작 지표가 만점이어도 이 단계는 남기는 편이 낫다.
- 관련: [원칙 R7](원칙.md#R7) · [Transfer_Artist](Transfer_Artist.md)

#### 대체 서체의 글자 폭 차이
옛 번호: #150 · 파트: UIUX · Transfer_Artist
- 증상: 문구 폭이 원본의 절반 남짓으로 줄어 배치가 달라진다.
- 원인: 고정폭 원본 서체를 비례폭 서체로 대체하고 폭을 재지 않았다.
- 방향: 글리프 폭 ÷ (글자 수 × fontSize) 를 원본과 비교한다. 원본이 고정폭이면 폰트 에셋에 advance 1em 으로 굽는 편이 낫다.
- 관련: [함정 - UI 흐름](함정%20-%20UI%20흐름.md) 「엔진마다 다른 텍스트 경계의 폭 비교」
