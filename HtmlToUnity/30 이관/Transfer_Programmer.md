# 이관 담당 · 코드/데이터

지식을 만들지 않고, Client 와 Design 의 지식을 합쳐 원본의 코드와 데이터를 Unity 프레임워크에 맞게 옮긴다.

## 역할

### 요약

- 이 역할의 이름은 HtmlToUnity_Transfer_Programmer 다. 한 단위 안에서 패스 ①과 ③ 두 번 돈다.
- 상위는 [PD](PD.md). 지식 출처는 [Client](Client.md) + [Design](Design.md).
- 규약은 [DataFramework](DataFramework.md) · [GameFramework](GameFramework.md) · [UIFramework](UIFramework.md).
- 원장은 `HtmlToUnity_작업내역_<게임명>.md` 이고 착수 시 PD 가 만든다.
- 방향 노트다. 기본값과 이유를 준다. 판단 대상이 아닌 것은 [원칙](원칙.md) 에만 있다.

### 규칙

#강제 [원칙 R1](원칙.md#R1) 목표는 시스템·데이터·거동 100% 이고, 「돌아간다」는 완료가 아니다.

#강제 [원칙 R17](원칙.md#R17) 아래 선언문의 「하지 않는 것」은 이 역할의 권한 경계다.

### 설계

```
작업 분해표의 단위 하나 :
  ① 코드 / 데이터 이관      ← 나
  ② 프리팹 / 연출 생성      ← Transfer_Artist
  ③ 게임 플로우에 따라 배선  ← 나 (UI · 연출 · 게임오브젝트)
  → 그 단위의 완료 조건 검사 → 완료 → 다음 단위
```

- 기본은 한 단위를 검사까지 완주하고 다음으로 가는 것이다. 이유: 게임 전체에 ①을 다 하고 ②를 다 하면 뒤에서 나온 결함이 앞 단위로 되돌아간다 (함정: [분석과 이관 사이에 작업 분해표가 없음](함정%20-%20문서%20운영.md#분석과%20이관%20사이에%20작업%20분해표가%20없음)).
- 끝난 단위를 다시 열어야 하면 대개 완료 조건이 약했던 것이다. 그 단위의 완료 조건을 고쳐 분해표에 반영한다.
- ①에서는 주입 API 를 선언하고, ②에서 실물이 나온 뒤 ③에서 실제로 호출한다.
- 이전 역할의 결론은 md 에 적힌 것을 이어받는 것이 기본이다. 이유: 기억으로 이어가면 앞 역할의 결론이 기록 없이 다음 판단에 섞인다.

역할 선언. 이 역할로 들어갈 때 다음을 출력한다 ([PD - 실행 단계](PD%20-%20실행%20단계.md) 「역할 기동 규약」).

```
[역할 전환] 지금부터 나는 Transfer_Programmer(패스 ① 또는 ③)다.
  할 수 있는 것 : 데이터·Manager·Management·Window 스크립트 · 배선
  하지 않는 것  : 프리팹 · 아트 · 굽는 스크립트 (Artist 에게 되돌린다)
```

## Unity 프로젝트 세팅

### 요약

- PD 착수 확정([PD - 착수 질문](PD%20-%20착수%20질문.md))의 답을 PD 가 아래 표에 채운다.
- 수치 계층은 원본이 JS 일 때의 기본값이다.
- 주의: 원본이 물리 엔진 위에서 돌면 수치 계층 기본값이 뒤집힌다. 그래서 착수 전에 원본이 엔진을 쓰는지부터 확인한다.

### 규칙

수치 계층:

- 계산 기본은 `double` 이다. 이유: 원본 JS 숫자는 전부 double 이라, `Mathf`(float) 가 섞이면 값이 갈린다.
- 확률 기본은 주입식 RNG 다. 이유: `Random` 을 직접 부르면 재현이 안 되고, 재현 불가면 채점 불가다.
- 가변 dt 는 원본과 같은 상한으로 클램프하는 것이 기본이다. 판정도 자체 코드가 기본이고 물리 엔진을 섞지 않는다.
- 원본이 물리 엔진을 쓰면 [[Client](Client.md) 「물리 엔진」](Client.md).

## 코드 파악

### 요약

- 패스 ① 의 기본 순서는 코드 파악 → 데이터 파악 → 합쳐 파악 → 이관이다.
- 이유: 뒤 단계가 앞 단계의 결과(읽는 함수 · 키 합집합)를 입력으로 쓴다.
- 코드는 프레임워크 → 시스템 → 게임 플로우 순으로 훑는다.
- 게임 플로우에는 무엇이 열리는가와 함께 무엇이 안 열리는가도 적는 것이 기본이다. 이유: 원본에 없는 창이 한 겹 더 뜨는 결함은 프리팹 대조로 안 잡힌다 ([PD - 게이트](PD%20-%20게이트.md) 「플로우 diff」).

### 설계

| 보는 것 | 무엇을 얻나 |
|---|---|
| 전역 상태·부팅 함수 | 저장 스키마·초기값·모듈 경계 |
| 메인 루프 | dt 클램프 · 정지 게이트 · 호출 순서 |
| 시스템별 진입 함수 | 계산식 · 상태 전이 |
| 게임 플로우 | 모든 UI 의 열기·닫기 경로 전수 |

```bash
grep -n "_loopBody\|requestAnimationFrame" -A 6 원본.html    # 메인 루프
grep -n "function setScreen" -A 20 원본.html                  # 화면 전이
grep -n "addEventListener\|onclick=\|data-act" 원본.html      # 버튼 전수 → 무엇을 여는가
```

## 데이터 파악

### 요약

- 원본 데이터의 형식(배열/객체, 키, 행 수)을 본다.
- 행 수를 센다. 그 수가 시트 어설션과 게이트 G1 의 통과 증명이다.
- 기본은 원본 필드를 전부 옮기는 것이다. 원본 객체의 키 합집합을 뽑아 시트 컬럼과 대조하고, 안 옮기는 편이 나은 필드는 이유를 적고 뺀다.
- 이유: 안 옮긴 필드는 시트 어설션·컨테이너 조회·화면 검증을 모두 통과하고 조용히 빈 칸이 된다.
- 사례: `ShipTreeNodeData` 의 `glyph` 누락으로 342개 중 300개 노드가 아이콘 없이 렌더됐다.

### 설계

- 요소 안에 쉼표가 들어가는 데이터는 1:N 시트로 정규화하는 것이 기본이다 (DataFramework 「배열에 쉼표가 들어가야 하면 배열을 쓰지 않는다」).
- 원본 `||` 뒤의 폴백 계수는 코드 상수로 두고 원본 행을 주석에 인용한다.

```bash
# 예시 — 파일 경로·객체명은 원본마다 다르다
node -e "const M=require('./scripts/data/gamedata.js'); console.log(Object.keys(M.SHOP).length)"
```

```bash
# 예시 — 원본 객체가 실제로 쓰는 키 전수. 시트 컬럼과 개수를 맞춘다
node -e "const T=require('./scripts/trees/shiptrees.js');
  const k=new Set(); Object.values(T).flat().forEach(n=>Object.keys(n).forEach(x=>k.add(x)));
  console.log([...k].sort().join(' '), '|', k.size)"
```

코드 + 데이터를 합쳐 「어떻게 쓰는가」를 본다.

- 기본은 데이터 항목마다 읽는 코드 지점을 짝지어 표로 적는 것이다.
- 이유: 건너뛰면 아무도 안 읽는 테이블이 생긴다.

| 테이블 | 컬럼 | 읽는 원본 함수 | 우리 쪽 |
|---|---|---|---|
| 표기 사전 | `unit` | `statLine()` | ? ← 빈 칸이 곧 결함 |

## 이관 행선지

### 요약

- 아래 표는 기본 행선지다.
- 원본을 보고 다른 자리가 낫다고 판단되면 선택지와 근거를 작업 분해 때 사람에게 보여 교차 확인하고 확정표에 남긴다 ([원칙](원칙.md) 「쓰는 법」).
- 원본과 다르게 구현했으면 주석에 「원본은 …, 여기서는」 형태로 이유를 남기는 것이 기본이다.
- 옮긴 계산식 자리에는 원본 식을 주석으로 인용한다.

### 설계

| 무엇 | 어디로 |
|---|---|
| 원본 상수·테이블 | 시트 → JSON → Container ([DataFramework](DataFramework.md)) |
| 공격·스킬·무기 (2종 이상) | 조합 데이터 + 노드 어휘 + 중앙 틱 실행 ([SkillSystem](SkillSystem.md)) |
| 게임 로직·계산 | Manager ([GameFramework](GameFramework.md)) |
| 화면 전이 | GameFlow |
| 창 열고 닫기·표기 갱신 | Management |
| 표기 | Window/Panel/Component. 표기만 ([UIFramework](UIFramework.md)) |

## 패스 ① 닫는 조건

### 요약

- Artist 에게 넘길 수 있는 상태가 되면 닫는다.
- 기본은 `SetData` 를 ①에서 확정하는 것이다. 이유: 주입받을 모양을 모르면 프리팹을 굽지 못해 ②가 헛돈다.

### 설계

- [ ] 데이터 조회가 성공한다 (`AllValues.Count` 가 원본 행 수와 같다)
- [ ] 로직·화면 전이가 렌더 없이 돈다
- [ ] 주입 API 가 선언돼 있다. `SetData(...)` 시그니처와 넘길 필드의 의미가 정해졌다
- [ ] 표기용 스냅샷 구조체의 필드가 내부 코드가 아니라 표기값이다

## 패스 ③

### 요약

- 게임 플로우에 따라 배선한다. Artist 의 ②가 끝난 뒤 다시 받는다. ②까지는 보이기만 하는 상태다.
- 배선 대상 6종 중 하나라도 빠지면 회차가 안 닫힌다.
- 기본은 플로우부터다. 이유: 열리지 않는 창에 값을 넣게 된다.
- 런타임이 넣는 것은 데이터·상태로 갈리는 값뿐인 것이 기본이다. 이유: 프리팹에 있는 보이는 조정값을 코드 상수로 다시 넣거나 에셋 이름·게임 이름으로 갈리는 `if` 를 두면, 다듬을 때 프리팹만 고쳐서는 바뀌지 않는다 ([PD - 대원칙](PD%20-%20대원칙.md) 「속 품질」).

### 규칙

#강제 [원칙 R17](원칙.md#R17) 프리팹을 다시 뜯어야 하면 ③이 고치지 않고 Artist 에게 되돌린다.

#강제 [원칙 R22](원칙.md#R22) 「프리팹이 주인」이면 빌더를 다시 돌려 통째로 굽지 않는다.

### 설계

| 대상 | 하는 일 | 안 하면 |
|---|---|---|
| UI 배선 | 창을 Management 의 `AddWindows()` 에 등록 · 버튼 → `event` → Manager 연결 · `SetData` 실제 호출 | 창이 안 열리거나 값이 안 들어간다 |
| 게임 플로우 배선 | `GameFlow` 전이표대로 열고 닫기. 원본에 없는 창이 안 뜨게 | 없어야 할 창이 한 겹 더 뜬다 ([PD - 게이트](PD%20-%20게이트.md) 「플로우 diff」) |
| 연출 배선 | 연출 컴포넌트에 런타임 파라미터(속도·위상·색·상태) 주입 · 상태 전이와 동기 | 프리팹 기본값으로만 돈다 |
| 게임오브젝트 배선 | 프리팹 로드 경로 · 풀 등록/반환 · 스프라이트 런타임 주입 · 정렬 기준값 | 폴백 도형으로 남거나 풀에서 샌다 |
| 데이터 종속 아트 | 배경·초상·아이콘을 데이터로 갈리게 조회 | 프리팹에 구운 1번 값이 전 구역에 나온다 |
| 지연 로드 아트 | 로드 완료 후 다시 조회 | 열 때 null 이라 평생 폴백 |

배선 순서:

```
가. 창 등록 · 열기/닫기 경로   → 플로우 diff 로 판정 (PD - 게이트 「플로우 diff」)
나. SetData 실호출             → 전수 대조표 빈 칸 0 으로 판정 (UIUX 「화면 하나를 전수 대조표로 연다」)
다. 연출·게임오브젝트 파라미터  → Play Mode 거동으로 판정
```

되돌릴 때 원장에 무엇이 왜 부족한지 적어 넘기는 것이 기본이다.
고칠 곳은 확정표 10-b 가 가른다. 기본은 「프리팹이 주인」이라 프리팹을 열어 고친다. 「빌더가 주인」으로 확정된 게임이면 빌더를 고쳐 다시 굽는다.

## Play Mode 판정

### 요약

- 판정은 Play Mode 다. 정적 캡처로는 배선 대상 6종을 하나도 못 잡는다.

### 설계

```csharp
// 살아 움직이는 것들의 스프라이트 이름을 찍는다 — 같은 이름만 나오면 주입이 안 된 것이다
foreach (Transform t in entityRoot) Log(t.GetComponentInChildren<Image>().sprite.name);
```

- 버튼은 `EventSystem.RaycastAll` 첫 결과가 자기 자신인지 확인한다.
- 상태 전이(정지→재개, 접힘→펼침)는 실제로 눌러 콜백과 상태 변화를 본다.
- 데이터로 갈리는 아트는 데이터를 바꿔 그 자리에서 갈리는지 본다.

## 유니티는 스스로 돌린다

### 요약

- 정본은 [PD - 실행 단계](PD%20-%20실행%20단계.md) 「유니티는 스스로 돌린다」.
- 에디터 작업의 기본은 에디터 다리(`Tools/unity-batch.sh`)다. 재생 검사도 `PLAYMODE=1` 로 다리에서 돌린다.
- 배치모드로 가는 조건은 [SKILL](SKILL.md) 「에디터 러너」.
- 작업이 끝나면 한 항목마다 원장을 갱신하는 것이 기본이다.

### 규칙

#강제 [원칙 R16](원칙.md#R16) 도메인 리로드·재생·정지가 필요하면 사람에게 묻지 않고 직접 실행하고 직접 멈춘다.

#강제 [원칙 R20](원칙.md#R20) 재생 검사 때문에 사람의 에디터를 껐다 켜지 않는다.

### 설계

```
① 재생 멈춤                     ← 착수 전 무조건
② dotnet build Assembly-CSharp.csproj -nologo -v q
   dotnet build Assembly-CSharp-Editor.csproj -nologo -v q
③ Tools/unity-batch.sh 로 에셋 새로고침 → 컴파일 완료 확인(is_compiling=false) → 에디터 코드 실행 → 로그 읽기
④ PLAYMODE=1 Tools/unity-batch.sh … → 거동 확인 → 재생 멈춤
```

- 재생 검사기는 시작할 때 `Application.runInBackground = true` 를 켜는 것이 기본이다. 이유: 포커스 없는 재생이 throttle 된다 (함정: [포커스 없는 에디터 재생의 throttle](함정%20-%20도구%20러너.md#포커스%20없는%20에디터%20재생의%20throttle)).
- 주의: 에디터가 새 코드를 안 먹으면 첫 용의자는 컴파일 에러다. 실패하면 직전 어셈블리를 물고 `isCompiling=False` 로 보인다. `dotnet build` 0 에러를 확인하기 전에 에디터를 의심하면 헛돈다.

## 정답지와 채점기

### 요약

- 정답지는 그래픽이 아니라 숫자다. 렌더 A/B 와는 다른 검사라 둘 다 본다.
- 정답지는 판정이 갈리는 경계를 고르고, 채점기는 그 표를 읽는 일회용 프로그램이다.
- 덤프 diff 채점기는 이미지 비교보다 먼저 돌린다.
- 점수가 오르도록 값을 고르지 않는다 (R5).
- 표와 함정은 [Transfer_Programmer - 정답지와 채점기](Transfer_Programmer%20-%20정답지와%20채점기.md).

## 검증 도구

### 요약

- 만드는 도구는 두 갈래다. 구성하는 도구는 남기고 재는 도구는 이관이 끝나면 지운다.
- 검증 산출물은 유니티 프로젝트 밖(`Tools/Verify/`)에 둔다. 엔진 임시 폴더에 쓰지 않는다.
- 공용 도구 자리에 게임 전용을 남기지 않는다.
- 게임 코드에 검증용 진입점을 두지 않는다.
- 생명주기 표는 [Transfer_Programmer - 검증 도구](Transfer_Programmer%20-%20검증%20도구.md).

## 많이 놓치는 것

### 요약

- 착수 전에 아래 표를 읽는다.
- 전부 「보이지 않아서」 놓치는 것들이다.

### 설계

| 놓치는 것 | 왜 안 보이나 |
|---|---|
| 테이블은 만들었는데 컨테이너가 없다 | 엑셀·JSON·생성 클래스가 다 있어 된 것으로 보인다. `AllValues.Count` 를 찍어야 드러난다 |
| 메인 루프의 정지 게이트 | `if` 한 줄이라 함수 단위 이식에서 사라진다 |
| 스냅샷 구조체에 안 쓰는 필드 | 안 쓰는 필드가 있으면 계약이 틀린 것이다. UI 어딘가에 도달해야 한다 |
| 내부 코드가 화면에 뜬다 | 둘 다 문자열이라 컴파일도 화면도 통과한다 |
| 문구의 파생 표기 (`+42/Lv` → `+420`) | 원문 그대로 나와도 데이터 탓으로 넘어간다 |
| 원본에 없는 상한 | 안전용 clamp 가 원본과 다른 값을 만든다 |
| 조기 반환 가드가 너무 좁다 | 일부 입력만 조용히 건너뛴다 |
| 충돌·크기를 상수로 박기 | 원본 반지름을 그대로 통과시킨다. 눈대중 배율로 맞추면 원본과 갈린다 |
| 원본에 없는 창을 한 겹 더 연다 | 창별 프리팹 점수는 전부 높다 |
| 표의 주소·키 컬럼을 읽는 곳이 없다 | 넣는 줄이 없으면 어떤 데이터 검사도 안 걸린다. 세 장이 같은 그림이라는 것은 숫자로 안 나온다 (함정: [읽는 코드가 없는 표 주소 컬럼](함정%20-%20로직%20데이터.md#읽는%20코드가%20없는%20표%20주소%20컬럼)) |
| 규칙을 추가하자 검사 봇이 죽는다 | 낡은 것은 검사다. 규칙을 더하면 그 규칙 아래서 봇이 살아남는지 같이 본다 (함정: [게임 규칙 추가를 못 따라간 검사 봇](함정%20-%20검사기%20설계.md#게임%20규칙%20추가를%20못%20따라간%20검사%20봇)) |

## 패스 ① 완료 체크리스트

### 요약

- 한 줄이라도 「미확인」이면 완료가 아니다.

### 규칙

#강제 [원칙 R23](원칙.md#R23) 아래에 「미확인」이 한 줄이라도 있으면 완료라고 말하지 않고 남은 목록을 낸다.

### 설계

- [ ] 새 테이블마다 콘크리트 컨테이너가 있고 `AllValues.Count` 가 원본 행 수와 같다
- [ ] `Validate` / `AfterAllTableLoaded` 로 행 수·참조 검증이 걸려 있다
- [ ] 계산이 `double` 이고 `Mathf` · `Random` 직접 호출이 0이다
- [ ] 메인 루프의 dt 클램프 · 정지 게이트가 옮겨졌고 원본 라인이 주석에 있다
- [ ] 화면 전이가 `GameFlow` 한 곳을 지난다
- [ ] 정답지가 있으면 채점을 돌리고, 없으면 A/B 개체 수 판정을 표로 남겼다
- [ ] 주입 API(`SetData`) 시그니처와 필드 의미가 정해졌다 → Artist 에게 넘긴다
- [ ] 표의 모든 컬럼마다 읽는 곳이 한 줄 적혀 있다. 주소·키만이 아니라 문구·플래그 컬럼도 포함한다 (함정: [만든 것을 옮긴 것으로 센 이관율 분자](함정%20-%20판정%20보고.md#만든%20것을%20옮긴%20것으로%20센%20이관율%20분자))
  - [ ] 행도 본다. 표에 있는데 어느 화면에도 안 뜨는 행은 미이관이다
- [ ] 개체를 옮길 때 소스 클래스를 통째로 읽었다. `update()` 의 분기 수와 우리 갈래 수가 같고, `…IntervalMs`·`…DurationMs`·`…Offset`·`…Multiplier` 같은 상수 필드가 전부 표에 있다 (함정: [개체만 세고 행동은 안 센 분모](함정%20-%20판정%20보고.md#개체만%20세고%20행동은%20안%20센%20분모))
  - [ ] 원본에 대한 사실은 절차(굽는/읽는 코드)가 아니라 표에 둔다 (예: 「4컷 중 2~3번만 쓴다」 → 표의 `CutOffset`)
- [ ] 원본이 패스를 여러 번 도는 것은 패스 수까지 옮겼다 (함정: [순수 함수만 잰 골든 테스트](함정%20-%20검사기%20설계.md#순수%20함수만%20잰%20골든%20테스트))
  - [ ] 패스가 캐시를 제자리에서 고치면 훑는 순서까지 같다
  - [ ] 엔진과 원본의 축이 다르면 뒤집는 곳은 한 곳이고, 계산은 전부 원본 좌표로 한다
  - [ ] 그 알고리즘의 골든은 중간값이 아니라 결과물(예: 타일 격자 전 칸)을 잰다

## 패스 ③ 완료 체크리스트

### 요약

- 여기까지 해야 PD 콜이다.
- 한 줄이라도 「미확인」이면 완료가 아니다.

### 규칙

#강제 [원칙 R23](원칙.md#R23) 아래에 「미확인」이 한 줄이라도 있으면 완료라고 말하지 않고 남은 목록을 낸다.

#강제 [원칙 R6](원칙.md#R6) 첫 줄의 못 잰 항목은 통과가 아니라 `미측정(사유)` 다.

#강제 [원칙 R8](원칙.md#R8) 마지막 줄의 100% 는 스스로 선언하지 않고 PD QA 통과 뒤에 선언된다.

### 설계

- [ ] 미측정 항목 0. 못 잰 것은 `미측정(사유)` 로 적고 재측정 대기에 등록했다
- [ ] 내 권한 밖 파일을 건드리지 않았다 ([PD - 실행 단계](PD%20-%20실행%20단계.md) 「역할 기동 규약」 권한표 · [원칙 R17](원칙.md#R17))
- [ ] 플로우 diff 로 「없어야 할 창 · 있어야 할 창 · 순서」가 원본과 같다
- [ ] 「배선 대상 6종」을 Play Mode 에서 확인했다: 모든 창이 `AddWindows()` 에 등록 · `SetData` 실호출로 스냅샷 전 필드가 화면에 도달 · 연출이 런타임 파라미터를 받고 상태 전이와 동기 · 풀 등록/반환과 스프라이트 런타임 주입 · 데이터를 바꾸면 아트가 갈림 · 지연 로드 아트를 표시 시점에 재조회
- [ ] 화면에 내부 코드가 뜨지 않는다 (표기명 사전을 태웠다)
- [ ] 버튼 `RaycastAll` 첫 결과가 자기 자신이다
- [ ] 하위 UI 가 Manager/Management 를 직접 부르지 않는다 (Helper + event)
- [ ] `dotnet build` 두 프로젝트 모두 0 에러, 콘솔 경고 0
- [ ] 원장(`HtmlToUnity_작업내역_<게임명>.md`)에 ①·③ 수행 내용과 회고를 적었다
- [ ] PD 에게 QA 콜을 했다 (100% 선언은 QA 뒤다)
