# SkillSystem

공격·스킬·무기를 데이터 조합으로 만들고 실행은 중앙 틱이 한 번에 돌린다.

## 노트 자리

### 요약

- 방향 노트다. 기본값과 이유를 준다.
- 판단 대상이 아닌 것은 [원칙](원칙.md) 에만 있다.
- 상위는 [PD](PD.md) 다. 사용자는 [Transfer_Programmer](Transfer_Programmer.md) 다.
- 지식 출처는 [Client](Client.md) 와 [Design](Design.md) 이다.

## 적용 조건

### 요약

- 기본은 원본의 공격·스킬·무기를 코드 한 덩어리로 옮기는 대신, 데이터에 적은 모듈 조합으로 만드는 것이다 [사람 확정].
- 실행은 시뮬레이션이 한 번에 돌린다.
- 이유: 스킬이 늘 때 데이터만 는다.
- 판정은 학습 단계에서 한다 ([분석로직 - 학습 판정](분석로직%20-%20학습%20판정.md) 「시스템 축 점검표」의 「공격·스킬」 축).

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 겉 합격 조건: 발동 시각·대상·궤적·피해·상태이상이 원본과 같다.
- 속 합격 조건: 스킬 1종 추가에 C# 수정 0.
- #강제 [원칙 R14](원칙.md#R14) 적용 범위: 이 문서를 넣은 뒤 새로 착수하는 게임부터다. 이미 이관한 게임의 무기 코드는 소급해서 바꾸지 않는다 [사람 확정].

### 설계

| 원본 | 처리 |
|---|---|
| 공격 수단이 2종 이상이고 발동 · 대상 · 발사 · 타격 · 소멸 중 둘 이상을 공유한다 (자동 발동 무기 · 액티브 스킬 · 강화로 붙는 투사체) | 이 문서 |
| 공격 수단이 1종뿐이고 강화로 종류가 늘지 않는다 | 평면형 데이터 + 시뮬 코드. 두 번째 종류가 생기면 이 문서로 옮긴다 |

## 세 층

### 요약

- 층은 조합 데이터 · 노드 어휘 · 실행 셋이다.
- 경계를 넘지 않는다. 이유: 층마다 「바뀌는 때」가 다르다.
- 사람이 고른 기본값이 셋이다. 스킬 조합 + 중앙 틱 · JS 조합 데이터 + Node 익스포터 · 공용 골격이다.

### 규칙

- 다르게 갈 때는 착수 확정 때 근거를 보여 교차 확인한다 ([원칙](원칙.md) 「쓰는 법」).
- #강제 [원칙 R22](원칙.md#R22) 굽기 산출물은 손으로 고치지 않는다. SSOT 에서 고친다.
- 게임 전용 노드는 게임 폴더가 기본이다. 이유: 두 번째 게임이 못 쓰는 것이 공용에 섞인다.

### 설계

```
[조합 데이터]              [노드 어휘]                 [실행]
JS 모듈 조합            →  노드 트리 (BT)           →  중앙 틱 시스템
발동·대상·발사·타격·소멸     ctx 에 값을 쓰고 Launch 가   투사체는 배열 개체
슬롯 · 토큰 · id 치환       읽어 투사체 레코드를 만든다   이동 → 판정 → 소멸 한 루프
굽기가 검증한다             [BTNode] 로 자기 등록        뷰는 배열을 그리기만 한다
```

| 층 | 사는 곳 | 바뀌는 때 |
|---|---|---|
| 조합 데이터 (SSOT) | `Assets/<게임명>/Editor/SkillData/`. 굽는 입력이라 빌드 제외 (`CLAUDE.md` 「로드 규칙」) | 스킬을 추가·조정할 때. C# 안 건드린다 |
| 굽기 산출물 | JSON `Assets/<게임명>/Data/` (DataManager 라벨) · enum `Assets/<게임명>/Scripts/Data/Generated/` | 굽기가 만든다 |
| 익스포터 | `Tools/SkillExporter/` (Node, 게임 무관) | 조립 규칙이 바뀔 때만 |
| 노드 골격 | 공용 `Assets/Scripts/Skill/`. 노드 베이스 · 레지스트리 · 빌더 · 컨텍스트 · 수정자 | 거의 안 바뀐다 [사람 확정. 골격은 공용으로 새로 둔다] |
| 노드 어휘 · 실행 시스템 | `Assets/<게임명>/Scripts/Skill/` | 원본에 새 동작 종류가 있을 때만 |

주의: 골격 공용화는 「두 번째 게임이 요구할 때 승격」(GameFramework)의 예외다.

## 조합 데이터

### 요약

- 스킬 하나는 파일 몇 개 복붙이다.
- 파일 구성 · 조립 규칙 · 굽기 검증은 [SkillSystem - 조합 데이터](SkillSystem%20-%20조합%20데이터.md) 에 있다.
- 리프 대부분은 컨텍스트에 값을 적기만 하고 마지막 Launch 가 그것을 읽는다.
- 굽기 검증을 통과 못 하면 아무것도 안 쓴다.

## 노드 어휘

### 요약

- 노드 어휘는 원본의 동작에서 뽑는다.
- 노드 종류는 enum 원본(`_enums.js`)과 C# 노드 클래스가 한 쌍이다.
- 기본은 원본 공격 수단을 전수로 펴서 센 갈래만큼만 어휘를 만드는 것이다.

### 규칙

- 기본은 클래스에 `[BTNode(ESkillNodeType.Xxx)]` 를 붙여 레지스트리가 리플렉션으로 집는 것이다. 이유: switch 를 손으로 늘리면 고칠 곳이 둘이 된다.
- #강제 [원칙 R23](원칙.md#R23) 받기만 하고 효과가 없는 종류는 `Inert` 로 신고한다. 레지스트리가 미구현으로 보고한다.
- #강제 [원칙 R1](원칙.md#R1) 노드 하나가 원본 동작 하나다. 원본의 조건 분기·순서·예외(조준 유지 · 화면 안 후보 · 첫 명중 대기)를 노드 파라미터로 드러낸다. 「비슷한 유도」로 뭉개지 않는다 (`Client.md` 「「비슷한 유도」로 뭉개기 쉬운 6가지」).

### 설계

전수로 펴는 이유는 장르 교과서 어휘나 원본에 없는 발사 방식을 미리 만들면 검증되지 않는 노드가 남기 때문이다.

| 갈래 | 원본에서 확인할 것 |
|---|---|
| 발동 | 쿨다운 기준(마지막 발사 · 고정 주기) · 공격 시 · 확률 · 첫 발 대기 |
| 대상 | 최근접 · 유지 · 화면 안/전체 · 부채꼴 · 무작위 · 자기 자신 |
| 발사 | 즉발 · 직선 · 포물선 · 곡선 · 유도 · 궤도(시전자 주위 회전) · 개수와 퍼짐 |
| 타격 | 단일 · 범위 · 관통 · 빔 틱 · 연쇄 · 적마다 한 번 여부 · 넉백 |
| 소멸 | 시간 · 명중 수 · 사거리 · 화면 밖 |
| 상태이상 | 종류 · 지속 · 틱 간격 · 중첩 정책 |
| 강화 | 어느 키를 · 덧셈인가 곱셈인가 · 상한 |

## 실행

### 요약

- 조합은 모듈식, 실행은 중앙 틱이다 [사람 확정].
- 투사체·이펙트는 동시에 수백 개가 뜬다.
- 기본은 개체당 컴포넌트 없이 배열 개체를 시스템 하나가 도는 것이다 ([SKILL - 잘못 옮긴 것](SKILL%20-%20잘못%20옮긴%20것.md) 「재생 계층」).
- 이유: 개체당 컴포넌트는 개체 수만큼 비용이 붙는다. 개체 수가 적으면 다른 계층을 착수 확정 때 교차 확인한다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 이동 · 판정 · 소멸의 순서가 원본과 다르면 원본을 따른다.
- #강제 [원칙 R1](원칙.md#R1) 판정은 원본의 모양(원 · 상자)과 크기를 그대로 쓴다 ([Client](Client.md) 「충돌 반지름」).
- #강제 [원칙 R1](원칙.md#R1) 강화 수정자의 덧셈/곱셈과 상한은 원본 규칙을 데이터로 적는다. 참고 구현의 곱셈 고정을 그대로 가져오지 않는다.

### 설계

| 참고 구현이 하던 것 | 여기서는 |
|---|---|
| 풀링 프리팹 하나에 컴포넌트 4개 (데이터 · 이동 · 판정 · 비주얼) | 투사체 = 배열 개체 (위치 · 이전 위치 · 방향 · 속도 · 이동 종류 · 노드 참조 · 명중 기록 · 프레임) |
| 이동 `Update` → 판정 `LateUpdate` 로 순서 고정 | 시스템 하나가 한 스텝 안에서 이동 → 판정(이전 위치→현재 위치 스윕) → 소멸 순으로 돈다 |
| 시전자 컴포넌트가 매 프레임 스킬 트리를 Tick | 시뮬레이션 스텝이 시전자마다 컴파일된 트리를 Tick |
| 비주얼 컴포넌트가 아트 자식을 붙임 | 뷰가 배열을 읽어 풀링된 렌더러를 동기화한다. 아트 프리팹에 스크립트 0 |

- 기본은 노드와 실행 시스템이 시각을 시뮬레이션 시계에서, 난수를 시드 난수에서 받는 것이다 ([GameFramework](GameFramework.md) 「무작위」). 이유: 엔진 시간·엔진 난수를 직접 부르면 같은 입력 두 번 실행 diff 0(G3)과 골든 벡터가 깨진다.
- 시뮬레이션은 유니티 타입 없이 서는 것이 기본이다. 이유: 하네스가 재생 없이 돌린다.
- 강화 수정자는 파라미터 키 단위로 적용하는 것이 기본이다.
- 상태이상은 개체의 데이터 목록이 기본이다 (개체 컴포넌트 · 런타임 `AddComponent` 대신).
- 보이는 조정값(그림 키 · 색 · 방향 · 크기 배율)은 Visual 모듈 데이터에 두는 것이 기본이다 (PD 「속 품질」).

## 검증

### 요약

- 기본 검증 세트다.
- 이유: 깨뜨려 보지 않은 굽기 검사는 막는지 모른다.

### 설계

| 무엇 | 통과 조건 |
|---|---|
| 굽기 검증 | 굽기 검사 표의 결함을 하나씩 일부러 넣어 굽기가 실패하는지 확인했다 |
| 어휘 전수 | 원본 공격 수단 갈래 수 = 노드 종류 수(뺀 것은 이유). 미구현 목록 0 |
| 골든 벡터 | 원본 스킬마다 발동 시각 · 대상 · 궤적 · 피해 · 상태이상 틱을 정답지로 대조 (`07_기대값.md`) |
| 결정성 | 같은 시드 · 같은 입력 두 번 실행 로그 diff 0 |
| 개체 수 | 원본 최대 동시 투사체 수에서 개체당 컴포넌트 0 · 프레임 비용 측정값을 원장에 적는다 |
| 확장성 | 스킬 1종을 실제로 추가해 봤고 C# 수정 0 (Master · Visual 복사만) |
