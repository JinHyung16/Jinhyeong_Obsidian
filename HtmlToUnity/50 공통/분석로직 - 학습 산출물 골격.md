# 분석로직 - 학습 산출물 골격

상위: [분석로직](분석로직.md)

## 자리와 시점

### 요약

- `HtmlToUnityLogic/` 의 기본 자리는 Assets 밖, 원본 옆이다.
- 기본은 학습 단계 착수 직후 골격 전부를 빈 파일로라도 먼저 만드는 것이다.
- 아래 카테고리의 표들을 채우는 것이 학습이다.

### 설계

```
<원본 HTML5 폴더>/
├─ 원본.html
├─ scripts/ …
└─ HtmlToUnityLogic/
    ├─ README.md            ← 목차 + 상태표
    ├─ 00_게임개요.md
    ├─ 01_게임플로우.md
    ├─ 02_시스템_<이름>.md   ← 시스템 수만큼
    ├─ 03_데이터.md
    ├─ 04_UIUX규칙.md
    ├─ 05_연출.md
    ├─ 06_리소스.md
    ├─ 07_기대값.md          ← 정답지의 유일한 자리
    └─ 99_원본지도.md
```

- 자리의 이유: 원본과 같이 갱신되고 유니티 임포트에 안 섞인다.
- 먼저 만드는 이유: 파일이 없으면 「이 게임엔 없다」로 넘어간다.
- `02` 의 개수는 [분석로직 - 학습 판정 「시스템 축 점검표」](분석로직%20-%20학습%20판정.md#시스템%20축%20점검표) 가 정한다.

## README

### 요약

- `README.md` 는 목차 겸 상태표다.
- 원본의 기획서와 사양서는 ②규약·사양이다. 이 문서들은 ①원본 코드 실측 기록이다.

### 규칙

#강제 [원칙 R3](원칙.md#R3) 원본의 기획서·사양서나 이 문서들이 원본 코드와 어긋나면 원본 코드가 이긴다.

### 설계

````markdown
# HtmlToUnityLogic — 학습 단계 산출물

원본을 실제로 돌려 보며 파악한 것을 정리한다. 규격은 `분석로직.md` 「HtmlToUnityLogic/」.
이관 담당자는 이 문서들을 근거로 작업한다. 최종 판정은 언제나 원본 코드다.

| 파일 | 담당 | 내용 | 회차 | 상태 |
|---|---|---|---|---|
| `00_게임개요.md` | Design | … | 0 | 미작성 |
| …
````

## 00 게임개요

### 요약

- 담당은 Design 이다.
- 한 판의 흐름 · 재화 · 진행 체인 · 저장되는 것을 적는다.

### 설계

````markdown
## 한 판의 흐름
시작 → … → 종료.  (원본에서 실제로 플레이해 본 순서로)

## 재화
| 재화 | 획득처 | 소비처 | 표기 | 원본 위치 |

## 진행 체인
| 단계 | 해금 조건 | 열리는 것 | 원본 위치 |

## 저장되는 것
| 키 | 자료형 | 초기값 | 원본 위치 |
````

## 01 게임플로우

### 요약

- 담당은 Client 다.
- 이 문서의 중심은 「무엇이 안 열리는가」다.
- 이유: 원본에 없는 창이 한 겹 더 뜨는 결함은 프리팹 대조로 안 잡힌다 (PD 「플로우 diff 를 프리팹 대조보다 먼저」).

### 설계

````markdown
## 화면 전이 그래프
(화면 → 화면. 조건과 함께)

## 버튼 전수 — 화면별로 한 표씩
| 화면 | 버튼(셀렉터) | 누르면 열리는 것 | 닫는 방법 | 원본 위치 |

## 겹침 순서 (z-index)
| 창 | z-index | 출처 | 비고(원본 명시 / 파생) |

## 메인 루프
| 항목 | 값 | 원본 위치 |
| dt 상한 | | |
| 정지 게이트 조건 전부 | | |
| 그리기는 계속 도는가 | | |
````

```bash
grep -n "addEventListener\|onclick=\|data-act" 원본.html    # 버튼 전수
grep -n "function setScreen" -A 20 원본.html                 # 화면 전이
grep -n "_loopBody\|requestAnimationFrame" -A 6 원본.html    # 메인 루프
grep -n "z-index" 원본.html                                   # 겹침 순서
```

## 02 시스템

### 요약

- 파일 이름은 `02_시스템_<이름>.md` 이고 시스템마다 한 장이다.
- 담당은 Design 과 Client 다.
- 계산식은 원본 코드를 그대로 붙인다. 요약하지 않는다.

### 설계

````markdown
## 무엇인가
(한 문단)

## 상태
| 변수 | 자료형 | 초기값 | 저장되나 | 원본 위치 |

## 계산식
(원본 코드를 그대로 붙인다. 요약하지 않는다)
```js
// 예: 원본.html 2866~3138. 라인은 인용할 때마다 grep 으로 재확정한다
…
```
URL 제공형이면 번들 소스의 해당 부분을 앵커(검색어)와 함께 붙인다. 난독화된 이름은 두고 옆에 해석을 단다.
소스가 없으면 제목에 「관측으로 세운 가설」이라 적고 규칙 등급을 ④로 둔다
(PD 「근거 등급」 — 값의 등급과 규칙의 등급은 따로다).

## 파생·폴백
| 항목 | 원본 표기 | 폴백값(`||` 뒤) | 원본 위치 |

## 이 시스템이 그리는 것
| 요소 | draw 함수 | 원본 위치 |
````

## 03 데이터

### 요약

- 담당은 Design 이다. 이것이 곧 시트 설계도다.
- 기본은 테이블마다 행 수를 세어 적는 것이다.
- 이유: 컨테이너 어설션과 게이트 G1 의 통과 증명이 된다. R7 을 증명하는 기본 방법이다.

### 설계

````markdown
## 테이블 전수
| 원본 객체/배열 | 행 수 | 키 | 컬럼(키·자료형) | 읽는 코드 | 시트 이름(예정) |

## 표기 사전 (내부 코드 → 표기명)
| 원본 사전 | 역할 | 행 수 |

## 문구의 파생 규칙
| 규칙 | 정규식/함수 | 원본 위치 | 예시 (입력 → 출력) |
````

- 담당은 UI/UX 다.
- 좌표계 · 색 변수 · 타이포 · 공통 컴포넌트 · 화면별 영역 표를 적는다.

### 설계

````markdown
## 좌표계
| 항목 | 값 |
| 논리 해상도 | |

| 변수 | 값 | 용도 |

## 공통 컴포넌트
| 클래스 | 구성 요소 | 쓰이는 화면 |

## 화면별 영역 표 — 화면마다 한 표
| 영역 | 위치·크기 | 자식 요소 | 원본 셀렉터 |
````

## 05 연출

### 요약

- 담당은 FX 다. 전수표가 본체다.
- `animation` · `:hover` · UI 연출은 정적 캡처에 안 찍힌다. 기본은 코드에서 뽑아 창마다 채우는 것이다.
- 「UI 연출」 표가 비면 이관율 분모에서 그 갈래가 빠진다.
- 전수 대조표는 「있나」만 세고 「움직이나」는 안 묻는다.

### 설계

````markdown
## 그리기 파라미터 전수표
| 위치(라인) | 대상 | lineWidth | shadowBlur | globalAlpha | 합성 모드 | 색 |

## 애니메이션
| 셀렉터 | animation | keyframes | 주기 | 이징 |

## :hover
| 셀렉터 | 무엇이 바뀌나 |

## UI 연출 — 창마다 한 줄 (정지 캡처에 원리적으로 안 찍힌다)
| 창 | 디머(색·α) | 버튼 idle 연출(펄스 식·주기) | 호버(배율·틴트) | 눌림 | 등장/퇴장 트윈 | 근거 |

## 엔티티 레이어 수
| 엔티티 | 원본 fill/stroke/drawImage 호출 수 | 층 구성 |
````

캔버스나 엔진 게임이면 CSS 가 아니라 업데이트 루프 안의 배율 식을 찾는 편이 맞다.

```bash
grep -n "lineWidth\|shadowBlur\|globalAlpha\|globalCompositeOperation" 원본.html
grep -no "animation:[^;]*;" 원본.html | sort -u -t: -k3
grep -no "[^{]*:hover{[^}]*}" 원본.html
grep -no "pointerenter\|Math.sin(\|alpha:\.[0-9]\|scale.set(" 번들.js | head   # 엔진 게임의 UI 연출
```

## 06 리소스

### 요약

- 담당은 FX 와 UI/UX 다. 두 목록이다.
- 기본은 ②를 ①과 함께 채우는 것이다.
- 이유: 미루면 단색 박스가 남고, 단색 박스는 미완성이다.

### 설계

````markdown
## ① 존재하는 리소스
| 파일 | 크기 | 쓰이는 곳 | 정적/데이터 종속 |

## ② 제작해야 하는 리소스 (CSS·canvas 로 그리고 있다)
| 무엇 | 원본이 그리는 방법 | 원본 위치 | 필요 크기 | 색이 데이터로 갈리나 |
````

## 07 기대값

### 요약

- 담당은 Client 다. 정답지의 유일한 자리다.
- 「입력 → 기대 출력」 표다. 채점기는 이 표를 읽기만 한다.
- 회차용 채점기는 회차 끝에 지운다. 게임별 하네스와 회귀 검사는 이관 끝에 지운다. 이 표는 남는다 ([Transfer_Programmer - 검증 도구](Transfer_Programmer%20-%20검증%20도구.md) 「검증 산출물 자리」).

### 규칙

#강제 [원칙 R5](원칙.md#R5) 점수를 근거로 정답지를 고치지 않는다. [파생]은 정답지가 아니다.
#강제 [원칙 R6](원칙.md#R6) 미측정은 채점에서 빼지 않는다. 남아 있으면 전 검사 통과라도 완료가 아니다.
#강제 [원칙 R9](원칙.md#R9) 비결정은 원본 자신이 갈린다는 실측으로만 빼고 「제외 N건」을 리포트에 찍는다.

### 설계

| 열 | 적는 것 |
|---|---|
| 입력 | 다시 넣을 수 있는 재현 가능한 형태 |
| 기대 출력 | 원본 실측값 |
| `n` | 잰 횟수. `n=1` 은 표본이다. `-1` 은 소스 직독 |
| 출처 구분 | [소스] · [관측] · [파생] (PD 「근거 등급」). [파생]의 지위는 R5. [소스]가 오면 [관측]으로 되돌리지 않고 실측치는 확인 근거로 남긴다 |
| 기준점 | 시각·좌표의 원점. 표마다 다르면 섞여도 안 보인다 |
| 판정 허용치 | ±얼마까지 통과인가 |

| 갈래 | 뜻 | 채점 |
|---|---|---|
| 정답지 | 원본이 같은 입력에 같은 답을 낸다 | 센다 |
| 비결정 | 원본 자신이 갈린다 (n≥3 으로 확인) | 빼되 「제외 N건」을 리포트에 찍는다 (R9) |
| 미측정 | 아직 안 쟀다 | 빼지 않는다 (R6) |

행을 「비결정」으로 옮기는 기본 방법은 원본을 n≥3 회 다시 재서 갈리는 것을 보이는 것이다.

## 99 원본지도

### 요약

- 담당은 전원이다.
- [공통절차 - 원본 코드 읽기 「실측 지도」](공통절차%20-%20원본%20코드%20읽기.md#실측%20지도) 의 구간표를 그 프로젝트 것으로 채운다.
- 기본은 grep 으로 확정한 값만 적는 것이다.

### 설계

````markdown
## 라인 지도
| 라인 | 담당 | 내용 |

## id / 클래스 → 실제 화면 대응표
| 원본 id | 실제 화면 | 비고 |

## 모듈 파일
| 파일 | 담당 |
````

- 주의: 원본 id 가 화면 이름과 반대이거나 무관할 수 있다. 그래서 대응표를 같이 적는 것이 기본이다.
- 실측 심화 기법은 [공통절차 - 원본에서 값 캐기](공통절차%20-%20원본에서%20값%20캐기.md).
