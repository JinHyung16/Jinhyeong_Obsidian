# 공통절차 - 원본에서 값 캐기

상위: [공통절차](공통절차.md)

## 쓰는 때

### 요약

- URL 제공형 심화다. [PD - 원본 형태](PD%20-%20원본%20형태.md) 「런타임 직독」의 다음 단계다.
- 좌표로 안 풀리는 물음이 대상이다. 언제 무엇을 했나 · 자산의 원래 색과 모양 · 도달할 수 없는 입력값 · 무작위의 경계다.
- 기본은 관찰을 늘리지 않고 보는 자리를 바꿔 푸는 것이다.

## 여는 순서

### 요약

- ⓪-a 먼저 열어서 해 본다. 소스를 읽는 것이 플레이를 대신하지 않는다.
- 증상은 사양인지 결함인지부터 가르는 것이 기본이다.
- 근거 절은 [PD - 원본 형태](PD%20-%20원본%20형태.md) 「원본 형태 판정」이다.

### 규칙

#강제 [원칙 R1](원칙.md#R1) URL 로 온 원본은 심판이다. 원본에도 있는 증상은 사양이다(함정: [그림에서 추정한 9슬라이스 인셋](함정%20-%20원본%20관측.md#그림에서%20추정한%209슬라이스%20인셋)).

### 설계

| 언제 | 무엇부터 |
|---|---|
| 사람이 증상을 말했다 (「깜빡인다」·「이상하다」) | 원본을 열어 같은 자리를 해 본다. 그다음 소스 |
| 사람이 값을 물었다 | 소스·덤프 |

- 게임은 대개 교차 출처 iframe 이다. 바깥에서 JS 훅과 픽셀 읽기가 안 되고, 프레임 URL 직접 접속은 막힌다. 서비스 페이지로 열어 키·클릭과 눈 확인으로 증상을 가른다.
- 값은 ⓪ 번들을 받아 읽는다. 자산은 파일 URL 로 받아 바이트로 잰다(함정: [브라우저 캔버스로 읽은 원본 그림의 색 왜곡](함정%20-%20아트%20굽기.md#브라우저%20캔버스로%20읽은%20원본%20그림의%20색%20왜곡)).
- 「플레이로 증상 가르기」 → 「소스로 규칙 캐기」 → 「우리 화면 재서 대조」는 답하는 물음이 달라 서로 대신하지 못한다.

## 번들 소스

### 요약

- ⓪ 번들 소스를 받는 것이 ①~⑤ 전부보다 먼저다.
- 「언제·왜」는 [PD - 원본 형태](PD%20-%20원본%20형태.md) 「번들 소스」.

### 규칙

#강제 [원칙 R11](원칙.md#R11) 번들에서는 규칙만 읽고 에셋은 받지 않는다.

### 설계

| 단계 | 어떻게 |
|---|---|
| 스크립트 URL 수집 | 게임 프레임 안에서 `performance.getEntriesByType('resource')` 로 `*.js` 를 모은다. 동적 `import()` 청크는 한 판을 돈 뒤 다시 모은다 |
| 프레임 안에서 받는다 | 게임 프레임 컨텍스트에서 `fetch` 하고(다른 출처면 차단) 청크 이름·해시 그대로 로컬에 저장한다 |
| 앵커 grep | 관측한 값·문자열(목표 배열 · 로케일 키 · 개체 이름 · 텍스처 이름)을 찾는다. 매치 앞뒤 2~3KB 가 그 시스템의 클래스다 |
| 이름 복원 | 난독화 이름은 구조로 읽고 `99_원본지도.md` 소스 지도에 적는다 |
| 기록 | 「원본 위치」 = `[소스] <청크>:<앵커>`. 줄번호 대신 앵커를 적는다 |

- 소스가 있어도 실측은 남긴다. 둘이 갈리면 번들 버전 차이를 먼저 의심한다. 그래서 청크 해시를 기록한다.
- 숫자는 관측치와 맞물린 앵커가 있을 때 줍는 것이 기본이다. R3 을 증명하는 기본 방법이다.

## 후킹

### 요약

- ① 순서와 횟수는 후킹으로 읽는다. 관찰로는 못 간다.
- 시계열 관찰로 반영하면 가설을 코드에 박는다.
- 기본은 엔진 메서드를 감싸(prototype/속성 교체) 호출 시각 · 인자 · 횟수를 기록하는 것이다.

### 설계

- 한 틱 안의 실행 순서를 읽는다. 시뮬레이션 다음이 이벤트 실행인가 반대인가다.
- 한 프레임의 실행 횟수를 읽는다. 고정 스텝 · 누적기 · 따라잡기다.
- 인자를 읽는다. 스텝 간격이 프레임 간격 그대로인가, 클램프가 걸리나다.
- 후킹은 「무엇을 했나」에 답하고 원본을 바꾸지 않는다. 원래 함수를 그대로 부른다.

## 자산 실측

### 요약

- ② 색 · 모양 · 크기는 소스 자산을 꺼내서 잰다.
- 화면 색 = 자산 색 × 런타임 착색이다.
- 기본은 원본 이미지 파일을 내려받아 파일 바이트를 읽는 것이다.

### 규칙

#강제 [원칙 R7](원칙.md#R7) RGB 나 알파 한 축만 본 지표로 닫지 않는다. 원본 파일과 결과물 바이트로 닫는다(함정: [색 키에서 빠진 알파 축](함정%20-%20아트%20굽기.md#색%20키에서%20빠진%20알파%20축) · [브라우저 캔버스로 읽은 원본 그림의 색 왜곡](함정%20-%20아트%20굽기.md#브라우저%20캔버스로%20읽은%20원본%20그림의%20색%20왜곡)).

### 설계

아틀라스(`main.png` 등)는 Pillow 같은 파일 디코더로 열고 좌표는 `main.json` 에서 얻는다. 브라우저는 「어디에 무엇이 있나」까지만 쓴다.

| 피할 것 | 기본 |
|---|---|
| 캡처에서 색을 집는다 | 소스 텍스처를 꺼내 픽셀을 센다 |
| 캔버스 `getImageData` 로 뜬다 | 파일 바이트를 읽는다. 캔버스는 저알파 RGB 를 왜곡한다 (함정: [브라우저 캔버스로 읽은 원본 그림의 색 왜곡](함정%20-%20아트%20굽기.md#브라우저%20캔버스로%20읽은%20원본%20그림의%20색%20왜곡)) |
| 알파를 있다/없다로만 뜬다 | 알파를 색과 별개의 축으로 뜬다 (함정: [색 키에서 빠진 알파 축](함정%20-%20아트%20굽기.md#색%20키에서%20빠진%20알파%20축)) |
| 반경별 알파 평균으로 모양을 판단 | 마스크를 그려서 본다 |
| 굽고 끝낸다 | 구운 결과를 소스와 픽셀 대조(IoU)해서 닫는다 |

- 단색 마스크로 나오면 결과 색을 여러 벌 굽기보다 착색 기전을 옮기는 편이 낫다.
- 인스턴스가 0이면 클래스에도 자산 목록이 없다. 사건 목록(성공 · 실패 · 전환 · 최초 진입)을 만들고 사건 프레임 훅으로 참조를 붙잡아 사라진 뒤 꺼낸다.
- 가속 캔버스는 픽셀 읽기가 전부 0일 수 있다. 읽을 수 없는 것이지 검은 화면이 아니다. 그때는 스크린샷으로 재는 편이 낫다.
- 다 굽고 나면 원본 파일과 바이트 단위로 같은지로 닫는 것이 기본이다. RGB 나 알파 한쪽만 보면 다른 쪽이 틀린 채 100% 가 나온다.

## 자산 단계

### 요약

- 자산은 네 단(段)으로 뜬다.
- 어디까지 갈지는 사람이 정한다.
- 기본은 착수 질문으로 묻고 확정표에 적는 것이다.

### 규칙

#강제 [원칙 R12](원칙.md#R12) 어느 단까지 갈지는 사람이 정한 정책이다. 측정은 보고하고 결정을 따른다.

### 설계

| 단 | 무엇을 뜨나 | 닫히는 것 | 열려 있는 것 |
|---|---|---|---|
| 1 | 존재·주소 | 빠진 자산 | 크기·모양·색 |
| 2 | 규격. 시트/컷 크기 · 컷 수 · fps · 표시 배율 | 컷 수·크기 | 그림 자체 |
| 3 | 형태·색. 실루엣 마스크 · 팔레트(색+비중) · 채움률 | 윤곽과 색조 | 안을 무엇으로 칠했나 |
| 4 | 픽셀 배치. 팔레트 인덱스맵 | 그림이 같은가 | 없음 |

- 3단 만점이어도 픽셀은 틀릴 수 있다([지표 선정](공통절차%20-%20캡처와%20덤프.md#지표%20선정)).
- 작은 스프라이트(≤32px)는 3단과 4단 사이에 중간이 없다.
- 4단으로 갔으면 「재제작」이라는 말 대신 의도된 차이 목록에서 그 줄을 지운다.
- 측정이 사람이 정한 단과 달라 보이면 보고로 끝낸다(함정: [사람이 없애라 한 버튼 둘레 띠를 측정으로 되살린 일](함정%20-%20사람%20권리%20안전.md#사람이%20없애라%20한%20버튼%20둘레%20띠를%20측정으로%20되살린%20일)).

## 입력값 폴링

### 요약

- ③ 입력값은 대리 축으로 겨냥하지 않는다.
- 실제 값을 폴링해서 끊는다.

### 설계

```
하지 않는다: 누른 시간 T 를 계산해서 T 만큼 누른다      → 도달 값이 흔들린다
한다:        누르는 동안 실제 값을 매 프레임 읽다가      → 원하는 값에서 끊는다
             목표에 닿는 순간 입력을 끝낸다
```

- 되먹임 보정에는 이상치 게이트를 두는 것이 기본이다. 이유: 포화 표본 한 발이 뒤 시행을 망친다.
- 도달 값이 이산 격자일 수 있다. 격자 사이 값은 「도달 불가」이고 정답지 값을 격자 위로 옮긴다. 격자의 시작과 간격을 먼저 잰다.

## 무작위 경계

### 요약

- ④ 무작위는 경계를 직독한다. 표본으로 유도하지 않는다.
- 엔진이 파라미터를 식으로 들고 있으면 기본은 수천 번 호출해 최소 · 최대와 서로 다른 값의 개수(distinct)를 세는 것이다.

### 설계

- min/max 만 보면 오독한다. −100~+100 에 흩어져도 distinct 가 2 면 둘 중 택일이다.

## 저작값 확인

### 요약

- ⑤ 그 전에 저작값이 적혀 있는지부터 본다.
- ①~④ 는 저작값을 못 찾았을 때 쓴다.

### 설계

- 이벤트 시트 · 스크립트 · 씬 데이터에 적힌 상수가 답이고 부호와 단위까지 나온다.
- 실측값을 시트 상수와 교차 확인하면 오귀속도 잡힌다.

## 사건 프레임 덤프

### 요약

- ⑥ 스크린샷 대신 그 프레임의 값을 뜬다.
- 규격은 [분석로직 - 사건 프레임 덤프](분석로직%20-%20사건%20프레임%20덤프.md).

### 설계

| 단계 | 어떻게 |
|---|---|
| 기록기 | 후킹으로 루트를 잡고 rAF 마다 가벼운 상태(표식 문구 · 주인공 좌표/틴트/알파 · 개체 수 · 포인터)를 읽는다 |
| 사건 판정 | 표식 묶음(문구 집합 + 틴트 + 개체 존재)을 한 줄 키로 만들고 키가 바뀌면 전체 덤프. 고정 시각(3·12·30·60s…)도 몇 개 |
| 전체 덤프 | 노드마다 `getGlobalPosition` · `worldTransform`(배율) · `worldAlpha` · 가시성(부모 사슬) · 텍스처 이름(아틀라스 사각형 역추적) · 문구 · 폰트 크기 → TSV 한 줄. 보이는 것만 들여쓰기 트리로 |
| 시계열 | 움직이는 값(주인공·카메라·버튼 배율)은 매 프레임 한 줄. 앵커는 프레임 수 |
| 봇 | 사람이 하는 조작만. 위협 회피 › 보석 › 포인터 목표. 창은 사람처럼 누른다(카드 → 선택, 부활, 확인). 경로 분기(「첫 사망에 거절」)는 인자로 준다 |
| 저장 | 20초마다 파일로 내려 쓴다 |

- 움직이는 것은 두 번 플레이하는 것이 기본이다. 첫 플레이로 주기를 재고, 두 번째에 주기로 계산한 프레임 수만큼 뜬다. 10 프레임은 밑바닥이지 기준이 아니다([분석로직 - 사건 프레임 덤프 「두 번 플레이」](분석로직%20-%20사건%20프레임%20덤프.md#두%20번%20플레이)).
- 우리 쪽도 재생 검사기가 같은 사건에서 원본 논리 좌표로 떠 `frames/` 와 줄 단위 diff 한다. 이미지 비교는 그 뒤 눈 확인이다.

## 도달 설계

### 요약

- 덤프는 도달한 상태만 준다. 그래서 도달을 설계한다.
- 조건부 개체와 상태는 거기까지 가지 않으면 안 보이고 이관율에도 안 잡힌다(함정: [조건부로만 나오는 요소를 없다고 적은 분석](함정%20-%20판정%20보고.md#조건부로만%20나오는%20요소를%20없다고%20적은%20분석)).

### 규칙

#강제 [원칙 R6](원칙.md#R6) 도달 못 한 상태는 「없음」이 아니라 미측정이다.

### 설계

1. 소스의 상태 전환(모드·퀘스트 단계·화면 전이)을 `grep` 해 상태 목록을 전수로 만든다. 목록은 관측이 아니라 소스로 센다.
2. 상태마다 도달 방법(조건 · 걸리는 시간 · 선행 상태)을 한 줄 적는다.
3. 봇이 그 경로를 밟게 한다.
4. 실패하면 정지 여부 · 남은 거리 · 체력 · 경과를 같이 찍는다.

- 봇은 게임을 멈추는 창(레벨 업·부활·보상)을 치운다. 안 누르면 시뮬이 한 틱도 안 돈다.
- 같은 코드로 두 번 돌린 결과가 다르면 도달을 먼저 본다(함정: [사람 마우스에 흔들리는 재생 검사](함정%20-%20검사기%20설계.md#사람%20마우스에%20흔들리는%20재생%20검사)).
- 맞추는 값의 기본은 앵커 좌표가 아니라 경계 상자(중심 cx, cy · 크기 w, h)다. 글자는 글리프 경계로 재고 서체가 다르면 높이만 본다.

| 무엇 | 허용 오차 (예시. 프로젝트가 정한다) |
|---|---|
| 중심 좌표 | ±1.5 논리 px |
