# 분석로직 - 사건 프레임 덤프

상위: [분석로직](분석로직.md)

## 덤프 규격

### 요약

- `frames/` · `motion/` · `paths.md` 는 이미지 대신 게임이 쓴 숫자를 남긴다.
- 분석의 정본은 원본이 그 프레임에 들고 있던 값이다.
- 씬 그래프(노드 · 좌표 · 배율 · 알파 · 텍스처 · 문구), 후킹 시계열, 버퍼(정점·UV)를 텍스트로 뜬다.
- 기본은 이미지를 마지막 눈 확인 한 장으로만 쓰는 것이다.
- 이유: 인상만 남고 토큰이 5~10배이며 오버레이 아래 색을 자산색으로 오독한다 (함정: [디머 아래에서 잡은 바탕색 팔레트](함정%20-%20아트%20굽기.md#디머%20아래에서%20잡은%20바탕색%20팔레트) · [스크린샷을 분석 입력으로 삼는 함정](함정%20-%20원본%20관측%20-%20상태%20직독.md#스크린샷을%20분석%20입력으로%20삼는%20함정)).

### 규칙

#강제 [원칙 R11](원칙.md#R11) `art_measure.tsv` 에는 규격만 뜨고 픽셀은 뽑지 않는다.

### 설계

```
<원본폴더>/HtmlToUnityLogic/
├─ frames/                    ← 사건 프레임마다 한 쌍
│   ├─ 012_38210ms_event_레벨 업!.tsv        노드 표 (id parent depth name x y sx sy alpha visible tint frame font text)
│   └─ 012_38210ms_event_레벨 업!.tree.txt   들여쓰기 트리 (보이는 것만 · 첫 줄에 label·시각·직전 상태)
├─ motion/                    ← 시계열 표 (t frame heroX heroY tint alpha enemies gems nearest …)
├─ paths.md                   ← 경로 지도 (아래)
└─ art_measure.tsv            ← 프레임별 크기 · bbox · 앵커 · 팔레트(hex·비율) · 행별 폭 — 픽셀은 뽑지 않는다(복사)
```

| 규칙 | 내용 |
|---|---|
| 사건으로 고른다 | 상태가 바뀐 프레임(창 열림/닫힘 · 피격 · 회복 · 폭발 · 퀘스트 전이)과 고정 시각 몇 개만. 판정 키 「표식 문구 + 틴트 + 개체 존재」가 바뀌는 순간이 사건이다 |
| 형식은 자료 모양대로 | 고정 열 표는 TSV, 계층은 들여쓰기 트리, 들쭉날쭉한 필드만 JSON. XML 은 피한다(토큰 2.5배) |
| 좌표는 원본 논리 좌표 | 논리 해상도(확정표 3-d) 기준 전역 좌표·배율(worldTransform). 우리 덤프도 같은 좌표계로 떠서 표 대 표로 diff |
| 경로를 전부 밟는다 | 성공 · 실패 · 중간 이탈 · 분기(광고 수락/거절)마다 플레이해서 뜬다. 봇은 사람의 조작(회피 · 줍기 · 포인터 따라가기)만 한다 |
| 판마다 다른 것을 갈라 적는다 | 자리가 판마다 다른 개체(절차 생성물 · 적 · 드랍 · 떠오르는 문구 · 가장자리 표식)는 크기와 존재만 맞추고 곡선은 motion 으로 본다 |
| 사건이 겹치면 겹친 창은 뺀다 | 한쪽만 모달이 떠 있으면 그 창 아래 노드를 양쪽에서 빼고 비교한다 |
| 한 프레임으로 판단하지 않는다 | 움직이는 것은 프레임마다 다르다. [두 번 플레이](분석로직%20-%20사건%20프레임%20덤프.md#두%20번%20플레이)가 기본 방법이다 |

- 씬 그래프가 없는 원본(즉시 모드 캔버스)은 `drawImage`/`fill` 호출 인자를 후킹해 같은 표로 만드는 편이 낫다.
- 코드로 그리는 것(도형 · 파티클 · 셰이더)은 파라미터만 남기고 생김새만 이미지 한 장으로 확인한다.

## 두 번 플레이

### 요약

- ① 몇 프레임이 필요한지 재고 ② 그만큼 뜬다.
- 기본은 프레임 수를 주기에서 계산하는 것이다.
- 10 프레임은 밑바닥이지 기준이 아니다.

### 설계

| 차례 | 무엇을 하나 | 산출 |
|---|---|---|
| ① 파악 플레이 | 화면마다 움직이는 것과 주기(컷 fps · 맥동 주기 · 채워지는 시간 · 깜빡임 간격)를 뜬다 | 개체별 주기표 |
| ② 분석 플레이 | 주기표에서 계산한 프레임 수로 다시 뜬다 | `frames/` · `motion/` |

| 무엇 | 필요한 프레임 |
|---|---|
| 컷이 도는 개체 | 두 바퀴 (한 바퀴 = `컷수 ÷ fps` 초). 한 바퀴만 보면 마지막 컷이 빈 것을 놓친다 |
| 주기 연출 (맥동 · 부유 · 회전) | 한 주기 이상. 최소·최대가 둘 다 나와야 한다 |
| 차오르는 것 (링 · 바 · 페이드) | 다 찰 때까지. 프레임 수가 아니라 「다 찼나」가 종료 조건이다 |
| 상태 깜빡임 (무적) | 간격의 세 배 이상. 켜짐·꺼짐·켜짐이 나와야 한다 |

- 사례: 이동 컷 다섯 중 마지막이 비었는데 모든 검사가 통과했다. 한 바퀴(0.42초)를 안 봤다 (함정: [칸 수와 자리 보폭이 달라 빈 시트 꼬리](함정%20-%20아트%20굽기.md#칸%20수와%20자리%20보폭이%20달라%20빈%20시트%20꼬리)).

## 경로 지도

### 요약

- `paths.md` 의 앞 절반이다.
- 경로마다 시작과 끝 · 사건 순서 · 봇 조작 · 결말을 적는다.

### 규칙

#강제 [원칙 R6](원칙.md#R6) 빠진 경로의 결말 창·연출은 미측정이고 이관율에서 0건이다.

### 설계

````markdown
| 경로 | 시작 → 끝 | 사건 순서 (frames/ 번호) | 봇 조작 | 결말 |
| 성공 | 시작 → 과제 완료 | 003 시작 → 012 레벨업 → … → 087 과제 완료 | 포인터 따라가기 · 자동 부활 | 「과제 완료」 창 |
| 실패-거절 | 시작 → 첫 사망 → 「아니요」 | … | 첫 사망에 거절 | (원본이 가는 곳) |
````

## 상태 전수표

### 요약

- `paths.md` 의 뒤 절반이고 경로 지도와 한 쌍이다.
- 「무엇이 아직 안 보였나」를 적는다.
- 기본은 소스의 상태 전환을 grep 해 전수로 적는 것이다. 이유: 조건부 상태는 봇이 그 경로를 밟아야 보여서, 관측으로 세면 빠진다.

### 규칙

#강제 [원칙 R6](원칙.md#R6) 도달 「아니오」는 없음이 아니라 미측정이고 이관율에서 0건이다.

### 설계

````markdown
| 상태 | 언제 나오나 | 도달 | 뜬 프레임 |
| 개체 A — 대기 모드   | 최초 배치부터            | 예 | 004 |
| 개체 A — 이동 모드   | 조건 X 를 만족한 뒤       | 예 | 031 |
| 개체 B (무리 N명)    | 퀘스트 단계 3 에서만      | 아니오 | — (미측정) |
````

- 도달 「아니오」 행은 「재측정 대기」로 올린다.
- 도달 설계는 [공통절차 - 원본에서 값 캐기 「도달 설계」](공통절차%20-%20원본에서%20값%20캐기.md#도달%20설계) 가 정본이다.

## 덤프 열 읽기

### 요약

- 덤프의 열은 셋 같이 읽는다. 크기만 보면 두 모드가 같아 보인다.
- 덤프 한 줄의 `frame`(원본 컷 크기) · `sx/sy`(배율) · `w/h`(그려진 크기) 관계가 그리는 방식이다.

### 설계

| 관계 | 뜻 | 엔진에서 |
|---|---|---|
| `w == frame × sx` | 정수배 확대. 테두리도 굵어진다 | 스프라이트 + 배율 |
| `w != frame × sx` | 9슬라이스. 모서리는 그대로, 가운데만 늘어난다 | 슬라이스 + 인셋 |

- 주의: `w/h` 만 보면 구별이 안 된다. 확대를 9슬라이스로 만들면 테두리가 실오라기가 된다.

## 덤프에 없는 것

### 요약

- 덤프에 원리적으로 없는 것이 있다. 그건 소스에 있다.
- 덤프는 속성만 뜨고 생성자 인자는 안 나온다.
- 기본 캐는 법은 생성자 이름으로 전수로 훑고 호출부 문맥을 같이 꺼내는 것이다.

### 규칙

#강제 [원칙 R4](원칙.md#R4) 빈칸을 공식으로도 그림 실측으로도 메우지 않는다. 못 캤으면 못 캤다고 적는다.

### 설계

| 덤프에 없는 것 | 어디 있나 | 안 캐면 |
|---|---|---|
| 9슬라이스 인셋 | `NineSlicePlane({leftWidth: …})` | 테두리 두께가 다르다 |
| 자리마다 다른 인셋 | 호출부마다 | 카드와 버튼이 같아진다 |
| 9슬라이스가 아닌 것 | 생성자 호출이 없다 | 안 늘어날 것을 늘린다 |
| 값의 식 | `updateLayout()` 류 | 화면비가 바뀌면 어긋난다 |

- 호출부 문맥을 같이 꺼내면 같은 텍스처의 다른 인셋(일반 버튼 15 / 카드 10)이 갈린다. 목록에 없는 텍스처는 9슬라이스가 아니다.
- 사례: 임포터가 인셋을 `min(폭,높이)/3` 으로 지어냈고 한 곳(6×6→2)이 우연히 맞았다 (함정: [덤프에 원리적으로 없는 값을 공식으로 메운 함정](함정%20-%20원본%20관측.md#덤프에%20원리적으로%20없는%20값을%20공식으로%20메운%20함정)).
- 모서리 곡률 휴리스틱은 안티에일리어싱에서 무너진다 (함정: [그림에서 추정한 9슬라이스 인셋](함정%20-%20원본%20관측.md#그림에서%20추정한%209슬라이스%20인셋)).

## 캡처

### 요약

- 대장도 폴더도 만들지 않는다.
- 정본은 [공통절차 - 캡처와 덤프 「캡처 사용 범위」](공통절차%20-%20캡처와%20덤프.md#캡처%20사용%20범위) 다.
- 캡처의 기본 용도는 세션 안의 마지막 눈 확인 한 장이다.
- 남기더라도 기본 자리는 저장소가 아니라 스크래치패드다.

### 설계

- 부득이 남기면 화면 · 상태(진행도·재화·선택·탭) · 애니메이션 정지 강제 여부 · 근거(원본 위치)를 같이 적는다.
- 상태가 없는 그림은 A/B 에 못 쓴다.
- 판정 순서는 ①원본 코드 → ②규약 문서 → ③덤프이고 그림은 그 뒤다.
