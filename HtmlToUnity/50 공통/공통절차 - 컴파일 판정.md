# 공통절차 - 컴파일 판정

상위: [공통절차](공통절차.md)

## 에디터 없는 컴파일

### 요약

- 에디터를 못 돌려도 컴파일 판정은 된다.
- 유니티 `.csproj` 는 포커스를 받아야 갱신된다. 그래서 `dotnet build Assembly-CSharp.csproj` 가 새 파일을 빼고 「0 에러」로 통과한다.
- 기본은 에디터 없이 임시 프로젝트로 직접 컴파일하는 것이다.
- 임시 프로젝트의 기본 자리는 스크래치패드다(Transfer_Programmer 「검증 산출물을 유니티 프로젝트 안에 만들지 않는다」).

### 설계

```xml
<!-- 스크래치패드에 둔다. 프로젝트 안에 만들지 않는다 -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>netstandard2.1</TargetFramework>
    <EnableDefaultCompileItems>false</EnableDefaultCompileItems>
  </PropertyGroup>
  <ItemGroup>
    <Compile Include="<프로젝트>\Assets\Scripts\**\*.cs" />
  </ItemGroup>
  <ItemGroup>
    <Reference Include="UnityEngine.CoreModule">
      <HintPath><Unity설치경로>\Editor\Data\Managed\UnityEngine\UnityEngine.CoreModule.dll</HintPath>
      <Private>false</Private>
    </Reference>
  </ItemGroup>
</Project>
```

주의: `HintPath` 는 절대경로로 적는다. 엔진 프로젝트 파일의 상대경로를 복사하면 참조가 조용히 빠져 「그 API 가 없다」 오류가 난다.

| 잡는 것 | 못 잡는 것 |
|---|---|
| 문법 · 타입 · 누락된 `using` · 시그니처 불일치 | `UnityEditor.*`. 참조를 따로 건다 |
| 새로 추가한 파일 전부 | 패키지 의존 코드. 그 DLL 을 참조에 추가한다 |
| 어셈블리 분리와 무관하게 전수 | 프리팹·에셋 참조 무결성 |

## 재생 정지

### 요약

- ⓪ 에디터가 재생 중이면 먼저 멈춘다. 물어보지 말고 멈춘다.
- 기본은 작업 시작 전에 묻지 않고 재생을 한 번 멈추는 것이다.
- 이유: 멈추는 것은 파괴적이지 않다. 재생 상태는 휘발이고 디스크 세이브는 남는다.

### 설계

| 증상 | 원인 |
|---|---|
| `isCompiling=True` 고착 | 「Recompile After Finished Playing」으로 컴파일 보류 |
| 새 메뉴·새 타입이 안 뜬다 | 옛 어셈블리가 돈다 |
| 프리팹을 구워도 반영이 안 된다 | 재생 중 `AssetDatabase` 쓰기는 신뢰할 수 없다 |
| 하네스가 실행 중인 게임 상태를 갈아엎는다 | Client 「ⓕ 하네스는 사용자 세이브를 건드릴 수 없어야 한다」 |

```
[재생 멈춤]     ← 작업 시작 전에 무조건 한 번
```

- `[...]` 는 무엇을 하는가다. 무엇으로 되는지는 그 프로젝트의 「도구 제약」 표가 정본이다. 그래서 스킬 문서에는 특정 도구 이름을 적지 않는 것이 기본이다.

## 어셈블리 웨지

### 요약

- ⓪-b 「에디터가 새 코드를 안 먹는다」의 첫 번째 용의자는 컴파일 에러다.
- 컴파일이 실패하면 유니티는 직전 어셈블리를 문다. `isCompiling=False` + 옛 DLL 이라 웨지와 같아 보이고 콘솔에 에러가 아직 없을 수 있다.
- `dotnet build` 가 바로 보여 준다.

### 설계

더 사나운 얼굴이 있다. 도구가 옛 어셈블리로 정상 실행되어 성공 로그를 찍는데 결과가 낡았다.

- 판별법 ①: 이번에 바꾼 값(경로·스위치·개수)을 도구가 성공 로그에 찍게 한다.
- 판별법 ②: 도구를 돌린 직후 엔진 로그에서 컴파일 에러를 훑는다. 성공 로그와 컴파일 성공은 다른 사건이다(함정: [컴파일 실패 뒤 직전 어셈블리로 찍힌 성공 로그](함정%20-%20도구%20러너.md#컴파일%20실패%20뒤%20직전%20어셈블리로%20찍힌%20성공%20로그)).

```bash
# 엔진 로그 자리는 플랫폼마다 다르다
grep -E "error CS" <엔진 로그> | tail
```

기본 순서는 아래다.

```bash
dotnet build Assembly-CSharp.csproj -nologo -v q          # 항상 여기부터 (런타임 csproj)
dotnet build Assembly-CSharp-Editor.csproj -nologo -v q   # (에디터 csproj)
```

| 관찰 | 뜻 |
|---|---|
| `dotnet build` 에러 있음 | 컴파일 에러. 웨지가 아니다 |
| `dotnet build` 0 에러 + 옛 DLL + `isCompiling=False` | 진짜 웨지. 에디터 창 클릭이 필요하다 |
| `isCompiling=True` 고착 | 재생 중([재생 정지](공통절차%20-%20컴파일%20판정.md#재생%20정지))이거나 포커스 대기 |

- 기본은 0 에러를 확인한 뒤에 에디터를 의심하는 것이다. 컴파일 검증은 에디터를 기다리지 않고 바로 돌린다. 프로젝트는 한 번에 하나다.
- 0 에러는 파일이 맞다는 증명일 뿐이다. 재생과 측정 전에 로드된 어셈블리에 새 멤버가 있는지 리플렉션으로 찍는다.
- 에디터 툴 실행 기본 순서는 `새로고침 → 컴파일 완료 확인 → 메뉴 실행 → 콘솔 확인` 이다. 컴파일 전에 돌리면 옛 어셈블리가 실행된다.
- 웨지는 `AssetDatabase.Refresh` + `RequestScriptCompilation` 으로 안 풀리고 에디터 창을 한 번 클릭해야 한다. 판별: 읽은 상수 배열 길이가 소스와 다르면 옛 어셈블리다.
  ```csharp
  return Generator.Ratios.Length;   // 소스는 7인데 5가 나오면 리로드 안 된 것
  ```
  급하면 같은 수식으로 외부(파이썬 등)에서 굽고 나중에 에디터 툴로 재생성하는 편이 낫다.
- `AddObjectToAsset` 은 재임포트로 앞서 채운 리스트를 되돌린다. 기본은 서브에셋을 먼저 붙여 저장하고, 데이터를 채운 뒤 `SetDirty` + `SaveAssetIfDirty(asset)` 로 확정하는 것이다.
- 아이콘 생성기는 텍스처 메모리 매핑 중 IO 예외로 뒤 전부를 안 굽는다. 내용이 같으면 건너뛰고, 실패하면 재시도하고, 그래도 안 되면 경고한다.
- 빌드 중 NRE 는 흘려보내지 않는 것이 기본이다. `AddComponent` 뒤 참조 주입이면 굽는 시점 `Awake` 가 null 을 만진다. `Awake` 에 null 가드를 넣어 경고 0을 완료 기준으로 쓴다.
