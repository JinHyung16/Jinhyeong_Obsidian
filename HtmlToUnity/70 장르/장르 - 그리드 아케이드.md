# 장르 - 그리드 아케이드

칸 격자 미로를 도는 아케이드에서 더 볼 것과 Unity 구조 차이다.

## 알아보는 신호

### 요약

- 플레이어와 자율 개체가 칸 격자 미로를 돈다.
- 수집물을 다 먹으면 클리어다.
- 개체에 닿으면 목숨이 준다.
- 판 데이터 · 벽 판정 · 방향 필드 · 랩 코드가 판정 근거다.

### 설계

| 신호 | 무엇이 보이나 |
|---|---|
| 판 데이터 | 판이 행 문자열 · 숫자 배열이고 칸 값이 벽 · 통로 · 수집물을 가른다 |
| 벽 판정 | 벽 판정이 개체 위치를 반올림한 칸 좌표를 받는다 |
| 방향 필드 | 플레이어에 현재 방향과 예약 방향 필드가 따로 있다 |
| 랩 | 격자 가장자리를 넘으면 반대편으로 옮기는 코드가 있다 |

## 더 볼 질문

### 요약

- 이동 · 벽 · 입력 · 자율 개체 · 수집 · 충돌 · 랩 · 루프 · 그리기를 따로 묻는다.
- 답은 원본 코드에서 잰다.
- 이름이 아니라 코드에 실제로 있는 것만 답으로 센다.

### 설계

| 주제 | 질문 |
|---|---|
| 이동 | 위치가 칸 단위로 점프하나, 실수 좌표로 `속도 × dt` 만큼 가나. 칸 판정은 반올림인가 내림인가 |
| 벽 | 벽에 닿으면 어디서 멈추나. 후보는 제자리 · 칸 중심 · 그 밖이다. 진행 축이 아닌 축도 튀나 |
| 입력 | 입력이 방향을 바로 바꾸나, 예약만 하나. 전환 허용 조건(칸 중심 정렬 창 · 멈춤 예외 · 목표 칸 벽 검사 기준)은 무엇인가 |
| 속도 | 속도가 개체 필드인가 코드 상수인가. 개체 · 상태마다 다른가 |
| 자율 개체 | 자율 개체가 플레이어 좌표를 한 번이라도 읽나. 상태 기계와 목표 칸이 코드에 실제로 있나 |
| 방향 선택 | 방향을 언제 고르나(벽에 닿을 때 · 갈림길마다). 후보에서 무엇을 빼나. 고른 방향을 벽 검사하나. 바꾸는 틱에 이동도 하나 |
| 난수 | 후보 배열 순서 · 동점 처리 순서는 무엇이고, 난수 호출 자리는 몇 곳인가 |
| 수집 | 이동해야 먹나, 매 틱 현재 칸을 먹나. 강화 수집물이 개체 상태를 실제로 바꾸나 |
| 충돌 | 충돌은 같은 칸 · 교차 · 거리 반경 중 무엇이고 이동 뒤 언제 재나. 한 틱에 몇 번 처리하고, 무엇을 되돌리나(개체만 · 맵까지) |
| 랩 | 랩은 어느 축인가. 격자 밖을 벽으로 치나. 랩 시점(벽 판정 전 · 이동 뒤)이 개체마다 다른가 |
| 루프 | 루프가 고정 틱인가 프레임 콜백의 가변 dt 인가. dt 상한이 있나 |
| 그리기 | 그리는 좌표가 개체마다 다른가(연속 · 칸 반올림) |

## Unity 구조 차이

### 요약

- 시뮬은 순수 C# 매니저이고 미로가 진실 소스다.
- 등록 순서가 곧 틱 순서다.
- 뷰는 시뮬 좌표를 받아 표기만 한다.
- 벽과 수집물은 같은 Tilemap 타일에 둔다.

### 규칙

- #강제 [원칙 R10](원칙.md#R10) 원본에 없는 보간은 의도된 차이로 등재했을 때만 들어간다.

### 설계

| 자리 | 기본과 이유 |
|---|---|
| 시뮬 | 순수 C# 매니저다. 기본은 미로(격자 · 점수 · 목숨 · 남은 수집물)가 진실 소스이고 플레이어 · 자율 개체가 미로에 벽을 묻는다. 이유: 판정이 한 곳에 모인다 |
| 틱 순서 | 등록 순서 = 틱 순서로 원본 루프(플레이어 → 자율 개체 → 충돌)와 종료 게이트를 옮긴다 ([GameFramework](GameFramework.md) · [Client](Client.md) 「메인 루프 게이트」). 이유: 충돌 시점이 순서에서 나온다 |
| dt | 기본은 틱이 `dt` 를 인자로 받아 하네스가 재생 없이 고정 dt 로 부른다 ([GameFramework](GameFramework.md) 「하네스 호환」). 원본이 고정 틱이면 틱 수 인자를 고려한다 |
| 난수 | 난수는 공용 유틸 한 곳에서만 꺼내고 후보 배열 순서를 원본과 같게 둔다. 이유: 매니저 난수 · 검증용 진입점은 실제 경로를 안 지난다 |
| 표 분할 | 미로는 행 문자열 표, 정렬 창 · 속도 · 충돌 거리 · 시작 칸은 설정 표, 개체는 시작 칸 · 방향 · 색 표가 기본 분할이다. 설정 값이 적으면 합쳐도 된다 |
| 타일 | 기본은 벽과 수집물을 같은 Tilemap 타일로 두고 먹은 칸만 다시 칠한다. 이유: 수집물은 많고 정적이다. 움직이거나 애니메이션이 있으면 개체를 고려한다 |
| 좌표 뒤집기 | 격자 y ↔ 월드 y 뒤집기는 뷰 변환 함수 하나에 몰고 타일 앵커도 그 기준에 맞춘다. 이유: 두 곳이면 반 칸 어긋난다 |
| 뷰 | 뷰는 시뮬 좌표를 받아 표기만 하고 방향도 시뮬 상태에서 받는다 |
| 입력 | 키보드 원본을 모바일로 옮기면 기본은 화면 전체 판 하나의 스와이프로 예약 호출까지만 하고, 문턱을 넘는 순간 한 축만 보낸다. 이유: 전환 허용은 시뮬이 가른다. 확정표가 가상 패드 · 버튼을 정했으면 그쪽이다 |
| 원본 하네스 | 원본 하네스는 난수를 시드 LCG 로, 프레임 콜백을 가로채 단조 증가 타임스탬프를 먹인다 ([공통절차 - 원본 관측 도구](공통절차%20-%20원본%20관측%20도구.md) 「결정적 스냅샷」) |
| 시드 수열 | 시드 수열이 원본과 다르면 기본은 무작위 거동을 횟수가 아니라 존재로 대조하고, 결정성은 같은 시드 두 번 diff 0 · 다른 시드 다른 로그로 닫는다. 수열이 같으면 횟수 대조를 고려한다 |

## 함정

### 요약

- 원본 이상을 고쳐 옮기는 사고가 가장 많다.
- 이름을 믿고 없는 시스템을 만드는 사고가 그다음이다.
- 반 칸 어긋남과 카메라 이중 렌더가 화면을 비운다.

### 규칙

- #강제 [원칙 R1](원칙.md#R1) 이런 이상도 재현하고, 고치려면 등재 · 확정을 거친다.
- #강제 [원칙 R3](원칙.md#R3) 이름은 근거가 아니고 코드가 가른다.

### 설계

| 사고 | 함정 노트 |
|---|---|
| 벽 스냅 · 전환 틱 정지 · 새 방향 벽 미검사 · 랩 순서 · 반올림 그리기 같은 원본 이상을 고쳐 옮긴다 | [원본 버그를 고쳐서 옮긴 이관](함정%20-%20판정%20보고.md#원본%20버그를%20고쳐서%20옮긴%20이관) |
| 「추격 AI」라는 이름을 믿고 원본에 없는 추적 · 상태 기계 · 강화 효과를 만든다 | |
| 「이동해야 먹는다」로 옮겨 시작 칸 점수가 어긋난다. 두 개체의 랩을 한 함수로 합쳐 한쪽 경계가 어긋난다 | |
| 하네스가 타임스탬프를 되감아 dt 가 음수가 된다. 반대로 튄 개체를 원본 이상으로 읽는다 | [하네스가 되감은 타임스탬프](함정%20-%20원본%20관측.md#하네스가%20되감은%20타임스탬프) |
| 매니저가 난수를 직접 만들거나 검증용 진입점을 뚫어 결정성 검사가 실제 경로를 안 지난다 | [게임 코드에 뚫은 하네스 전용 진입점](함정%20-%20검사기%20설계.md#게임%20코드에%20뚫은%20하네스%20전용%20진입점) |
| 타일 앵커와 개체 좌표가 반 칸 어긋난다. 스와이프 y 부호가 뒤집힌다 | [순수 함수만 잰 골든 테스트](함정%20-%20검사기%20설계.md#순수%20함수만%20잰%20골든%20테스트) · [좌표계가 다른데 그대로 옮긴 부호 있는 값](함정%20-%20로직%20데이터.md#좌표계가%20다른데%20그대로%20옮긴%20부호%20있는%20값) |
| UI 카메라가 월드 판을 다시 그리거나 HUD 배경이 판을 가려 화면만 빈다 | [그릴 대상을 안 가른 두 카메라의 이중 렌더](함정%20-%20UI%20흐름.md#그릴%20대상을%20안%20가른%20두%20카메라의%20이중%20렌더) · [HUD 창을 가리는 불투명 배경](함정%20-%20UI%20흐름.md#HUD%20창을%20가리는%20불투명%20배경) |
