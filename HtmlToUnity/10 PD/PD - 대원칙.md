# 대원칙

상위: [PD](PD.md)

## 대원칙

### 요약

- 값과 규칙은 원본에서 가져오고, 구조는 Unity 식으로 다시 설계한다.
- 이관은 번역이 아니라 재구현이다.
- 원본은 「무엇을 하는가」의 출처다. 「어떻게 만드는가」는 Unity 가 정한다.
- 근거는 「원본이 이렇게 생겼으니」가 아니라 「원본이 무엇을 하니 우리는 이 구조로 한다」여야 한다.

### 규칙

#강제 [원칙 R2](원칙.md#R2) 값과 규칙은 원본에서 가져오고, 구조는 Unity 식으로 다시 설계한다.

#강제 [원칙 R1](원칙.md#R1) 구조를 다시 짜도 값·분기·순서는 한 줄도 바꾸지 않는다. 「더 나은 공식」도 바꾸는 것이다.

### 설계

| 원본에서 가져오는 것 | 원본에서 버리는 것 |
|---|---|
| 수치 · 확률 · 계수 · 문구 | DOM 계층 · CSS 셀렉터 |
| 계산식 · 상태 전이 · 조건 분기와 그 순서 | `flex` · `absolute` · `%` 같은 배치 수단 |
| 무엇이 보이고 무엇이 눌리는가 | `innerHTML` 재생성 · SVG · canvas 호출 순서 |
| 개체 수 · 층 수 · 등장 조건 | 유니코드·폰트·색을 공짜로 쓰던 전제 |

아래는 기본 대응이다. 원본·장르·규모를 보고 더 맞는 Unity 구조가 있으면 고른다. 기본과 다르게 가면 착수 확정이나 작업 분해 때 선택지와 근거를 사람에게 보여 교차 확인한다.

| 원본이 그 일을 하던 방법 | Unity 구조 |
|---|---|
| DOM 계층 | Window / Panel / Component ([UIFramework](UIFramework.md)) |
| `display:flex` · `position:absolute` | LayoutGroup · 앵커 · 재활용 스크롤 ([PrefabRule](PrefabRule.md)) |
| `innerHTML` 로 매번 재생성 | 프리팹 풀링 + 값 주입 ([PD - 엔진 패러다임 차이](PD%20-%20엔진%20패러다임%20차이.md) ①) |
| 컨테이너 1개 + `closest()` 이벤트 위임 | 개체가 적으면 Button, 많으면 뷰 하나가 좌표로 ([PD - 엔진 패러다임 차이](PD%20-%20엔진%20패러다임%20차이.md) ④) |
| 유니코드 기호 · 임의 폰트 | 아틀라스 아이콘 · `TMP_SpriteAsset` ([ResourceRule](ResourceRule.md) 「폰트」) |
| 전역 상수 · 하드코딩 테이블 | 시트 → JSON → Container ([DataFramework](DataFramework.md)) |

스스로 검사하는 문장:

- 원본 좌표식을 그대로 옮기고 있으면 멈춘다. 위치인지 순위인지 가르는 것이 기본 점검이다 (UI/UX 「renderMode 는 상황마다 다르다」).
- 원본 DOM 을 1:1 로 대응시키고 있으면 멈춘다. 프레임워크 3계층에 앉히는 것이 기본 처방이다.

## 속 품질

### 요약

- 겉이 원본과 같아도 속이 엉망이면 결과물을 이어서 다듬을 수 없다.
- 사람이 디테일을 올릴 때 프리팹이나 데이터를 조금 고쳐서 끝나는 것이 목표다.
- 보이는 값을 바꾸는데 코드를 고쳐야 하면 속 품질이 모자란 것이다 (G8).
- 검사가 겉만 재면 속이 엉망이어도 전부 통과한다. 속은 G8 로 판정한다 ([PD - 게이트](PD%20-%20게이트.md)).

### 규칙

#강제 [원칙 R14](원칙.md#R14) 이 기준은 정한 뒤 새로 착수하는 게임부터다. 이미 이관한 게임은 소급해서 고치지 않는다 [사람 확정].

#강제 [원칙 R22](원칙.md#R22) 프리팹이 주인이면 빌더 재실행으로 이미 있는 프리팹을 덮어쓰지 않는다.

### 설계

| 값 | 사는 곳 | 이유 |
|---|---|---|
| 보이는 조정값. 위치 · 크기 · 색 · 알파 · 연출 속도 · 타이밍 · 이징 | 프리팹 직렬화 필드. 기본값은 원본 값, 출처는 `[Tooltip]` 이나 주석 | 사람이 에디터에서 바로 고친다 |
| 굽는 아트의 입력 (규격 · 색 · 예외) | 굽는 입력 데이터 (에디터 전용 JSON 등) | 다시 구워도 유지된다 |
| 밸런스. HP · 확률 · 비용 · 레벨 표 | 데이터 시트 ([DataFramework](DataFramework.md)) | 표로 한꺼번에 조정한다 |
| 원본 규칙 · 계산식 · 폴백 계수 | 코드 상수 + 원본 행 인용 | 다듬을 대상이 아니라 사양이다 |

- 기본은 프리팹이 주인이다 (확정표 10-b 기본값). 빌더는 첫 초안만 굽는다. 이유: 사람이 에디터에서 올린 디테일이 다음 굽기에 사라지지 않는다. 이 게임에 다른 방식이 낫다고 보면 착수 확정 때 선택지와 근거를 사람에게 보여 교차 확인한다 ([PrefabRule](PrefabRule.md) 「프리팹 생성 방식」).
- 런타임이 바꾸는 값은 데이터·상태로 갈리는 값으로 한정하는 것이 기본이다. 이유: 런타임이 프리팹 값을 코드 상수로 다시 덮으면 프리팹을 고쳐도 화면이 안 바뀐다.
- 원본과 다르게 가기로 한 것(의도된 차이 · 사람 확정)은 결과물(프리팹 · 데이터 · 굽는 입력)에 반영하는 것이 기본이다. 생성기·런타임 코드에 에셋 이름 목록으로 분기를 넣으면 아래 사례처럼 된다.
- 사례: 버튼 둘레 띠 제거를 빌더 코드의 이름 목록(`NoOuterHalo`)으로 넣었다. 되돌리거나 다른 에셋에 적용하려면 코드를 고쳐야 했다.
- 갈리는 것은 데이터 행이나 프리팹 필드로 표현하는 것이 기본이다. 에셋 이름·게임 이름으로 갈리는 `if` 는 G8 ③ 에서 센다.

## 원본 이상

### 요약

- 원본의 이상 거동은 고치는 것도 이관이 아니다.
- 기본값은 재현이다.
- 「이상」과 「직관과 다른 것」은 처리가 다르다. 둘 다 실측으로 확증하고 정답지로 못 박는다.
- 찾은 건수를 원장에 숫자로 적는 것이 기본이다. 0건이면 「아직 안 찾았다」를 먼저 의심하는 편이 낫다.

### 규칙

#강제 [원칙 R1](원칙.md#R1) 모자란 루프 상한, `0` 의 falsy 판정, 빠진 가드도 사양이다. 고쳐서 옮기지 않는다.

#강제 [원칙 R10](원칙.md#R10) 고치려면 확정표 12번에 「의도된 차이」로 등재한다. 등재 없이 고친 것은 결함이다.

#강제 [원칙 R1](원칙.md#R1) 직관과 다른 것(구현의 필연적 결과)은 확정 절차 없이 재현한다.

### 설계

기본 절차:

1. 원본을 돌려 실측으로 확증한다.
2. 학습 문서에 [실측] 표시와 재현 방법을 적는다.
3. 원장 「원본 이상 목록」에 올린다.
4. PD 가 재현/수정을 확정한다. 확정 전에는 그 항목을 이관 대기로 둔다.

사례: 매치 루프 상한이 하나 모자라 특정 자리 4연속이 3점이 됐다. 무매치 기저 보드에서 점수 증분을 재서 확증했다.

| | 원본 이상 | 직관과 다른 것 |
|---|---|---|
| 무엇 | 저자가 의도하지 않았을 수 있는 것 (모자란 상한, falsy, 빠진 가드) | 구현 방식의 필연적 결과 (순회 방향, 판정 순서, 즉시 수정) |
| PD 확정 | 필요 (재현/수정) | 불필요. 재현한다 (R1) |
| 고칠 수 있나 | 「의도된 차이」 등재 시 | 없다. 고치면 다른 게임이다 |
| 놓치면 | 특정 자리만 어긋난다 | 전 구간이 조용히 어긋난다 |

- 가르는 질문: 「원본을 그대로 옮겼는데도 이 값이 나오나?」 나오면 직관과 다른 것이다. 특정 한 줄을 그대로 옮겨야만 나오면 이상이다.
- 주의: 직관과 다른 것은 「교과서대로」 구현하고 맞다고 믿기 쉽다. 그래서 겹치는 입력·연속 입력을 벡터에 넣는 것이 기본이다.
- 원장에 「원본 이상 목록」(확정 대기)과 「직관과 다른 것」(벡터만)을 따로 두는 것이 기본이다. 이유: 위 표처럼 처리가 다르다.
