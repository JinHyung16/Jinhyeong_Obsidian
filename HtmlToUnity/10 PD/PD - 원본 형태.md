# 원본 형태

상위: [PD](PD.md)

## 원본 형태 판정

### 요약

- 원본이 코드로 오나 URL 로만 오나에 따라 학습 방법이 갈린다.
- URL 제공형도 블랙박스로 단정하지 않는다. 런타임 직독 → 번들 소스 → 실측 순으로 찔러 본다.
- 「블랙박스」라고 적기 전에 아래 절의 방법을 다 쓴다.

### 설계

| 형태 | 무엇 | 학습 방법 |
|---|---|---|
| 코드 제공형 | 원본 폴더에 HTML/JS/CSS 가 있다 | 코드 정독 + 실행 실측 |
| URL 제공형 | 서비스 링크만 있다 | 런타임 직독 → 번들 소스 수신 → 실측 |

## 런타임 직독

### 요약

- 엔진 런타임은 대개 전역으로 노출돼 있다. 오브젝트 · 좌표 · 프레임 수를 직접 읽을 수 있다.
- 착수 실측 첫 순서로 아래 자리를 한 묶음으로 찔러 본다.
- 읽은 값은 사양이 아니라 원본에서 온 값이다.

### 규칙

#강제 [원칙 R3](원칙.md#R3) 런타임에서 읽은 값도 [실측]+재현 방법을 붙인다.

### 설계

| 찌를 자리 | 나오는 것 |
|---|---|
| 프레임 전수 순회 (먼저) | 게임은 첫 iframe 이 아니라 더 안쪽 프레임(대개 다른 출처)에 있을 수 있다 |
| 콘솔 로그 | 엔진 종류 · 진행 이벤트 |
| 엔진 런타임 전역. 예시: `window.c3_runtimeInterface._localRuntime` (Construct) · `window.game`/`Phaser` · `unityInstance` | 오브젝트 클래스 전수 · 인스턴스 좌표·크기 · 애니메이션 프레임 수 · 레이어 |
| 게임 프레임의 `canvas` | 논리 해상도 · 스케일 방식 |
| 저장소 (`localStorage` 등) | 진행 저장 여부와 키 |

사례: 프레임 전수 순회를 안 해 블랙박스로 오판했다. 못 찾으면 「안 뒤진 곳이 있다」를 먼저 의심한다.

런타임 조회의 함정:

| 함정 | 대응 |
|---|---|
| 화면 밖 대기 개체 (좌표가 음수이거나 터무니없이 큼) | 배치값이 아니라 대기 상태로 읽는다 |
| 한 화면에 배율이 둘 이상 (레이어별 스케일·시차) | 레이어마다 배율을 따로 환산한다 |
| 충돌 칸과 그림 스프라이트의 크기가 다름 | 분리해서 옮긴다 |
| 매 프레임 갱신 연출(흔들림·위상차) | 캡처로 안 보인다. 런타임 속성명을 단서로 쓴다 |
| 첫 인스턴스가 미끼·대기·비활성 | 전 인스턴스를 열거한다 |
| 연달아 조작한 상태는 첫 상태와 다름 | 판정용 실측은 시행마다 새 컨텍스트(또는 재시작)에서 잰다 |

## 번들 소스

### 요약

- 웹 게임 코드는 브라우저로 내려온다. 난독화돼도 저작 상수·식·클래스 구조는 문자열로 남는다.
- 여기서 판이 바뀐다. 관측만으로는 규칙이 안 닫힌다.

### 규칙

#강제 [원칙 R3](원칙.md#R3) 번들에서 주운 숫자는 관측치와 맞물리는 앵커가 있을 때만 값으로 인정한다.

### 설계

| 단계 | 무엇 |
|---|---|
| ① 스크립트 URL 수집 | 게임 프레임이 로드하는 `*.js` 를 네트워크에서 모은다 |
| ② 게임 프레임 안에서 받는다 | 그 프레임 origin 으로 받아 교차 출처를 피하고, 로컬 파일로 저장한다 |
| ③ 앵커로 찾는다 | 관측한 값(목표 배열 · 간격 · 개체 이름)을 정규식으로 찾아 근처를 읽는다 |
| ④ 우리 구조로 다시 구현 | 상수·식·순서만 우리 표·시뮬로 옮긴다 (코드 복사는 R11) |

사례: 실측만 8회차로 상수는 2% 안으로 맞췄으나 규칙(스폰·조준·업그레이드·레벨 목표·카메라)은 전부 틀렸다. 소스를 받은 9회차에 한 번에 닫혔다.

심화는 [공통절차 - 원본에서 값 캐기](공통절차%20-%20원본에서%20값%20캐기.md)이 정본이다. 후킹 · 자산의 원래 색·모양 · 도달 불가 입력 · 무작위 경계 · 저작값 찾기가 거기 있다.

## URL 제공형 첫 질문

### 요약

- URL 제공형이면 아래 셋을 한 번에 묻는다.
- 게임명이 폴더명 · 원장명이 된다.

### 설계

```
이 게임의 정확한 게임명은 무엇입니까? 【기본값: 서비스 페이지의 표기】
제공하신 URL 이 원본의 전부입니까 — 따로 받을 수 있는 코드·에셋이 있습니까?
이관 대상은 어느 범위까지입니까 (모드·월드 등)?
```

## 원본 폴더

### 요약

- URL 제공형은 착수 시 원본 폴더를 만든다.
- 위치는 저장소 진입 파일(CLAUDE.md 등)이 정한다. 기본은 코드 제공형 풀과 다른 루트다.
- 이유: 폴더 이름에서 「코드가 없다」가 읽혀야 다음 회차가 없는 코드를 찾지 않는다.

### 설계

```
[예시]
<URL 원본 풀>/<NN>-<게임명>/     ← 이 폴더가 <원본폴더> 역할이다
├─ 00_원본정보.md               ← 코드 대신 원본 포인터
└─ HtmlToUnityLogic/            ← 골격 전부(덤프 포함). 규격 동일 (분석로직)
                                   캡처 폴더는 없다 — 공통절차 「캡처는 쌓지 않는다」
```

- `00_원본정보.md` 최소 행: 게임명 · 원본 URL · 제작사/서비스 · 실측 엔진(콘솔 로그로 확인) · 조작 방법 [실측] · 접속·재현 방법(입력 자동화 포함) · 플랫폼 소속 목록.
- 원본이 내려가면 이 문서와 기대값 표가 2차 심판이다.
- 그래서 실측마다 재현 방법을 남기는 것이 기본이다.

## 플랫폼 소속

### 요약

- 서비스 플랫폼이 그리는 것은 원본이 아니다.
- 포털의 홈 버튼 · 광고 · 로그인 · SDK 연출은 게임이 아니다.
- 이유: 섞으면 플로우 diff 가 오탐한다.

### 설계

- 기본은 실측 첫 회차에 화면 요소를 게임 소속 / 플랫폼 소속으로 가르는 것이다.
- 플랫폼 소속 목록은 `00_원본정보.md` 에 적어 이관 범위에서 뺀다.

## 막히는 구간

### 요약

- 자동 입력으로 재현이 안 되는 구간이 있다. 정밀 타이밍·제스처, 후반 구간, 결제·계정 뒤가 그렇다.
- 기본은 사람에게 플레이 영상을 한 묶음으로 요청하고 스틸(ffmpeg 등)로 실측하는 것이다.
- 못 받으면 미측정이다 (R6).

## URL 제공형의 증거

### 요약

- 코드 인용 게이트는 실측 재현 방법으로 대체한다. 면제가 아니다.
- 연속 입력값이 있으면 성공 1점이 아니라 「실패-성공-실패」 3점을 담는다.
- 원본 리소스는 뜯어 오지 않고 재제작한다.

### 규칙

#강제 [원칙 R3](원칙.md#R3) URL 제공형의 값 근거는 아래 표의 오른쪽 열이다. 「이런 게임은 보통 이렇다」 같은 장르 지식은 가설 등급까지만이다.

#강제 [원칙 R11](원칙.md#R11) 원본 스프라이트·사운드는 런타임·번들로 읽혀도 뜯어 오지 않는다.

### 설계

| 코드 제공형의 증거 | URL 제공형의 동등 증거 |
|---|---|
| 원본 파일:줄 인용 | [실측] + 재현 방법. URL · 진입 경로 · 입력 시퀀스 · 캡처 파일명 |
| 상수·테이블 발췌 | 반복 실측값 + 측정 횟수. 못 재면 `미측정` |
| 정답지를 코드 로직으로 산출 | 입력 시퀀스 → 화면 결과를 표로 채록 |
| 캡처 `_대장.md` 의 「근거(원본 코드 위치)」 컬럼 | 재현 방법 컬럼 |

실측으로 채록한 정답지는 성공 1점으로 만들지 않는다.

- 연속 입력값(누르는 시간·거리·각도)이 있으면 기본은 레벨·상황마다 「실패-성공-실패」 3점을 담는 것이다. 성공 구간의 양쪽 경계가 고정된다.
- 이유: 성공 1점만 담으면 곡선이 어긋나도 통과한다.
- 사례: 성긴 격자로 한 발도 성공하지 못해 「깰 수 없는 구간」으로 오판할 뻔했다. 성공을 못 찾으면 격자를 촘촘히 한다.

리소스는 재제작하고 합격 기준(확정표 12)을 퀄리티 동일로 잡는 것이 기본이다. 수치·규칙은 실측해 재현한다.
