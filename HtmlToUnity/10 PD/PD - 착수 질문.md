# 착수 질문

상위: [PD](PD.md)

## 착수 질문

### 요약

- 착수 전 확정은 PD 가 사람에게 물어 확정한다.
- 이 답이 모든 파트의 분기를 결정한다.
- 답은 두 곳에 적는 것이 기본이다. 각 담당자 md 의 `[Unity 프로젝트 세팅]` 절(담당자는 이 절만 본다)과 원장(확정표 전체)이다.
- 규약 문서(`PrefabRule.md` 등)는 게임을 넘어 쓰이므로 게임의 답을 적는 자리가 아니다.

### 규칙

#강제 [원칙 R13](원칙.md#R13) 답이 없으면 그 아래를 짜지 않는다.

#강제 [원칙 R13](원칙.md#R13) 답을 못 받은 항목이 있으면 학습 단계를 열지 않는다.

## 질문 문안

### 요약

- 파생 문항까지 전부 묻는다. 일부만 묻고 넘어가지 않는다.
- 화면·해상도 계열(2·3·7)은 한 덩어리로 먼저 묻는 것이 기본이다. 이유: 미정이면 좌표 단위를 모르고 아트를 두 번 굽는다.
- 기본값 있는 질문은 「이대로 갈까요?」로 묻고, 답이 무엇을 바꾸는지 한 줄을 붙인다.
- 아래 기본값은 출발점이다. 다른 값이 낫다고 판단하면 선택지와 근거를 같이 올려 교차 확인하고, 고른 결과와 이유는 확정표에 남긴다 (원칙 「쓰는 법」).

### 규칙

#강제 [원칙 R12](원칙.md#R12) 다른 답을 받으면 그 답이 이긴다. 실측이 확정과 다르면 보고하고 확정을 따른다 (함정: [사람이 없애라 한 버튼 둘레 띠를 측정으로 되살린 일](함정%20-%20사람%20권리%20안전.md#사람이%20없애라%20한%20버튼%20둘레%20띠를%20측정으로%20되살린%20일)).

### 설계

[화면 · 해상도]

- 1. 타깃 플랫폼은? 【기본값: 모바일】 → 세이프에어리어·터치 입력·텍스처 압축이 갈린다. 원본이 데스크톱 전용 흐름 배치면 모바일 레이아웃은 원본에 없으므로 기준을 12번에서 따로 정한다.
- 1-b. 구체 플랫폼은? (Android / iOS / Windows / WebGL …) 【기본값: Android】 → 패키지 이름·최소 OS·텍스처 압축 포맷·스크립팅 백엔드·그래픽 API 가 갈린다. 답이 없으면 빌드 설정이 끝까지 기본값으로 남는다.
- 1-c. 제품명과 패키지 식별자는? 【기본값: 게임명 그대로 · `com.<회사>.<게임명>`】 사례: 행이 없어 첫 게임의 제품명·패키지가 두 번째 게임에 남았다.
- 2. 화면 방향은? 【기본값: Portrait】 주의: 자동 회전을 끄지 않으면 기기를 돌렸을 때 원본에 없는 레이아웃이 나온다.
- 3. Canvas Reference Resolution 은? 【기본값: Landscape 1920×1080 · Portrait 1080×1920】
- 3-b. Canvas Screen Match Mode 는? 【기본값: Match Width or Height · Match = 0 (Width 기준)】 → 세로 게임의 판정 대상이 대개 폭이다.
- 3-c. Canvas Render Mode 는? 【기본값: ScreenSpace-Camera + 전용 UICamera】 → UI 사이에 파티클·스프라이트·셰이더를 끼울 수 있다. Overlay 는 나중에 통째로 갈아야 한다.
- 3-d. (알림) 원본 논리 해상도는 PD 가 원본을 띄워 실측하고(CSS 가 아니라 JS 가 잡는 경우가 많다) 환산 배율을 계산해 확인만 받는다. 배율은 한 곳만 통과시키는 것이 기본이다. 프로젝트에 스케일·레이아웃 규약이 있으면 그쪽이 우선이다.
- 7. 리소스는 원본 크기 그대로인가, 재제작인가? 【기본값: 재제작 · 크기는 4의 배수】 → 먼저 원본 아트 해상도를 재서 알린다. 다시 구운 아트는 「그림이 원본과 같다」 판정을 포기한다.
- 7-b. 원본에 소리가 있으면? 【기본값: ① 오디오 없이 간다】 지금 안 정해도 된다. ①이어도 「의도된 차이」로 등재하고 자리를 남긴다.

  | # | 선택지 | 뜻 |
  |---|---|---|
  | ① | 오디오 없이 진행 | 나중에 「오디오 넣어줘」라고 하면 원본과 대조해 장면별로 배치하고 클립을 최적화해 넣는다 |
  | ② | 오디오 파일을 받는다 | 받은 클립을 원본과 대조해 배치·최적화한다 |
  | ③ | 직접 구워서 원본과 같게 | 원본이 코드로 합성하는 소리를 같은 파형·주파수로 굽고 숫자로 증명한다 |
  | ④ | 런타임에 원본 방식으로 합성 | 코드로 소리를 만든다. 오디오 파일 0개 |

[렌더]

- 4. 2D 입니까 3D 입니까? 【기본값: 2D】
- 5. 렌더 파이프라인은? 【기본값: 프로젝트에 이미 깔린 것(URP 등)】
- 6. 색공간은? 【기본값: 프로젝트 현재값 유지】 → 브라우저는 감마 합성이다. 코드·데이터의 알파는 원본값 그대로 두고, 차이는 굽기·헬퍼·프리팹 세팅 한 곳에서 흡수한다 (Fx.md 「색공간」).

[원본 · 데이터]

- 8. 원본 HTML5 는 어디에 있고 어떻게 실행합니까? 【기본값 없음. 받아야 착수한다 (R13)】
- 9. 데이터는 어디에 둡니까? 【기본값: JSON 전용 + Container】 → 기본은 엑셀 파이프라인 없이 간다. 밸런스 행이 많으면 JSON 에서 엑셀을 만드는 규칙으로 승격하는 편이 낫다 ([DataFramework](DataFramework.md) 「JSON 전용과 엑셀 승격」).
- 9-b. (원본 공격 수단이 2종 이상일 때) 스킬 데이터는? 【기본값: 조합형. JS 모듈 + 익스포터 굽기 · 실행은 중앙 틱 (SkillSystem.md)】 → 평면 JSON 으로 가면 스킬 1종 추가마다 C# 을 고친다. 사람이 고른 설계 기본값이다. 이 게임에 다른 방식이 낫다고 보면 선택지와 근거를 같이 올린다.
- 10. UI 프레임워크는? 【기본값: 있으면 그것, 없으면 최소 세트만 새로】 → 신규면 구축 자체가 리스트업 항목이다 ([GameFramework](GameFramework.md) 「최소 세트」).
- 10-b. 프리팹(화면·개체 조립품)은 초안을 구운 뒤 어디서 고칩니까? 【기본값: 프리팹이 주인. 빌더는 첫 초안만 굽고 이미 있는 프리팹은 덮어쓰지 않는다. 이후 수정은 프리팹을 직접 고친다】 → 「빌더가 주인」이면 디테일 수정이 전부 빌더 코드 수정이 되고, 손으로 고친 것은 다음 굽기에 사라진다. 이 답이 패스 ②·③의 고칠 곳을 가른다. 사람이 고른 설계 기본값이다. 다른 방식을 권하려면 선택지와 근거를 같이 올린다.
- 10-c. 아트·프리팹 로드 방식은? 【기본값: UI 프리팹은 Resources · 그 밖의 아트는 Addressables】 → 큰 아트는 로드/해제 단위가 있어야 빌드가 안 부푼다.

[판정]

- 11. 수치 정답지가 있습니까? 【기본값: 없음 → 이번 회차 리스트업 항목】 (담당 Transfer_Programmer · G2 를 열기 전) → `HtmlToUnityLogic/07_기대값.md` 에 표로 만든다. 검증용 파일·에셋은 유니티 프로젝트 밖에 두는 것이 기본이다 ([Transfer_Programmer - 검증 도구](Transfer_Programmer%20-%20검증%20도구.md) 「검증 산출물 자리」).
- 11-b. 레벨이 몇 번째까지 원본과 같아야 합니까? 【기본값: 앞 10~20개를 채록해 규칙을 뽑고 나머지는 규칙으로】 → 레벨이 있으면 이 문항은 묻는다 (범위 결정은 R13). 이유: 안 물으면 1레벨만 맞는다. 채록 개수는 숫자로 적는다.
- 12. 합격 기준은 픽셀 동일입니까, 퀄리티 동일입니까? 【기본값: 퀄리티 동일】 → PD 가 판정 가능한 숫자 초안으로 바꿔 확인받는다.

## 이월과 재질문

### 요약

- 두 번째 게임부터는 이월되는 것과 다시 묻는 것을 가른다.
- 저장소 규약은 이월한다. 게임의 결정은 게임마다 다시 묻는다.
- 주의: 10-b 는 이전 게임이 「빌더가 주인」이었어도 새 게임에서 기본값(프리팹이 주인)으로 다시 묻는다.
- 주의: 화면 방향과 해상도가 가장 잘 이월돼 버린다. 사례: 묻지 않고 세로 1080×1920 으로 만들었는데 맞은 것은 우연이었다.

### 규칙

#강제 [원칙 R13](원칙.md#R13) 「게임의 결정」 행은 이월하지 않고 게임마다 다시 묻는다.

### 설계

| 종류 | 무엇 | 두 번째 게임에서 |
|---|---|---|
| 저장소 규약 | 구체 플랫폼 · 렌더 파이프라인 · 색공간 · 데이터 소스 · UI 프레임워크 · 프리팹 생성 방식 · 로드 방식 | 이월한다 |
| 게임의 결정 | 화면 방향 · 해상도 · 입력 대체 · 사운드 · 렌더 방식(어떻게 그릴까) · 리소스 정책 · 합격 기준 · 정답지 유무 · 원본 위치 | 게임마다 다시 묻는다 |

묻는 문구: 「이 게임은 세로(Portrait)로 갈까요, 가로(Landscape)로 갈까요? 해상도는 몇×몇으로 잡을까요? 【기본값: 세로 1080×1920 / 가로 1920×1080】」

## 묻는 법

### 요약

- 비개발자가 고를 수 있게 묻는다.
- 사례: 렌더 방식을 「Tilemap / 스프라이트 개체 / 절차적 텍스처」로 물어 비개발자가 고를 근거가 없었다.

### 설계

| 피할 것 | 기본 |
|---|---|
| 「Tilemap 으로 할까요?」 | 「① UI 로 그릴까요 ② 2D 게임에서 많이 쓰는 타일맵으로 그릴까요 ③ 그림 한 장으로 구울까요」 |
| 선택지 2개 | 가능한 방식을 최대한 다 편다 |
| 용어만 | 용어 + 한 줄 설명 + 무엇이 달라지나 |
| 「권장」만 적기 | 권장을 맨 앞에 두고 나머지가 왜 있는지 적는다 |

1. 유니티 용어 옆에 무엇인지 한 줄 붙인다.
2. 고르면 무엇이 달라지나(비용·품질·나중에 바꾸기 어려운가)를 쓴다.
3. 나중에 정해도 되는 것은 그렇게 말한다.

## 회차 폐기와 재개

### 요약

- 회차를 버릴 때와 끊긴 뒤 다시 시작할 때의 순서다.
- 재개는 md 에 적힌 것을 근거로 삼는 것이 기본이다. 이유는 「역할을 바꾸면 기억을 이어가지 않는다」와 같다.

### 규칙

#강제 [원칙 R18](원칙.md#R18) 폐기에 따른 커밋은 사람 몫이다.

#강제 [원칙 R23](원칙.md#R23) 폐기한 회차의 원장 행은 지우지 않는다.

### 설계

폐기

1. 폐기 대상을 나열한다. 그 회차의 아트·프리팹·코드 변경과 원장 해당 행 전부.
2. 파일은 작업 트리에서 지우거나 되돌리고 목록을 사람에게 넘긴다.
3. 원장 그 회차에 「폐기」와 사유를 적는다.
4. 원인이 확정표 빈 행이면 그 행부터 다시 확정한다.

재개 (컨텍스트가 끊긴 뒤)

① 원장 최신 회차 → ② 미흡 목록 → ③ 최하위 미통과 게이트 순으로 읽는다.
