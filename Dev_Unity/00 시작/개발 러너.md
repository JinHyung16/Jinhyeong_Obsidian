# 개발 러너

Unity 게임을 처음부터 만들 때의 진입 노트다. 러너(단계 표 · 위상 · 진행 표기 · 종료), 노트 로딩 안내, 원장 규칙이 여기 있다. 새 게임·새 콘텐츠를 착수하거나 만든 것을 검증할 때 가장 먼저 편다.

## 이 세트가 무엇인가

Unity 게임을 처음부터 만드는 범용 개발 오케스트레이션 노트 세트다. 특정 타이틀·특정 장르에 묶이지 않고, 어떤 게임을 만들 때도 그대로 쓴다.

여기에는 심판할 원본이 없다. 옮겨 오는 작업이라면 "원본과 같은가"로 끝나지만, 새로 만들 때는 그 기준이 없다. 그래서 심판을 직접 만든다.

1. 확정표가 심판이다 — 착수 13행에 없는 것은 만들지 않는 것이 기본이고, 확정표와 다르면 구현이 틀린 것으로 본다
2. 실측이 완료 조건이다 — "구현했다"가 아니라 "돌려서 쟀다"가 완료다

확정표가 애매해서 판정이 안 되면 그건 구현 문제가 아니라 확정 문제다. [역할 - PD](역할%20-%20PD.md) 로 되돌린다.

## 뼈대 — 착수 13행이 트렁크 전체를 잠근다

```
      [착수 질문 13행]                      ← 가지: 사람에게만 물을 수 있는 것
             ▼
  확정표 · 코어루프 · 레퍼런스 실측본        ← 허리: 표준 산출물 계약
             ▼
 ┌───────────┴───────────┐
 │  규약 7 — 확정표가 값을 채운다        │  ← 트렁크: 게임 종류를 모른다
 │  뷰 · 플랫폼 · 최적화                 │
 │  데이터 · UI · 프리팹 · 아트 방향     │
 └───────────┬───────────┘
             ▼
   버티컬 슬라이스 → [계약 확정] → 트랙 겹치기 → 연결 → 실측 → 게이트 → QA
                                    ├ 기획 데이터
                                    ├ 클라 기능
                                    └ 아트/UI 프리팹·배치
             ▼
          Unity 빌드
```

트랙은 겹치되 이음매는 나누지 않는다. 계약(데이터 스키마 · 바인딩 계약)을 먼저 박으면 마지막이 "연결"로 끝나고, 계약 없이 겹치면 그게 재작업이 된다. 규격은 [역할 - PD](역할%20-%20PD.md) 트랙 절.

규약 노트에는 특정 장르·특정 게임의 분기를 넣지 않는 것이 기본이다. 이유: "서바이버면 이렇게"가 [규약 - UI](규약%20-%20UI.md) 에 스며들면 새 장르가 올 때마다 규약을 전부 고치게 된다. 장르 차이가 들어가도 되는 자리는 셋이다.

1. 장르 노트 ([장르 문법 지도](장르%20문법%20지도.md) 에서 찾는다)
2. 레퍼런스 TSV (그 게임에서 잰 값)
3. 확정표의 값

규약은 모양을 정하고, 확정표는 값을 정한다. 규약이 값을 들고 있으면 버그로 본다.

## 여덟 축

일곱 규약 + 장르. 이 여덟이 안 정해지면 만든 것을 두 번 만들게 된다.

| 축 | 노트 | 안 정하면 |
|---|---|---|
| 장르 | [장르 문법 지도](장르%20문법%20지도.md) | 그 장르가 이미 치른 수업료를 다시 낸다 |
| 뷰(카메라) | [규약 - 뷰](규약%20-%20뷰.md) | 좌표계·정렬·스폰 경계·아트 규격이 전부 흔들린다 |
| 플랫폼 | [규약 - 플랫폼](규약%20-%20플랫폼.md) | 입력 계층과 UI 를 두 번 만든다 |
| 최적화 | [규약 - 최적화](규약%20-%20최적화.md) | 최적화가 "나중에"로 밀리고, 그 나중은 갈아엎기다 |
| 데이터 구조 | [규약 - 데이터](규약%20-%20데이터.md) | 콘텐츠 추가마다 C# 을 고치게 된다 |
| UI 구조 | [규약 - UI](규약%20-%20UI.md) | 화면이 늘 때마다 깊이·로드·해제가 매번 다르게 난다 |
| 프리팹 구조 | [규약 - 프리팹](규약%20-%20프리팹.md) | 프리팹이 MB 로 붓고, 한 화면 열면 전부 올라온다 |
| 아트 방향 | [규약 - 아트 방향](규약%20-%20아트%20방향.md) | 한 장씩은 괜찮은데 모으면 따로 놀고, 양산 뒤에 스타일을 바꾸면 전량 재작업이다 |

## 러너 — 프롬프트 하나가 0→7 을 멈추지 않고 돈다

입력은 둘이다: 장르 + 핵심 기획서. 선택으로 레퍼런스 재료 폴더.
그 다음은 단계 노트가 순서를 안다. 기본 흐름에 사람에게 되묻는 자리(HOLD)는 없다. 빈칸은 추정으로 채우고 스펙 추정 절에 쌓는다. 사람은 끝난 뒤 그 표의 상위 5행을 본다.

| # | 단계 | 노트 | 받는 것 | 내는 것 | 게이트 |
|---|---|---|---|---|---|
| 0 | 접수 | [단계 0 - 접수](단계%200%20-%20접수.md) | 장르 · 기획서 · (재료) | 스펙 확정표 절 · 스펙 추정 절 · `_Ref/*.tsv` | G0 · G1 · 병합 1·2 |
| 1 | 설계 | [단계 1 - 설계](단계%201%20-%20설계.md) | 확정표 · 추정 · TSV | 큐 · 스펙 계약 절 · 스펙 하네스 절 | G0-b · 완료 기준 전수 |
| 2 | 데이터 | [단계 2 - 데이터](단계%202%20-%20데이터.md) | 계약 스키마 · curve TSV | `_DataExporter/GameData/**` → `Assets/GameData/*.json` (Addressables `game_data`) | G3 |
| 3 | 아트 | [단계 3 - 아트](단계%203%20-%20아트.md) | 확정표 12행 · art/view TSV · 에셋 목록 | 스펙 아트 규격 절(방향 표 · 판정 표) · 스타일 프레임 · 라인업 · `_Art/**` + `.meta` · 프리팹(스크립트 0) | 아트 체크리스트 · 양방향 감사 · 아트 방향 판정 미측정 0 |
| 4 | UI | [단계 4 - UI](단계%204%20-%20UI.md) | 바인딩 계약 · ui TSV · UI 조각 | `_Art/Prefabs/UI/*.prefab` · 캡처 | G8 · 계약 위반 0 |
| 5 | 클라 | [단계 5 - 클라](단계%205%20-%20클라.md) | 계약 · 하네스 · JSON · 프리팹 · 큐 | 코드 · `Temp/runloop.report`(god) | G2 · G4 · G7 |
| 6 | QA | [단계 6 - QA](단계%206%20-%20QA.md) | 확정표 · 리포트 · 캡처 · 기준표 | 스펙 QA 절 · 스펙 실측 기준 절(밸런스 · 기준표) | G5 · G6 · G9 · 위반 0 |
| 7 | 플레이 | [단계 7 - 플레이](단계%207%20-%20플레이.md) | QA · 추정 · 큐 | 기록(그날 날짜 파일) · 보고 | 큐 잔여 = 슬라이스 밖 |

### 위상 — 선형이 아니다

```
0 접수 ──▶ 1 설계 ──┬──▶ 2 데이터 ──┐
                    ├──▶ 3 아트 ────┼──▶ 5 클라 ──▶ 6 QA ──▶ 7 플레이
                    └──▶ 4 UI ──────┘        ▲          │
                                             └── 위반 ──┘  (행마다 3회 한도)
```

- 2·3·4 는 트랙이다. 1 이 박은 계약(스키마 · 바인딩)이 셋을 잇는다. 계약에 빈칸이 있으면 그 트랙은 아직 열지 않는다 (G0-b)
- 3 은 프록시로 먼저 5 에 넘기고 진짜 아트는 병렬로 간다. 5 의 G4 는 프록시로 통과한다
- 6 의 위반은 큐 하단에 append 되어 5 로 돌아간다. 같은 행이 3회 걸리면 "미달"로 남기고 다음 행으로 간다
- 어느 단계든 같은 게이트를 3회 못 넘으면 그 지점에서 시도 3회를 보고하고 종료한다. 실패 정지이지 HOLD 가 아니다

### 진행 표기와 종료

- 응답마다 `[stage n/7 · 항목 k/전체]` 를 앞에 단다. 큐 항목이 끝나면 큐에서 지우고 다음으로 간다
- 노트는 단계마다 그 단계 노트 + 그 노트 "읽을 노트" 칸의 것을 연다. 개수 상한은 두지 않는다 (아래 노트 로딩 절)
- 종료는 7단계 보고 형식으로 한다. "완료"는 QA 미달 0 일 때만 쓴다

### 빈칸을 채우는 순서 — 전 단계 공통

1. 레퍼런스 실측 (`_Ref/*.tsv` 의 `adopt=채택`)
2. 해당 장르 노트 ([장르 문법 지도](장르%20문법%20지도.md) 에서 찾는다)
3. 규약 노트 기본값
4. 되돌리기 가장 싼 값

어느 출처든 스펙 추정 절에 한 행으로 남긴다: `# · 단계 · 항목 · 값 · 출처 · 틀리면 되돌아가는 비용`.
출처 없이 채운 값은 추정이 아니라 지어낸 값이고, 그런 값만이 재작업의 근거가 된다.

## 언제 여나

| 언제 | 무엇부터 |
|---|---|
| 새 게임·새 콘텐츠 개발 착수 | 위 러너 표의 0단계부터. [단계 0 - 접수](단계%200%20-%20접수.md) 가 13행을 기획서에서 추출한다. 되묻지 않는다 |
| 만든 것이 스펙대로 도는지 검증 | 같은 세트. [역할 - PD](역할%20-%20PD.md) 를 QA/게이트 역할로 연다 |
| 특정 파트 작업만 (수치·시스템·에셋) | 해당 역할 노트만 ([역할 - 기획](역할%20-%20기획.md) · [역할 - 클라](역할%20-%20클라.md) · [역할 - 아트](역할%20-%20아트.md)) |
| 규약 하나만 필요 (UI 한 화면 추가 등) | 해당 규약 노트만. 확정표를 다시 묻지 않는다 |
| 레퍼런스 게임이 있을 때 | [레퍼런스 해부](레퍼런스%20해부.md) — 다섯 시각으로 병렬 해부 → TSV |
| 낯선 장르 착수 | 해당 장르 노트. 노트가 없으면 레퍼런스 실측으로 먼저 쓴다 ([장르 문법 지도](장르%20문법%20지도.md)) |
| 사고 발생 | [함정 색인 - 개발](함정%20색인%20-%20개발.md) 에서 증상으로 찾는다. 새 사고는 일반화해 추가한다 |
| 개발과 무관한 단순 수정 | 이 세트를 펴지 않는다. 프로젝트 진입 파일이 기본 규칙이다 |

### 사람은 "게임 개발"이라는 말을 쓰지 않는다

어휘로 판정하지 않는다. 같은 요청이 사람마다 다르게 온다.

- "이런 게임 만들 수 있어?" · "뱀서류 하나 뽑자" · "로비 화면 붙여줘"
- "스킬 10개 추가" · "쿼터뷰로 갈까 탑다운으로 갈까" · "모바일로 낼 건데"

공통점은 "무엇을 플레이하게 만든다"는 것이다. 그러면 이 세트를 편다.

## 구성 — 폴더가 층이다

폴더 번호로 층을 읽고, 노트 이름의 분류 접두어로 그 노트가 어느 층인지 읽는다. 새 노트는 이 폴더 중 하나에 넣고 분류 접두어(`단계 N - ` · `역할 - ` · `규약 - ` · `양식 - ` · `함정 - ` · `장르 문법 - `)로 이름을 시작하는 것이 기본이다. 볼트 운영 규칙은 [문서 쓰는 법](문서%20쓰는%20법.md).

```
00 시작   Dev_Unity 지도 · Dev_Unity 원칙(강제 조항은 여기에만)
          개발 러너    이 노트 — 진입점 · 러너(단계 표 · 위상) · 노트 로딩 · 원장
          문서 쓰는 법  표기 규약 · 특정 게임 이야기를 적는 자리 · 볼트 운영
│
├── 10 단계   단계 0 - 접수 · 1 - 설계 · 2 - 데이터 · 3 - 아트 · 4 - UI · 5 - 클라 · 6 - QA · 7 - 플레이
│             노트마다 같은 모양 — 표(받는 것 · 읽을 노트 · 내는 것 · 게이트) + 절(하는 일 · 막혔을 때 · 자주 틀리는 것)
│             (카테고리 하나를 고치려면 그 단계 노트 하나만 연다. 러너는 안 건드린다)
│
├── 20 역할   (지식 + 실행. 각자 자기 노트의 규약대로 일한다)
│    ├── 역할 - PD     오케스트레이터 — 착수 13행 · 추출 계약 · 트랙 · 게이트 · 원장
│    ├── 역할 - 기획   코어 루프 · 스펙 · 수치/밸런스 · 콘텐츠 축 · 네이밍
│    ├── 역할 - 클라   부트 순서 · 수명주기 · 풀링 · 검증 하네스 · 에디터 자동화
│    └── 역할 - 아트   에셋 규격 · 반입 절차 · 폴더링/어드레서블 · 씬 · VFX
│
├── 30 분석
│    └── 레퍼런스 해부  착수 전 병렬 해부 — 재료 규약 · 다섯 시각 배분 · 병합 게이트
│
├── 40 규약   (트렁크. 게임 종류를 모른다. 확정표가 값을 채운다)
│    ├── 규약 - 뷰          뷰/카메라 — 좌표계 · 정렬 · 스폰 경계 · 뷰별 규약
│    ├── 규약 - 플랫폼      입력 · 해상도 · 세이프에리어 · 빌드 설정 · 예산표
│    ├── 규약 - 최적화      처음부터 넣는 것 / 재고 나서 하는 것 · 측정법
│    ├── 규약 - 데이터      SSOT · 모듈 조립 · 굽기 · Registry
│    ├── 규약 - UI          Window/Component 2계층 · WindowType 깊이 · 풀링 · 재활용 스크롤
```

## 표본은 폴더가 아니라 잰 값이다

지어낸 수치는 상식과 구분되지 않는다 ([함정 65](함정%20-%20판단%20검증.md)).

표본은 사용자가 지목한 실제 레퍼런스 게임에서 잰 TSV 다. 절차는 [레퍼런스 해부](레퍼런스%20해부.md).
출처가 붙지 않은 수치는 표본이 아니라 추측이다.

## 역할이 곧 시각이다

같은 것을 봐도 역할마다 봐야 하는 것이 다르다. 역할을 연기할 때는 그 시각으로만 보는 것이 기본이다.

| 역할 | "레벨업 3택1"을 볼 때 |
|---|---|
| PD | 이게 이번 슬라이스에 있어야 하나? 게이트 통과 조건이 숫자로 박혀 있나? |
| 기획 | 후보 풀 규칙이 표로 있나? 중복 허용? 가중치? 값은 데이터 파일에 있나? |
| 클라 | 일시정지 중 다른 시스템이 새나? 풀 재사용 시 상태가 남나? 하네스로 잡히나? |
| 아트 | 카드가 세이프에리어 안인가? 폰트에 글리프가 있나? 터치 타깃이 충분히 큰가? |

한 명이 전 역할을 연기한다. 역할을 바꿀 때는 그 역할의 노트를 열고 그 시각으로 본다.

## 노트 로딩 — 단계 노트가 적은 것은 전부 연다

기본은 모든 노트를 상시 열지 않고, 그 단계 노트의 "읽을 노트" 칸에 적힌 노트는 개수와 상관없이 전부 여는 것이다.
"몇 개까지만" 같은 상한은 두지 않는다. 이유: 상한이 있으면 필요한 노트를 안 연 채로 단계가 지나가고, 그게 가장 큰 사고로 이어진다.
프로젝트 문서 감사기(`.claude/tools/audit_docs.py`)가 "읽을 노트"의 노트가 실제로 있는지를 착수 전에 센다.

| 단계 | 여는 노트 |
|---|---|
| 어느 단계든 | 그 단계 노트(`단계 N - …`) + 그 노트 "읽을 노트" 칸의 노트 전부 |
| 착수 / 확정 | [역할 - PD](역할%20-%20PD.md) + 해당 장르 노트([장르 문법 지도](장르%20문법%20지도.md) 에서 찾는다) |
| 레퍼런스 해부 | [레퍼런스 해부](레퍼런스%20해부.md) + 각 파트가 자기 역할 노트 |
| 뷰·카메라 결정 | [규약 - 뷰](규약%20-%20뷰.md) (+ 같은 뷰 레퍼런스의 `view.tsv`) |
| 플랫폼·예산 결정 | [규약 - 플랫폼](규약%20-%20플랫폼.md) |
| 데이터 설계 | [규약 - 데이터](규약%20-%20데이터.md) + [역할 - 기획](역할%20-%20기획.md) |
| UI 설계·구현 | [규약 - UI](규약%20-%20UI.md) + [규약 - 프리팹](규약%20-%20프리팹.md) + [양식 - UI 프리팹](양식%20-%20UI%20프리팹.md)(굽을 때) |
| 시스템 구현 | [역할 - 클라](역할%20-%20클라.md) + [양식 - 하네스](양식%20-%20하네스.md) (+ [함정 색인 - 개발](함정%20색인%20-%20개발.md) 훑기) |
| 에셋 작업 | [역할 - 아트](역할%20-%20아트.md) + [양식 - 아트 생성기](양식%20-%20아트%20생성기.md) |
| 성능이 목표를 못 맞춤 | [규약 - 최적화](규약%20-%20최적화.md) |
| QA / 게이트 | [역할 - PD](역할%20-%20PD.md) 게이트 절 + 원장 |

## 원장 — 프로젝트마다 만드는 것은 셋이고, 시제로 나뉜다

원장은 볼트가 아니라 게임 프로젝트 저장소에 있다. 볼트는 어느 게임에도 쓰는 지침이고, 게임 하나의 상태는 그 원장에 있다.

| 이름 | 시제 | 규칙 | [예시] 파일 |
|---|---|---|---|
| 큐 | 미래 | 미완료만. 착수 전에 세우고 항목이 끝나면 지운다. 100줄 이하 | `TASKS.md` |
| 스펙 | 현재 | 이 게임의 확정값과 실측값. 절: 확정표 · 추정 · 계약 · 하네스 · 아트 규격 · 실측 기준 · QA | `.claude/spec.md` |
| 기록 | 과거 | 큐를 비운 날 봉인. 확정 / 산출 / 실측 / 발견 4칸. 하루 = 파일 하나 | `.claude/history/YYYY-MM-DD.md` |

프로젝트 도구 명령과 보호 경로는 진입 파일([예시] `CLAUDE.md`)에 둔다.

한 파일이 두 시제를 담으면 과거가 미래를 덮고, 다음 할 일이 묻힌다.
재사용할 수 있는 교훈은 기록이 아니라 함정 노트로 보낸다([함정 색인 - 개발](함정%20색인%20-%20개발.md)). 기록에는 "함정 N" 한 줄만 둔다.

### 큐 전이

| 시점 | 하는 일 |
|---|---|
| 착수 전 | 할 일을 전부 리스트업하고 순서를 정한다. 항목마다 판정 가능한 완료 기준 |
| 진행 중 | 하나씩. `[stage n/7 · 항목 k/전체]` 로 표시. 단계마다 컴파일·검증·실측 후 다음으로 |
| 부족 발견 | 그 자리서 채우고 큐 하단에 append. 지금 항목을 중단하지 않는다 |
| 항목 완료 | 큐에서 지운다 + 오늘 기록에 네 칸으로 |
| 큐 소진 | 기록을 봉인하고 7단계 형식으로 보고 |

완료 기준은 "구현했다"가 아니라 "돌려서 쟀다"다. 미측정은 통과가 아니다. 막힌 단계는 건너뛰지 않는 것이 기본이다. 이유: 건너뛴 단계의 산출물을 받는 다음 단계가 판정 기준을 잃는다.
