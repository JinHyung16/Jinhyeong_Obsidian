# 양식 - 하네스

검증 하네스의 요청 파일 · 리포트 · 에디터 태스크가 정확히 어떤 파일 · 어떤 줄로 생겼는지 정하는 틀이다. 하네스를 만들거나, 요청을 쓰거나, 리포트를 읽을 때 편다.

[역할 - 클라](역할%20-%20클라.md) 검증 하네스 문화 절이 "무엇을 재나"를 정하면, 이 노트는 "요청과 결과가 정확히 어떤 파일 · 어떤 줄로 생겼나"를 정한다.
프로젝트의 실제 키 목록은 스펙 하네스 절이 든다. 여기는 모양만.
칸 순서 · 섹션 머리 · 로그 첫 줄과 끝 줄은 파서와 읽는 쪽이 자리로 읽는다. 그래서 모양은 그대로 두는 것이 기본이고, 아래 각 절에 왜 그 모양인지 적는다.

## 왜 파일인가

사람이 클릭하지 않아도 돌아야 한다. 요청은 파일 하나를 쓰는 것이고 결과도 파일 하나가 생기는 것이다.
브리지가 없어도, 배치모드여도, 다른 프로세스에서도 같은 길이다. `Temp/` 는 에디터 기동 때 비워지므로 요청이 남아 도는 일이 없다.

## 요청 파일 — `Temp/runloop.request`

```
<모드>[:<초>[:<캐릭터>[:<화면>]]]

[예시]
god               경로 검증. 무적 · 기본 시간
mortal:820        밸런스. 무적 끄고 820초 (또는 사망까지)
god:60:2          캐릭터 2번으로 60초
god:15:1:skill    15초 뒤 로비 skill 탭을 촬영하고 종료   ← UI 촬영용
```

- 첫 칸이 모드. 경로 검증은 `god`, 밸런스는 `mortal` 로 나눠 돌리는 것이 기본이다. 이유: 섞으면 둘 다 못 잰다.
- 칸은 뒤에서부터 생략하고 순서는 그대로 둔다. 이유: 파서가 자리로 읽는다.
- 파일이 생기면 감시자가 집어 `Temp/runloop.active` 로 옮긴다. 감시는 항상 걸어 두는 것이 기본이다. "플레이 중이 아닐 때만" 같은 조건은 감시자 밖에 두지 않는다. [함정 49](함정%20-%20구조%20설계.md)

## 리포트 — `Temp/runloop.report`

섹션 머리는 `[이름]` 이고 순서가 고정이다. 이유: 읽는 쪽([단계 6 - QA](단계%206%20-%20QA.md))이 머리로 찾는다.

```
[예시] 섹션 순서는 고정, 값은 이 프로젝트 실측
[요청]   god:60:2                          ← 무엇을 요청했나 그대로
[무효]   (없음 | 사유)                      ← 워치독. 경과 프레임·게임 시간이 안 흘렀으면 사유를 적고 아래 숫자는 무효
[진단]   스폰=58 부착스킬=3 팀=Friend 테이블=파츠27/옵션159/스킬27 렌더러이상=0 플레이어y=0.08
[무적]   킬=58 Lv=6 파츠=3 시너지=1 생존적=12 FPS=71       ← god 모드 실측
[필멸]   생존=615s 사망라운드=11 구간최저HP=27%             ← mortal 모드 실측
[보스]   등장=1 처치=1 체력=3888
[자해]   0회                                                 ← 팀 검사 회귀
[클리어] 보스 격파 / 사망 / 시간 만료
[캡처]   Temp/runloop_60.png Temp/runloop_end.png
[중단]   (없음 | 사유)                                       ← 하네스가 스스로 멈춘 이유
```

| 섹션 | 규칙 |
|---|---|
| `[무효]` | 제일 위. 워치독이 실패하면 아래 전부를 무효로 읽는다. 없으면 `(없음)` 을 명시 — 빈 줄은 "안 잰 것"과 구분이 안 된다 |
| `[진단]` | 판정에 필요한 상태 전부. "킬 0"만 있으면 원인이 열 갈래다 — 스폰 수 · 부착 스킬 · 팀 · 테이블 로드 · 렌더러 이상 · 좌표 |
| 실측 섹션 | `키=값` 나열. 키 이름은 큐 항목 제목(루프 화살표)과 같다 — [단계 1 - 설계](단계%201%20-%20설계.md) 가 정한 이름을 [단계 5 - 클라](단계%205%20-%20클라.md) 가 그대로 찍는다 |
| `[캡처]` | 파일명에 시점을 넣는다(`_60`, `_end`, `_<탭>`). 촬영 시점은 `EndGame()` 뒤 — 결과 화면을 한 번도 제대로 못 본 사고가 있었다 |
| 단위 | 초 `s` · 퍼센트 `%` · 그 외 정수. 단위 없는 숫자는 반려 |

리포트는 덮어쓴다. 직전 결과가 필요하면 6단계가 스펙 실측 기준 절로 옮겨 둔 것을 본다.

## 에디터 태스크 — `Temp/editor.task`

플레이가 필요 없는 작업. 한 줄에 태스크 이름 하나. 결과는 `Temp/editor.task.log`.

```
[예시] 태스크 표 — EditorTaskRunner 가 이 표를 든다. 새 태스크 = 여기 한 줄 + 메서드 하나
refresh    에셋 갱신 + 컴파일 대기
build      아트 프리팹 굽기 + 어드레서블 등록
validate   데이터 검증 (G3)
nodes      노드 어휘 검사 → config.UnimplementedNodes 갱신
ui         UI 프리팹 굽기 (양식 - UI 프리팹)
prefabs    프리팹 감사 (규약 - 프리팹 검사 목록 + 양식 4줄)
```

- 태스크 메서드는 인자 없는 public static 이 기본이다. 이유: 배치모드 `-executeMethod` 로도 같은 것을 부른다.
- 로그 첫 줄은 `[태스크] 시작`, 마지막 줄은 `[태스크] 완료 <숫자>` 또는 `[태스크] 실패 <사유>`. 중간에 죽으면 "완료"가 없으므로 실패로 읽는다.
- 컴파일 중에는 태스크를 받지 않는 것이 기본이다. 이유: 도메인 리로드가 실행 중인 태스크를 통째로 날린다. [함정 33](함정%20-%20에디터%20자동화.md) · [함정 38](함정%20-%20하네스%20측정.md)

UI 프리팹 양식은 [양식 - UI 프리팹](양식%20-%20UI%20프리팹.md), 프리팹 검사 목록은 [규약 - 프리팹](규약%20-%20프리팹.md).

## 하네스가 지키는 것

규약 요약이다. 상세는 [역할 - 클라](역할%20-%20클라.md).

- 회피를 한다. 이유: "가장 가까운 아이템으로 직진"은 밸런스가 아니다. [함정 34](함정%20-%20하네스%20측정.md)
- 콘텐츠 id 는 하드코딩하지 않고 참조를 한 곳에 둔다. 이유: 시스템을 갈아엎으면 하네스만 0 을 보고한다.
- 측정이 도는 동안에는 코드를 고치지 않는 것이 기본이다.
- 룩 판정은 브리지가 붙은 화면 캡처로 한다. 이유: 브리지 없이 배치모드로 돌린 헤드리스는 화면을 못 본다.

## 검사

| 검사 | 실패 조건 |
|---|---|
| 섹션 순서 | `[무효]` 가 첫 실측 섹션보다 아래에 있음 |
| 키 이름 | 실측 섹션의 키가 스펙 하네스 절 표에 없음 |
| 단위 | 숫자 뒤에 단위 없음 (정수 카운트 제외) |
| 캡처 | `[캡처]` 의 파일이 실제로 없음 |
