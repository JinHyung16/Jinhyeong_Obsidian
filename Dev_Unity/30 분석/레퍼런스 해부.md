# 레퍼런스 해부

레퍼런스 게임을 재료 · 해부 · 개발 중 재료 요청 세 갈래로 다루는 지침이다. 착수 때 레퍼런스를 다섯 시각으로 해부할 때, 그리고 개발 중 룩·감 판정 재료가 없을 때 편다.

## 언제 여나

| 언제 | 어느 절 |
|---|---|
| 확정표를 받은 뒤, 스펙을 쓰기 전 (레퍼런스 게임이 있을 때) | "재료 규약" → "배분" → "병합 게이트" |
| 개발 중, 룩·감을 판정해야 하는데 재료가 없을 때 | "개발 중에 재료가 필요해지는 순간" |

레퍼런스 게임이 아예 없으면 착수 해부는 건너뛰고 바로 [역할 - 기획](역할%20-%20기획.md) 으로 간다.
단, "개발 중에 재료가 필요해지는 순간" 절은 레퍼런스 게임이 없어도 적용된다. 베낄 대상이 없는 것과 볼 것이 없는 것은 다르다.

## 왜 여기만 병렬인가

이 세트에서 병렬 팬아웃을 쓰는 단계는 여기 하나뿐이다. 이유는 셋:

1. 읽기 전용이다 — 아무것도 안 고치니 충돌할 게 없다
2. 다섯 시각이 서로 다른 것을 본다 — 같은 화면을 봐도 기획은 곡선을, 아트는 규격을 본다.
   한 사람이 순서대로 보면 앞서 본 시각에 물들어 나머지가 흐려진다
3. 합칠 때 싸울 일이 없다 — 각자 다른 칸을 채우고 PD가 표 하나로 엮는다

### "해부의 병렬"과 "구현의 트랙"은 다른 것이다

여기서 말하는 병렬은 읽기 전용 팬아웃이다. 넷이 같은 재료를 동시에 본다.

구현 단계에서 트랙을 겹치는 것(기획 데이터 ∥ 클라 기능 ∥ UI 프리팹)은 막는 것이 아니라 권장하는 것이고, 그건 [역할 - PD](역할%20-%20PD.md) "트랙" 절이 다룬다.
차이는 하나다 — 해부는 계약이 필요 없고(각자 다른 칸을 채운다), 구현 트랙은 계약이 먼저 있어야 한다(마지막에 연결해야 하므로).

### 이음매는 나눠 갖지 않는다

파트별로 이음매까지 나누면 아무도 이음매의 주인이 아니다 ([함정 63](함정%20-%20작업%20방식.md)).

기본은 이음매(부트 순서·로드 순서·씬 전환·저장 스키마)를 한 명이 쥐고 순차로 가는 것이다.
트랙으로 겹쳐도 되는 것은 산출물이 갈리는 것뿐이다.
판단 기준 한 줄: "A가 실패해도 B가 그대로 맞는가?" 아니면 순차다.

## 재료 규약 — 없으면 일반론이 나온다

분석하는 쪽은 그 게임을 플레이할 수 없다. 준 재료만큼만 실측이 된다.

| 재료 | 이걸로 잴 수 있는 것 | 못 재는 것 |
|---|---|---|
| 텍스트 공략·위키 | 시스템 구조, 성장 축, 해금 조건, 용어 | 화면 밀도, 타이밍, 손맛 |
| 스크린샷 | 화면당 정보량, UI 배치, 아트 규격, 팔레트 | 전이·연출 타이밍 |
| 영상 프레임 (일정 간격 추출) | 연출 길이, 스폰 밀도 변화, 피드백 지연 | 조작 감각 |
| 직접 플레이 노트 (사람이 적어 줌) | 손맛, 지루한 구간, 헷갈린 지점 | — |

재료 없이 돌린 분석은 실측이 아니다. "대체로 이런 장르는…" 으로 시작하는 문장이 나오면 그건 상식이고, 상식은 [장르 문법 지도](장르%20문법%20지도.md) 와 장르 노트에 이미 있다.
러너(HOLD 0)에서는 재료가 없어도 멈추지 않는다 — [단계 0 - 접수](단계%200%20-%20접수.md) 순서대로 웹에서 재료를 모으고 출처를 검증한 뒤,
그래도 없으면 장르 노트 값을 쓰되 그 행은 실측이 아니라 추정으로 표시한다. 피할 것은 상식을 실측인 척 적는 것 하나다.

재료는 확인한 것만 넘기고, 출처가 그 게임이 맞는지부터 검증한다 ([함정 64](함정%20-%20작업%20방식.md)).

### 아트 재료 — 많이보다 골라서, 장마다 한 줄

아트는 레퍼런스를 많이 받는 것도, 의도만 받는 것도 기본값이 아니다. 기본은 짧은 의도 + 골라 낸 레퍼런스 몇 장 + 장마다 무엇을 가져올지 한 줄이다.

| 받는 방식 | 생기는 일 |
|---|---|
| 레퍼런스를 많이 | 스타일이 섞여 평균이 나온다. 무난하고 개성이 없다. 어느 장을 따를지 에이전트가 고르게 된다 |
| 의도만 | 빈칸이 무난한 기본값으로 채워진다. 이것이 게임과 안 어울리는 가장 흔한 경로다 |
| 의도 + 골라 낸 레퍼런스 + 한 줄씩 | 방향 표를 채울 근거와 잴 대상이 같이 온다 |

사람에게 요청하는 입력 형식:

```
[예시]
의도
  원하는 인상 : 귀엽다 · 경쾌하다 · 한눈에 읽힌다
  피할 인상   : 공포 · 사실적
  플랫폼/타깃 : 모바일 세로 · 캐주얼
레퍼런스 (3~5장)
  A.png  가져올 것: 팔레트 · 채도 대역      가져오지 말 것: 캐릭터 비율
  B.png  가져올 것: 적이 배경에서 튀는 정도  가져오지 말 것: UI 모양
  C.png  가져올 것: 이펙트 밀도와 크기감
```

- 레퍼런스는 분위기 자료보다 측정 재료로 쓴다. 방향 표의 값(팔레트 · 외곽선 · 명암 · 배경 대비)을 같은 방법으로 잰다 ([규약 - 아트 방향](규약%20-%20아트%20방향.md) 방향 표 절)
- 실제 플레이 화면 캡처가 기본이다. 이유: 원화 · 키 아트 · 마케팅 이미지는 인게임 표시 크기와 달라 텍셀 밀도 · 가독성을 잴 수 없다. 원화는 톤 키워드 판정에만 쓴다
- 한 게임에 표현 방식 한 계열로 받는다 (도트면 도트끼리). 계열이 섞여 오면 어느 쪽을 기준으로 할지 먼저 정하고 스펙 추정 절에 적는다
- "가져오지 말 것"이 없는 레퍼런스는 전부 가져올 것으로 읽힌다. 비어 있으면 에이전트가 채워 추정으로 적는다
- 받지 못했으면 멈추지 않는다. 장르 노트 · 기획서 톤으로 방향 표를 추정으로 채우고, 스타일 프레임 1장을 사람 확인 목록에 올린다

## 개발 중에 재료가 필요해지는 순간 — 스스로 알아채고 묻는다

착수 때만 재료가 필요한 게 아니다. 구현 도중에도 판정 기준이 룩·감에 있는데 재료가 없는 순간이 온다.
그때 말없이 "적당히" 만들면 그게 나중에 전부 재작업이 된다.

### 신호 — 하나로 수렴한다

"이걸 숫자로 못 적겠는데, 못 적는 이유가 몰라서가 아니라 본 적이 없어서다"

"모르는 것"은 재료 없이도 정할 수 있다(기획이 정하면 된다).
"본 적이 없는 것"만 재료가 필요하다. 둘을 구분하는 게 이 절의 전부다.

### 트리거 5종 — 이 자리에서 울리면 묻는다

| 트리거 | 구체 신호 | 필요한 재료 형태 |
|---|---|---|
| 뷰 확정 (G9) | 각도·거리·화면 대비 캐릭터 비율을 숫자로 못 적겠다 | 게임플레이 스크린샷 1~2장 |
| 연출 밀도·타이밍 | "몇 초"·"동시 몇 개"를 못 적겠다 | 영상 또는 프레임 추출본 |
| UI 정보량·배치 | 이 화면에 무엇을 몇 개 놓을지 못 정하겠다 | 해당 화면 스크린샷 |
| 아트 규격 | 팔레트 폭·외곽선·애니 프레임 수를 못 정하겠다 | 플레이 스크린샷 우선 · 스프라이트 시트 (원화는 톤 판정에만. 형식은 위 아트 재료 절) |
| 손맛·조작감 | 선입력 버퍼·코요테 타임 같은 관용 수치를 못 정하겠다 | 사람의 플레이 노트 (영상으로 안 잡힌다) |

마지막 행이 특히 중요하다 — 손맛은 영상으로 못 잰다. 사람이 직접 해 보고 적어 줘야 하는 유일한 재료다.
영상을 받아 놓고 "손맛을 쟀다"고 하면 그건 미측정이다.

### 물을 때의 규격 — 세 줄로 묻는다

```
[예시]
1. 판정하려는 것 : 레벨업 선택 팝업에 카드를 3장 놓을지 4장 놓을지
2. 필요한 형태   : 해당 화면 스크린샷 1장 (세로 기준). 영상이면 더 좋다
3. 없으면        : 3장으로 가정하고 진행한다. 나중에 4장으로 바꾸면
                   카드 폭·터치 타깃·후보 풀 최소 개수가 같이 바뀐다
```

기본은 3번(없으면 어떻게 하나)을 붙이는 것이다. 이유: 3번이 빠진 요청은 사람을 멈춰 세운다.

### 묻고 멈추지 않는다

- 재료에 안 걸린 작업부터 전부 끝낸다
- 가정으로 진행한 것은 원장에 "가정"이라고 적는다 (측정 등급: 미확인)
- 진짜 블로킹으로 세우는 것은 되돌리기가 비싼 축뿐이다 — 확정표 2행(뷰)·3행(플랫폼)처럼 바뀌면 아래가 전부 다시인 것

### 묻지 않아도 되는 때

못 묻는 것보다 과잉 요청이 더 자주 사고를 낸다. 아래면 묻지 않고 만드는 게 기본이다.

- 장르 노트에 이미 답이 있다 — 상식은 재료가 아니다
- 가정으로 만들고 나중에 조정하는 비용이 싼 것 (수치 하나 · 색 하나)
- 이미 받은 재료로 잴 수 있는 것 (재료 규약 표를 먼저 본다)
- 이번 슬라이스 범위 밖의 것 — 그건 그 슬라이스를 열 때 묻는다

그리고 한 번에 몰아서 묻는다. 한 작업 중에 세 번 나눠 물으면 세 번 멈춘다.

### 이 절은 실제 개발로 자란다 — 캘리브레이션 슬롯

트리거 표는 적을 수 있지만 하한선은 몇 번 틀려 봐야 잡힌다. 회차마다 원장에 적는다.

| 적을 것 | 그러면 고칠 곳 |
|---|---|
| 요청했는데 결국 안 쓴 재료 | 그 트리거의 하한선을 올린다 (묻지 말았어야 했다) |
| 안 물어서 두 번 만든 것 | 그 자리를 트리거 표에 행으로 추가한다 |
| 받았는데 그걸론 못 쟀던 것 | "필요한 재료 형태" 칸을 고친다 (형태를 잘못 요청했다) |

## 배분 — 다섯 시각

같은 레퍼런스를 동시에 본다. 각자 자기 역할 노트의 시각으로만 본다.

| 파트 | 무엇을 캐 오나 |
|---|---|
| 기획 [역할 - 기획](역할%20-%20기획.md) | 코어 루프 한 문장 · 성장 축과 곡선 · 세션 길이 · 선택지 구조(후보/가중치/중복) · 재화 종류 |
| 뷰 [규약 - 뷰](규약%20-%20뷰.md) | 차원·투영·각도·카메라 자유도 · 정렬 방식 · 화면에 보이는 월드 범위 · 캐릭터 대비 화면 비율 |
| 클라 [역할 - 클라](역할%20-%20클라.md) | 그 루프를 돌리려면 엔진에 없으면 안 되는 것 · 동시 오브젝트 규모 · 데이터로 뺄 수 있는 축 |
| UI/UX | 화면당 정보 개수 · 조작 동선(엄지 반경) · 피드백 지연 · 정보 우선순위 · 화면 종류 수와 밴드 |
| 아트 [역할 - 아트](역할%20-%20아트.md) | 해상도·픽셀 밀도 · 팔레트 폭 · 애니 프레임 수 · 외곽선 규칙 · 부위 피벗 |

UI/UX 전용 노트는 없다. [규약 - UI](규약%20-%20UI.md)(구조)와 [역할 - 기획](역할%20-%20기획.md)(정보 우선순위)을 겹쳐 보되 산출물은 따로 낸다.
이유: 아트에 섞으면 "예쁜가"에 묻혀 "쓸 수 있나"가 사라진다.

뷰 시각은 새로 추가된 자리다. 착수 확정표 2행을 채우는 것이 이 칸이고, 스크린샷 한 장으로 가장 많이 잴 수 있는 칸이기도 하다 —
캐릭터 키가 화면 높이의 몇 %인가, 지면 격자가 몇 도로 기울었나, 카메라가 도는 장면이 있나.

## 산출물은 TSV 다 — 마크다운 표가 아니다

각 파트는 TSV 파일 하나를 낸다. 문장으로 흘려 쓰면 병합할 수 없고, 마크다운 표로 쓰면 옮겨 적는 단계가 한 번 더 생긴다.

왜 TSV 인가

| 이유 | 마크다운 표로는 |
|---|---|
| 스프레드시트에 그대로 붙는다 → 정렬·피벗으로 곡선이 눈에 보인다 | 눈으로 훑는 수밖에 없다 |
| 행 단위 diff — 회차마다 무엇이 바뀌었는지가 보인다 | 표 전체가 한 덩어리로 바뀐 것처럼 보인다 |
| 그대로 데이터 모듈로 굽는다 ([규약 - 데이터](규약%20-%20데이터.md)) | 사람이 다시 옮겨 적는다 = 옮겨 적다 틀린다 |
| 열이 고정이라 네 파트가 같은 칸을 채운다 | 파트마다 표 모양이 갈려 병합이 수작업이 된다 |

### 파일 배치

```
_Ref/<게임명>/
   design.tsv     코어 루프 · 성장 축 · 세션 · 선택지 · 재화
   view.tsv       차원 · 투영 · 각도 · 화면 대비 캐릭터 비율 · 정렬
   client.tsv     동시 오브젝트 규모 · 없으면 안 되는 것 · 데이터로 뺄 축
   ui.tsv         화면당 정보 개수 · 동선 · 피드백 지연 · 화면 종류와 밴드
   art.tsv        해상도 · 팔레트 폭 · 애니 프레임 수 · 외곽선 · 피벗 · 광원 · 텍셀 밀도 · 역할별 배경 대비 (항목은 규약 - 아트 방향 방향 표)
   curve_*.tsv    곡선만 따로 (아래)
```

### 열 규격 — 여덟 칸 고정

```
axis	item	observed	value	unit	source	adopt	cost
```

| 열 | 무엇 | 반려 기준 |
|---|---|---|
| `axis` | 무엇에 대한 것인가 (`성장` · `스폰` · `화면밀도` · `팔레트`…) | 빈 칸 |
| `item` | 잰 항목 한 개 | 두 개를 한 행에 |
| `observed` | 레퍼런스에서 실제로 본 것 | 출처 없는 관찰 |
| `value` | 잰 값. 못 쟀으면 `미측정` | 어림값을 실측인 척 |
| `unit` | `초` · `개` · `%` · `px` · `도` · `-` | 단위 없는 숫자 |
| `source` | `shot03` · `vid 1:24` · `note` · `wiki:URL` | 빈 칸 |
| `adopt` | `채택` · `변형` · `버림` + 이유 한 줄 | "좋아 보임" |
| `cost` | 가져올 때 드는 것 (신규 시스템 · 에셋 종류 · 데이터 축) | 빈 칸 |

"레퍼런스처럼"이라고 적기보다 레퍼런스에서 잰 값을 적는다 ([역할 - 기획](역할%20-%20기획.md) 과 같은 규칙).

### 곡선은 따로 — `curve_<축>.tsv`

성장·스폰·난이도는 점 하나가 아니라 점의 나열이다. 관찰 표에 억지로 넣으면
한 행에 "1렙 100, 2렙 140, 3렙 190…"처럼 뭉쳐 들어가고, 그 순간 정렬도 굽기도 못 한다.

```
axis	x	y	unit	source
성장	1	100	hp	shot02
성장	2	140	hp	shot02
스폰	60	4	마리/초	vid 0:60
```

이 파일이 [역할 - 기획](역할%20-%20기획.md) 의 곡선 확정 입력이 되고, 확정된 곡선이 [규약 - 데이터](규약%20-%20데이터.md) 의 데이터 모듈로 그대로 구워진다. 사람이 옮겨 적는 구간이 없다.

### 미측정 행은 남긴다

기본은 `value` 가 `미측정`인 행을 지우지 않는 것이다. 이유: 지우면 "재 봤는데 못 쟀다"와 "아예 안 봤다"가 구분되지 않는다.
병합 게이트 3번이 보는 것이 바로 이 행들이다.

## 병합 게이트 — PD가 확인하는 것

넷이 다 끝나면 PD가 표 하나로 합친다. 합치기 전에 확인한다.

1. 네 파트가 같은 게임을 봤는가 — 출처가 엇갈리면 전부 폐기하고 재료부터 다시
2. 충돌하는 관찰이 있는가 — 기획은 "3택1", UI는 "4택1" 같은 불일치. 재료로 되돌아가 판정
3. 미측정이 어디인가 — 미측정 칸이 스펙의 핵심이면 재료를 더 모은다([단계 0 - 접수](단계%200%20-%20접수.md) 재료 2).
   그래도 못 재면 추정으로 채우되 스펙 추정 절 맨 위에 비용과 함께 올린다. 피할 것은 미측정을 실측처럼 적는 것이다
4. 가져올 것의 총 비용이 슬라이스에 들어가는가 — 안 들어가면 여기서 자른다. 구현 중에 자르면 이음매가 깨진다

게이트를 통과하면 그 표가 스펙의 입력이 된다. 통과 전에는 스펙을 쓰지 않는 게 기본이다.

## 흔한 실패

- 레퍼런스를 베낄 대상으로 삼음 — 분석은 베끼려는 게 아니라 우리와 다르게 갈 곳을 정하려는 것이다. "같게 간다"가 전부인 칸은 분석하지 않은 것과 같다
- 네 파트가 같은 결론을 냄 — 시각이 안 갈렸다는 뜻이다. 대개 한 사람이 먼저 결론을 내고 나머지가 따라간 경우다. 각 파트는 다른 파트의 산출물을 보기 전에 낸다
- 분석이 스펙을 대신함 — 분석은 입력이지 결정이 아니다. 수치를 확정하는 것은 [역할 - 기획](역할%20-%20기획.md), 넣을지 말지는 PD
