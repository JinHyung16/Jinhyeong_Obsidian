# 단계 1 - 설계

확정표 → 계약 → 작업 큐. 확정표가 나온 뒤, 무엇을 어떤 순서로 먼저 못 박고 만들지 정할 때 편다.
확정표는 무엇을 만들지 정하고, 이 단계는 순서를 정한다. 큐 없이 착수하면 "일단 되는 것부터"가 되고 그 순서는 이음매에서 무너진다.

| 칸 | 내용 |
|---|---|
| 받는 것 | 스펙 확정표 절, 추정 절 · `_Ref/<게임>/*.tsv` |
| 읽을 노트 | [역할 - PD](역할%20-%20PD.md) · [역할 - 기획](역할%20-%20기획.md) · [규약 - 데이터](규약%20-%20데이터.md) · [규약 - UI](규약%20-%20UI.md) · [양식 - CommonConfig](양식%20-%20CommonConfig.md) · [규약 - 패키지](규약%20-%20패키지.md) |
| 내는 것 | 큐 · 스펙 계약 절, 하네스 절 |
| 게이트 | G0-b 계약 빈칸 0 · 큐 항목마다 완료 기준 존재 · 루프 밖 항목이 슬라이스 위에 없음 |

## 하는 일

읽을 노트에서 볼 곳:

- [역할 - PD](역할%20-%20PD.md) 트랙 · 계약 · 슬라이스 · 게이트
- [역할 - 기획](역할%20-%20기획.md) 코어 루프 · 스키마
- [규약 - 데이터](규약%20-%20데이터.md) 조합형 설계
- [규약 - UI](규약%20-%20UI.md) 바인딩 계약
- [양식 - CommonConfig](양식%20-%20CommonConfig.md) 전체
- [규약 - 패키지](규약%20-%20패키지.md) 전체

1. 코어 루프(9행)를 화살표로 분해한다. 화살표 하나 = 시스템 하나. 루프가 둘(런 내 / 메타)이면 각각 적고 접점을 명시한다
2. 슬라이스를 자른다. 루프 안의 화살표만 슬라이스다. 설정·도감·상점처럼 루프에 없는 것은 큐 하단 "슬라이스 밖" 절로 보낸다
3. 계약을 쓴다 → 스펙 계약 절. 확정표 값이 갈 자리는 [양식 - CommonConfig](양식%20-%20CommonConfig.md) 필수 절 6개다. 새 게임이면 `CommonConfig.cs` 를 이 양식으로 먼저 채운다
   - 데이터 스키마: 콘텐츠 종류별 필드명 · 타입 · 단위 · enum 목록 · 필수 · 기본값 + 기대값 시나리오 1건
   - 화면별 바인딩 계약: 화면 이름 · 밴드 · 경로 상수 소유 클래스 · 노드 계층 · 컴포넌트/필드명 · Listener 시그니처
   - 에셋 목록: 역할 단위("플레이어 4방향 걷기" "적 3종 걷기+대기" "FX 키 N종"). 규격은 [단계 3 - 아트](단계%203%20-%20아트.md) 가 채운다
4. 하네스 시나리오를 정한다 → 스펙 하네스 절
   - 경로 검증(무적) · 밸런스(필멸) · 회귀(기준표) 셋을 분리한다
   - 리포트에 들어갈 진단 항목: 스폰 수 · 부착 스킬 수 · 팀 · 테이블 로드 수 · 경과 프레임(워치독)
   - 요청 파일 형식과 결과 파일 경로를 여기 적는다. [단계 5 - 클라](단계%205%20-%20클라.md) 가 이대로 만든다
5. 큐를 쓴다. 순서는 아래를 기본으로 둔다
   0. 패키지 설치 — [규약 - 패키지](규약%20-%20패키지.md) 의 두 패키지를 릴리스 페이지에서 태그 확인 → `manifest.json` → `refresh` 로 컴파일 0. 새 프로젝트면 이게 첫 항목이다
   1. 하네스. 이유: 기준만 정해 놓으면 아무도 안 잰다
   2. 계약이 물리는 골격 — 스키마 → Registry, 바인딩 계약 → 빌더 함수
   3. 코어 루프 화살표 순서대로
   4. 슬라이스 밖
6. 항목마다 완료 기준을 붙인다. 13행 완료 정의와 게이트 표에서 문장을 가져온다.
   못 쓰겠으면 확정표가 애매한 것이다. 사람에게 가져가기보다 [단계 0 - 접수](단계%200%20-%20접수.md) 추정 규칙으로 그 행을 다시 채우고 스펙 추정 절에 적는다

### 큐 항목의 모양

[예시]

```
### S-3. 처치 → 드랍
적이 죽으면 드랍 규칙(`Tables/drop`)에 따라 파츠 상자가 떨어진다.
- 완료 기준: god:60 리포트에 `drop_spawned >= 1` · 스크린샷에 상자가 보인다
```

제목은 루프의 화살표 이름이다. 완료 기준은 하네스 리포트의 키나 파일명으로 끝난다.

## 막혔을 때

| 상황 | 하는 일 |
|---|---|
| 코어 루프(9행)가 추정이다 | 장르 노트 "문법"의 루프를 그대로 쓴다. 스펙 추정 절 비용: "큐 전체 재작성" — 이 행이 추정이면 추정 표 맨 위에 온다 |
| 스키마 필드의 타입·단위를 모른다 | 레퍼 `design.tsv` 의 `unit` 열 → 없으면 `float`·`초`·`개` 기본값. 비용: "굽기 재실행 + Registry 필드 1개" |
| 바인딩 계약의 화면 수를 모른다 | 장르 노트 "데이터·UI 축"의 최소 화면 수. 비용: "화면 1개당 빌더 함수 1개 추가" |
| 하네스 리포트 키를 정할 근거가 없다 | 루프 화살표 이름을 그대로 키로 (`kill`·`drop_spawned`·`levelup`). 단계 5가 이 이름으로 찍는다 |

## 자주 틀리는 것

- 스키마 없이 콘텐츠 개수부터 큐에 넣는다. 스키마가 1번, 콘텐츠는 [단계 2 - 데이터](단계%202%20-%20데이터.md)
- 바인딩 계약을 "나중에 화면 만들 때"로 미룬다. 계약이 없으면 [단계 4 - UI](단계%204%20-%20UI.md) 트랙을 열 수 없다 (G0-b)
- 슬라이스에 아트 완성을 넣는다. 슬라이스는 프록시로 G4 를 통과하는 범위다. 아트는 단계 3에서 병렬로 간다
- 큐가 100줄을 넘는다. 넘으면 슬라이스가 너무 크다는 뜻이다 — 루프 밖으로 내린다
