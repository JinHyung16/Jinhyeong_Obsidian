# 역할 - 기획

기획 역할이 스펙 · 수치 · 콘텐츠를 어떻게 설계하고 무엇으로 판정받는지 모은 노트다. 시스템 스펙을 쓸 때, 밸런스를 잡을 때, 클라 · 아트로 넘기기 전에 편다.

[확정표 9·10·11] 이 이 역할의 입력이다.

## 이 역할이 지키는 것

기획의 산출물은 판정 가능한 문장이다. 클라가 "스펙대로 됐다 / 안 됐다"를 실측으로 가릴 수 있어야 스펙이다. 못 가리면 스펙이 아니라 소감이다.

| 소감 (반려) | 스펙 (통과) |
|---|---|
| 적당히 어렵게 | 5분 시점 동시 적 수 N, 평균 접촉 DPS M |
| 타격감 있게 | 피격 시 플래시 0.1초 + 넉백 0.5유닛 + 피해 숫자 팝업 |
| 점점 빨라지게 | 스폰 간격 A초 → B초, T초에 걸쳐 선형 감소 |
| 가끔 등장 | 등장 확률 표 (조건별 %) |

게이트 G1 은 이 표로 판정한다. "느낌 · 적당히 · 자연스럽게"를 검색한 결과가 0건이면 통과다.

## 코어 루프 — 모든 스펙의 뿌리

코어 루프는 한 문장으로 적고, 각 화살표를 시스템으로 분해한다.

```
[예시] 처치 → 재화 드랍 → 획득 → 레벨업 → 3택1 강화 → 더 강한 처치
       └스폰/전투  └드랍 규칙  └자석/획득 └경험치 곡선 └후보 풀 규칙
```

- 화살표 하나가 시스템 하나다. 화살표마다 스펙 문서가 있어야 루프가 돈다
- 루프에 없는 시스템(설정 · 도감 · 상점)은 슬라이스에서 빼는 것이 기본이다. [역할 - PD](역할%20-%20PD.md) 의 슬라이스 규칙과 같다
- 루프가 둘 이상이면(런 내 / 메타) 각각 따로 적고 접점(무엇이 넘어가나)을 명시한다

## 스키마가 먼저 나오면 클라가 같이 간다

기획의 첫 산출물은 기본이 콘텐츠 N건이 아니라 스키마 1장이다 ([역할 - PD](역할%20-%20PD.md) 트랙 절 · 게이트 G0-b).

```
[예시] 스키마 = 필드명 · 타입 · 단위 · enum 값 목록 · 필수여부 · 기본값 + 기대값 시나리오 1건
```

스키마가 나오면 클라는 더미 데이터 1~2건으로 기능을 끝까지 만들 수 있고, 기획은 그동안 콘텐츠를 쌓는다. 합류는 굽기 1회로 끝난다.

스키마 없이 콘텐츠부터 쌓으면 클라는 기다리게 된다. 그리고 나중에 필드 하나를 추가하는 일이 스키마 변경(PD 승인 + 굽기 검증 반영)이 된다. 스키마에 없는 필드는 클라가 조용히 무시한다 ([함정 1](함정%20-%20런타임%20배선.md)).

## 수치는 데이터 파일에, 규칙은 표로

기본은 수치를 엔진 코드가 아니라 확정표 5행이 정한 곳에 적는 것이다. 이유: 기획이 수치를 바꿀 때 클라를 부르게 되면 파이프라인 불합격이다 ([규약 - 데이터](규약%20-%20데이터.md)).

시스템 스펙을 이루는 네 가지:

1. 규칙 표 — 상태 · 조건 · 결과. 분기가 있으면 전 분기를 표의 행으로
2. 수치 표 또는 수식 — 곡선은 수식 + 대표 구간 값 3~5개를 같이 적는다. 이유: 수식만 주면 검산을 못 한다
3. 기대값 — 클라가 하네스로 대조할 구체 시나리오 ("X 상태에서 Y 하면 Z가 나온다")
4. 경계 조건 — 0일 때 · 최대일 때 · 동시에 터질 때 무엇이 맞는 동작인가

```
[예시] 경험치 곡선: 필요XP(lv) = 10 + (lv-1)*6  →  lv1:10, lv5:34, lv10:64
       기대값: 처치당 3XP × 4마리 = 12XP → lv1(10) 돌파, 잔여 2
```

### 파생 · 해금 규칙은 참조로 적는다

"A를 가진 상태에서만 B가 등장" 같은 의존은 id 직접 기입이 아니라 참조 표기로 데이터에 남기는 것이 기본이다 ([규약 - 데이터](규약%20-%20데이터.md) id 참조 절). 이유: 숫자 id 를 손으로 적으면 오타가 런타임까지 산다.

## 밸런스 방법론

- X축을 먼저 정한다. 세션 길이(확정표 10행)가 모든 곡선의 정의역이다
- 곡선은 3점만 정하고 시작한다: 시작값 · 목표 시점 값 · 상한. 중간은 보간으로 두고 실측 후 조정한다
- 첫 조정은 가설로 해도 된다. 두 번째 조정부터는 하네스 숫자를 보고 하는 것이 기본이다. 실측 없이 두 번 조정하지 않는다
- 난이도는 플레이어 성장 곡선과 위협 곡선의 차다. 한쪽만 만지면 반대쪽이 망가지므로, 조정할 때 두 곡선을 같은 표에 놓고 본다
- 무작위가 들어가는 곳(드랍 · 후보 풀 · 크리티컬)은 분산까지 스펙이다. 기대값만 적으면 체감 편차 민원을 판정할 기준이 없다. 최악 연속 실패 허용치(천장)를 함께 정한다
- 피격 무적(i-frame)이 없으면 접촉 피해가 프레임마다 들어가 프레임레이트가 곧 난이도가 되고, 어떤 수치로도 밸런스가 안 잡힌다. 있냐 없냐가 아니라 수치 스펙으로 정한다

## 선택지 시스템 설계 (강화 · 증강 · 카드류 공통)

장르 불문 반복되는 패턴이라 공통 규칙으로 둔다.

| 항목 | 정해야 하는 것 |
|---|---|
| 후보 풀 | 전체 목록 · 등장 조건(해금/의존) · 제외 조건(이미 보유 등) |
| 추첨 | 개수 · 가중치 · 중복 허용 여부 · 풀이 모자랄 때(3개 미만) 동작 |
| 적용 | 즉시/영구/스택 여부 · 같은 것을 다시 집었을 때 |
| 표시 | 이름 · 설명 · 등급의 정보량. 설명은 수치를 포함하는 것이 기본 ("강해진다" 대신 수치) |
| 시간 | 선택 중 월드가 완전히 멈추는가. 안 멈추면 선택이 벌칙이 된다 |

## 콘텐츠 설계 — 종류를 늘리기 전에 축을 늘린다

콘텐츠 N개를 찍기 전에, 그 콘텐츠들이 어떤 축에서 서로 달라지는지부터 정하는 것이 기본이다.

```
[예시] 발사 방식(직선/유도/관통/장판) × 수치 프로필(속사/중타) × 속성(연출·상태이상)
```

축이 3개면 조합으로 수십 종이 나오고, 데이터 파이프라인이 조합을 지원하면 콘텐츠 1종 = 데이터 1파일이 된다 ([규약 - 데이터](규약%20-%20데이터.md) 조합형 절).

축 없이 개별 제작한 콘텐츠 10개보다, 축 위에 놓인 6개가 확장이 빠르고 밸런스도 잡힌다.

### 두 분류 축의 충돌 확인

축을 정하면 조합 표를 실제로 그려서 빈칸 · 불가능 칸을 눈으로 본다 ([함정 32](함정%20-%20데이터%20설계.md)).

## 레퍼런스를 다루는 법

- 레퍼런스는 베끼는 대상이 아니라 실측 대상이다. 영상에서 프레임을 뽑아 UI 배치 · 타이밍 · 밀도를 표로 만들고, 우리 스펙과 다르게 갈 곳을 명시한다
- 스펙에는 "레퍼런스처럼" 대신 레퍼런스에서 잰 값을 적는 것이 기본이다
- 장르 관례([장르 문법 지도](장르%20문법%20지도.md))와 레퍼런스가 충돌하면 관례가 왜 생겼는지부터 확인한다. 관례는 대개 실패의 흉터다
- 절차는 [레퍼런스 해부](레퍼런스%20해부.md)

## UI 정보 설계 — 기획이 정해야 화면이 나온다

아트 · 클라가 화면을 만들기 전에 기획이 답해야 하는 것:

- 이 화면에서 플레이어가 내리는 결정이 무엇인가 (없으면 그 화면은 필요 없다)
- 그 결정에 필요한 정보의 우선순위 1 · 2 · 3위. 나머지는 접거나 뺀다
- 한 화면에 몇 개를 보여줄 것인가. 개수 상한이 곧 목록 방식을 정한다 ([규약 - UI](규약%20-%20UI.md))
- 값이 언제 갱신되는가 (실시간 / 화면 열 때 / 서버 응답 시)

"화면 와이어 + 필요 에셋 목록(역할 단위)"이 아트로 넘어가는 산출물이다 ([역할 - PD](역할%20-%20PD.md) 인수인계 절).

## 기획이 자주 내는 사고

- 수식은 극단값 두 개를 대입해 검산하고 결과를 표에 같이 적는다 ([함정 59](함정%20-%20전투%20규칙.md))
- 규칙 두 개가 겹치는 경우는 표의 행으로 만들어 정한다 ([함정 60](함정%20-%20데이터%20설계.md))
- 회복 수단 없는 생존 스탯은 고르는 사람이 없다 ([함정 35](함정%20-%20전투%20규칙.md))
- 단위 누락 — 초인지 프레임인지, % 인지 배수인지. 모든 수치 열에 단위를 적는 것이 기본이다

## 마케팅을 고려한 기획 — 이름과 기대감도 스펙이다

기획은 "잘 돌아가는 시스템"을 넘어 유저가 해보고 싶어지는 것을 만든다. 메커니즘이 같아도 이름 · 연출 · 설명이 다르면 유저에게는 다른 콘텐츠이고, 그 기대감이 스토어 페이지 · 스크린샷 · 광고 소재가 된다.

- 게임명 · 캐릭터명 · 스킬명은 세계관 어휘로 짓는 것이 기본이다. 기능명(`직선 투사체`)을 그대로 노출하지 않는다. 내부 id 는 기능명, 노출명은 세계관명으로 두고 둘을 데이터에서 분리해 둔다 (`id` / `displayName`)
- 메커니즘 1개 = 노출 콘텐츠 N개가 정상이다. 발사 방식이 같아도 캐릭터 · 속성 · 연출 · 이름을 달리해 별개 콘텐츠로 낸다. 이름이 다르면 기대감이 생기고, 기대감은 해금 동기가 된다
- 해금 콘텐츠는 "보이되 못 쓰는" 상태가 기본이다. 잠긴 노드의 이름 · 아이콘 · 한 줄 설명은 보여 준다. 이유: 안 보이는 콘텐츠는 기대감을 못 만든다
- 설명 한 줄은 광고 카피처럼 쓰되 수치는 유지한다. 수치 없는 카피는 스펙 불합격, 카피 없는 수치는 마케팅 불합격이다
- 네이밍 규칙을 표로 먼저 정한다. 어미 · 말장난 · 세계관 용어 목록을 적어 두면 콘텐츠 N개의 이름이 한 톤으로 나온다. 개별 작명보다 규칙이 먼저다
- "스크린샷 한 장으로 설명되는가"를 콘텐츠 검수 항목에 넣는다. 연출 · 이름 · 숫자 팝업이 한 프레임에 들어오면 합격이다
