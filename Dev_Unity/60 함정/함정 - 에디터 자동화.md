# 함정 - 에디터 자동화

에디터를 자동화로 띄우고 요청을 넣고 돌리는 과정에서 포커스·도메인 리로드·프로세스 수명·잠금이 어긋나, 에러 없이 멈추거나 남의 작업을 건드린 사고다. 에디터를 띄우거나 끌 때, 요청 파일·태스크를 넣을 때, "자동화가 반응이 없다"를 볼 때 편다.

## 에디터 루프와 요청 파일

### 백그라운드에서 멈추는 게임 루프
번호: 함정 5
- 증상: 자동화·하네스가 돌지 않는다. 자동 검증이 frame=2 에서 영원히 대기한다.
- 원인: 에디터가 포커스를 잃으면 플레이가 정지한다.
- 방향: 기본은 `runInBackground` 를 프로젝트 설정에 영구 반영하는 것이다.
- 관련: [규약 - 플랫폼](규약%20-%20플랫폼.md) · [역할 - 클라](역할%20-%20클라.md)

### 도메인 리로드 때만 도는 훅 + 포커스 때만 도는 임포트
번호: 함정 6
- 증상: 요청 파일이 영영 안 잡히거나, 백그라운드 자동화가 조용히 멈춘다.
- 원인: `[InitializeOnLoad]` 는 리컴파일 때만 실행되어 C# 변경이 없으면 요청 파일이 영영 안 잡힌다. 에디터는 포커스 시에만 에셋 임포트를 한다. 또 새로 만든 훅 자신은 컴파일 전이라 자기 요청을 못 본다 (닭-달걀).
- 방향: 기본은 훅을 `EditorApplication.update` 상시 감시로 두고 `AssetDatabase.Refresh()` 를 직접 호출하는 것이다. 새 훅의 첫 실행은 기존 훅으로 리컴파일을 유발해서 태운다.
- 관련: [역할 - 클라](역할%20-%20클라.md) · [양식 - 하네스](양식%20-%20하네스.md)

### Temp 는 에디터 기동 시 비워진다
번호: 함정 26
- 증상: 에디터가 켜졌는데 자동화 요청에 반응이 없다. "분명 넣었는데 반응이 없다"로 보인다.
- 원인: 요청 파일 방식 하네스에서 에디터를 띄우기 전에 요청을 넣어 두면 기동 과정에서 지워진다.
- 방향: 기본은 요청을 에디터가 완전히 뜬 뒤에 넣는 것이다. 그리고 하네스는 플레이를 마치고 편집 모드로 돌아올 때 감시자를 다시 등록한다 — 안 하면 그 뒤 요청이 전부 무시된다.
- 관련: [양식 - 하네스](양식%20-%20하네스.md) · [함정 49](함정%20-%20구조%20설계.md)

### 새로 고침 직후 플레이 진입 — 도메인 리로드가 자동화를 먹는다
번호: 함정 33
- 증상: 자동화가 플레이 진입 직후 응답이 없다. 증상은 "에디터가 멈춤"으로 보이고 로그에도 에러가 없다.
- 원인: 요청 파일을 감지하고 에셋 새로 고침 → 곧바로 플레이 진입을 한 프레임에 했더니, 컴파일이 한 박자 늦게 시작되면서 플레이 진입 도중 도메인 리로드가 났다. 하네스의 정적 상태가 통째로 날아가 리포트가 영영 안 나온다.
- 방향: 기본은 새로 고침과 진입 사이에 최소 한 폴링을 띄우는 것이다. 새로 고친 다음 턴에 컴파일 중이 아님을 확인하고 들어간다.
- 관련: [함정 38](함정%20-%20하네스%20측정.md) · [양식 - 하네스](양식%20-%20하네스.md) · [역할 - 클라](역할%20-%20클라.md)

## 에디터 프로세스와 인스턴스

### 자동화 셸의 자식으로 띄운 에디터
번호: 함정 23
- 증상: 자동화로 띄운 에디터가 곧바로 죽는다. 다음 단계가 "에디터가 없다"로 실패하고 원인이 보이지 않는다.
- 원인: 에디터를 자동화 셸의 자식 프로세스로 띄워, 그 셸 작업이 끝날 때 같이 죽었다.
- 방향: 기본은 부모와 수명을 끊어 띄우는 것이다. 띄운 뒤 프로세스 목록에서 프로젝트 경로로 확인한다 — 다른 프로젝트가 열려 있는 것을 우리 것으로 착각하기 쉽다.
- 관련: [함정 40](함정%20-%20에디터%20자동화.md)

### 강제 종료를 반복하면 복구 다이얼로그가 에디터를 막는다
번호: 함정 25
- 증상: 에디터가 켜졌는데 자동화 요청에 반응이 없다. 프로세스는 살아 있고 로그도 깨끗해서 "하네스가 고장났나"로 보인다.
- 원인: 자동화가 에디터를 강제 종료하면 다음 기동 때 "이전 세션의 씬 백업을 복구할까요" 창이 뜬다. 이 창이 떠 있는 동안 에디터 업데이트 루프가 돌지 않아 요청 파일을 영영 집어가지 않는다.
- 방향: 기본은 자동화가 종료를 정상 경로로 하는 것이다. 그래도 떴는지 확인하려면 창 제목을 본다 — 프로젝트 이름이 아니면 다이얼로그가 떠 있는 것이다. 뜬 경우 버튼을 찾아 눌러 해제한다. [원칙](Dev_Unity%20원칙.md)
- 관련: [함정 40](함정%20-%20에디터%20자동화.md) · [함정 49](함정%20-%20구조%20설계.md)

### 유니티 프로세스를 필터 없이 죽이면 남의 작업을 닫는다
번호: 함정 40
- 증상: 다른 프로젝트의 유니티가 강제 종료되고, 다음에 그 프로젝트를 열면 "Scene backups 복구" 대화상자가 뜬다.
- 원인: 배치 빌드 전에 에디터를 정리하려고 `Get-Process Unity | Select -First 1 | Stop-Process` 를 썼다. 다른 프로젝트의 유니티가 함께 떠 있으면 그쪽이 먼저 잡힌다.
- 방향: 기본은 프로세스를 명령줄의 projectPath 로 고르는 것이다 (아래 명령). 창 제목은 부팅 중이거나 대화상자가 뜨면 비어 있거나 "Error!" 라서 믿을 수 없다. [원칙](Dev_Unity%20원칙.md)
  - 되받기: 같은 이유로 "우리 인스턴스가 떠 있나" 판정도 제목으로 하면 틀린다. 제목이 아직 비어 있는 동안 "없다"로 보고 같은 프로젝트를 두 번 열면, 유니티가 이를 막으며 에러 대화상자를 띄우고 에디터가 그대로 멈춘다. 요청 파일이 영영 소비되지 않는다.
  - 되받기 2: 라이선스 클라이언트가 에디터 여러 개에서 흔들린다(`Unsupported protocol version` 505). 남이 유니티를 쓰는 중이라면 자동 측정을 계속 돌리지 않고 멈춘다 — 측정 하나가 남의 세션보다 비싸지 않다. [원칙](Dev_Unity%20원칙.md)
- 관련: [함정 23](함정%20-%20에디터%20자동화.md) · [함정 25](함정%20-%20에디터%20자동화.md) · [함정 42](함정%20-%20에디터%20자동화.md)

```
Get-CimInstance Win32_Process -Filter "Name='Unity.exe'" |
  Where-Object { $_.CommandLine -like '*<프로젝트명>*' }
```

### 배치모드를 쓰려고 에디터를 껐다 켰다
번호: 함정 41
- 증상: 빌드·검증마다 에디터 부팅(20초+)을 수십 번 반복한다.
- 원인: `-batchmode -executeMethod` 는 프로젝트를 배타적으로 잠근다(`Temp/UnityLockfile`). GUI 에디터가 떠 있으면 두 번째 인스턴스가 못 뜬다. 그래서 빌드·검증마다 에디터를 죽이고 배치를 돌리고 다시 띄웠다 — 리로드가 필요해서가 아니라 잠금 때문이었다.
- 방향: 기본은 이미 떠 있는 에디터에 태스크를 넘기고 에디터를 끄지 않는 것이다. [원칙](Dev_Unity%20원칙.md)
  - [예시] `EditorTaskRunner` 가 `Temp/editor.task` 를 폴링해 `refresh · build · validate · nodes` 를 그 자리에서 돌리고 결과를 `Temp/editor.task.log` 에 쓴다. `/tmp/task.sh <작업>` 이 그것을 부른다.
  - 부트스트랩만 예외다 — 새 에디터 스크립트는 한 번 임포트돼야 살아난다. 백그라운드 프로세스의 `SetForegroundWindow` 는 윈도우가 실제 포커스로 인정하지 않아 오토 리프레시가 안 돈다. 이미 컴파일돼 도는 하네스(`runloop.request`)로 한 번만 돌리면 된다.
- 관련: [양식 - 하네스](양식%20-%20하네스.md) · [함정 6](함정%20-%20에디터%20자동화.md)

### 인스턴스 감지를 인라인 PowerShell 로 했다가 프로젝트를 두 번 열었다
번호: 함정 42
- 증상: 같은 프로젝트가 두 번 열려 에디터가 언다.
- 원인: 여러 줄 PowerShell 을 `$( )` 안에 넣었더니 빈 문자열이 돌아왔고, "에디터 없음"으로 판정했다. 같은 프로젝트 중복 실행은 에디터를 얼린다.
- 방향: 기본은 감지를 스크립트 파일로 빼고 개수만 받는 것이다. 숫자가 아니면 새로 띄우지 않고 멈춘다 — 모르는 상태에서 띄우는 쪽이 안 띄우는 쪽보다 훨씬 비싸다.
- 관련: [함정 40](함정%20-%20에디터%20자동화.md)

## 세션과 로그

### 자동화 세션을 에디터보다 먼저 켰다
번호: 함정 57
- 증상: 에디터 브리지가 붙지 않는다.
- 원인: 에디터 브리지는 세션 시작 시점에 한 번 연결된다. 에디터를 나중에 띄우면 끝내 붙지 않는다.
- 방향: 기본은 화면을 봐야 하는 작업이면 에디터를 먼저 띄우는 것이다. 안 붙었으면 배치 모드로 내려가되 무엇이 막혔는지 보고하고 화면 판정은 보류한다.
- 관련: [함정 43](함정%20-%20판단%20검증.md)

[사고] 세션을 먼저 켜고 에디터를 띄워 브리지 없이 진행했고, 화면 판정을 하지 못했다.

### 다른 프로젝트의 로그를 우리 것으로 읽었다
번호: 함정 58
- 증상: 로그에 우리와 상관없는 오류가 보인다.
- 원인: 에디터 로그의 기본 경로는 여러 프로젝트가 같이 쓴다.
- 방향: 기본은 배치 실행에 `-logFile` 로 프로젝트별 로그를 받는 것이다. 로그 안의 프로젝트 경로를 먼저 확인한다.
- 관련: [함정 40](함정%20-%20에디터%20자동화.md)

[사고] 다른 프로젝트의 임포트 로그를 보고 우리 프로젝트 오류로 판단했다.
