# 함정 - 데이터 설계

분류 축·열 타입·스폰 규칙·규칙 겹침이 설계 단계에서 정해지지 않아, 시스템은 도는데 결과가 도달 불가능하거나 매판 달라진 사고다. 스키마·분류 축·이벤트 스폰·규칙 표를 설계할 때, "없다"로 보이는 증상을 볼 때 편다.

### 두 분류 축이 충돌해 조합이 도달 불가능해진다
번호: 함정 32
- 증상: 조합 시스템을 넣었는데 조합이 한 번도 안 뜬다. 시스템은 멀쩡히 돈다.
- 원인: "부위 6칸"(착용 제약)과 "계열 6종"(조합 조건)을 각각 설계했더니, 한 계열의 콘텐츠가 한 부위에 몰려 있는 경우가 생겼다. 부위당 하나만 착용 가능하므로 그 계열은 최대 1개, 즉 계열 조건(2개/4개)이 영원히 충족 불가능하다.
- 방향: 기본은 분류 축을 두 개 이상 두면 교차표를 만들어 도달 가능성을 먼저 세는 것이다 — "계열별로 서로 다른 부위가 몇 개인가"가 곧 착용 가능한 최대 개수다. 조합을 만들라면서 조합을 막는 제약이면 제약을 버린다. 검출은 리포트에 "발동 중인 조합" 개수를 찍는 것이다. 오래 돌려도 0 이면 확률이 아니라 구조를 의심한다.
- 관련: [단계 2 - 데이터](단계%202%20-%20데이터.md) · [규약 - 데이터](규약%20-%20데이터.md)

[사고] 6계열 중 하나는 0% · 넷은 2단계까지만 · 하나만 4단계 가능이었다.

### bool 열에 숫자 1을 넣으면 조용히 false 가 된다
번호: 함정 36
- 증상: "보스가 안 나온다". 실제로는 보스가 스폰돼 있었고 표식만 안 붙었다.
- 원인: 데이터에 `boss: 1` 을 쓰고 열 타입을 bool 로 선언했다. 파서의 `AsBool()` 은 값 타입이 Bool 일 때만 읽고 아니면 기본값(false)을 돌려준다. 에러도 경고도 없다.
- 방향: 기본은 bool 열에 `true`/`false` 를 쓰는 것이다. 생성기를 거친다면 생성기가 그렇게 내보내는지 본다. 검출은 "없다"로 보이는 증상에 그 반대 증거를 같이 찍는 것이다 — "보스 미등장" 옆에 살아 있는 적 중 최대 체력을 찍었더니 97,200 이 나와, 스폰 실패가 아니라 표식 실패임이 한 줄로 갈렸다.
- 관련: [규약 - 데이터](규약%20-%20데이터.md) · [함정 55](함정%20-%20하네스%20측정.md)

### 이벤트 스폰이 타입을 안 정하면 보스가 매판 다른 몸으로 나온다
번호: 함정 37
- 증상: 보스 체력·속도가 판마다 크게 달라, 어떤 판에선 "피하면서 깎는" 보스전이 성립하지 않는다.
- 원인: 보스를 "그때 등장 가능한 적 중 가중치 추첨 + 체력 배수"로 만들었다.
- 방향: 기본은 하나만 나오는 개체의 타입을 데이터로 지정하는 것이다. 추첨은 정예처럼 물량으로 소비되는 이벤트에만 쓴다.
- 관련: [규약 - 데이터](규약%20-%20데이터.md)

[사고] 꼬물이(50)로 뽑히는 판과 우락이(200)로 뽑히는 판의 보스 체력이 4배 차이가 났고, 속도도 3.2 vs 2.0 이었다.

### 두 규칙이 겹치는 경우가 정해져 있지 않다
번호: 함정 60
- 증상: 규칙끼리 겹칠 때 동작이 매번 다르다.
- 원인: 규칙 하나하나는 명확해도 동시에 걸리는 경우가 빠져, 구현하는 사람이 임의로 정했다.
- 방향: 기본은 규칙 두 개가 겹치는 경우를 표의 행으로 만들어 정하는 것이다.
- 관련: [역할 - 기획](역할%20-%20기획.md)

[사고] "지나가면 발동"과 "큰 이동"이 겹쳤을 때 한 번에 몇 번 발동하는지 아무도 정하지 않았다.
